* External-Tool (LTI) Assignments — and No Turnitin

An assignment whose submissions an LTI tool takes (Gradescope is the case this was built for) carries =EXTERNAL_TOOL_URL= and/or =EXTERNAL_TOOL_ID= beside =SUBMISSION: external_tool=. =org-canvas--assignment-add-external-tool= nests them into =external_tool_tag_attributes= — a URL, or =content_id= plus the =content_type= Canvas requires — and always sends =new_tab=, since an explicit false is meaningful. Because the field is nested, all three properties declare a =:remote-fn= (=org-canvas--assignment-remote-tool-*=); read flat, =alist-get= returns nil and /every/ external-tool assignment reports drift forever. =org-canvas--validate-external-tool= warns both ways: =external_tool= naming no tool (Canvas creates an assignment that launches nothing and fails only when a student opens it) and a tool named without =external_tool= (silently ignored). Launch URLs are not guessable, so =org-canvas-list-external-tools= lists them — it passes ~include_parents=true~, without which Canvas returns only course-installed tools and institutional courses come back empty.

The boundary: org-canvas owns the Canvas side only. Gradescope has no supported public API, so the tool-side assignment and its grade push stay in Gradescope's hands; grades arrive in Canvas over LTI and the submissions module reads them from there.

*Turnitin support was removed, deliberately — do not add it back without re-probing.* =TURNITIN_ENABLED= drove the legacy account-level plugin. Probed live on 2026-08-25 against clemson.instructure.com: zero of 62 assignments carried a =turnitin_enabled= key, so the plugin is off; Turnitin is installed as an LTI 1.3 tool (=assignment_selection: no=), the plagiarism-review association, which the Assignments REST API does not expose. The property was inert and =turnitin_settings= would have been dead code. The fields remain in =test/contract/canvas-contract.json= because that fixture describes Canvas's API, not ours.

*Turnitin's document-processor mode is observed, never set (issue #184).* The mode an =online_upload= course actually wants — PDF stays in Canvas, grading in SpeedGrader, the similarity report from the score — is Canvas's LTI Asset Processor placement, and Canvas's own reference for =assignment[asset_processors][]= says a new one can be added only through the interactive Deep Linking flow in a browser, not by API token; only /deletion/ (an empty array) is allowed by API. So the shape is observe and protect: =DOCUMENT_PROCESSOR= is a =:canvas-owned= string property on the assignments registration with a =:remote-fn= (=org-canvas--assignment-remote-document-processor=) reading =asset_processors=. The pull writes it, =org-canvas--diff-compare-fields= compares a =:canvas-owned= spec even when the heading is silent (silence is not the file's opinion about a field it cannot hold one on, and a processor attached after the last pull is the whole point of the row), =org-canvas--validate-check-canvas-owned= warns, push-only, when it is typed on a heading with no =CANVAS_ID=, and the payload builder never emits the field — a test holds it to that, because an empty array would strip a processor attached by hand. The response shape was not observable when this was written (probed 2026-09-10: none of the 78 assignments on the course carried the key, with or without an =include[]=), so the reader takes a name from =title=, =tool_name=, the nested tool's =name= or =text=, and the =id=, and never raises. The legacy =turnitin_enabled= flag stays out for the reason above.

*The processors come from GraphQL, REST is the fallback (issue #350).* The REST key never arrived: on course 297530 (2026-09-25) =GET assignments/:id?include[]=asset_processors= carried no processor key on any assignment, while one GraphQL request over the course listed five columns with Turnitin attached — so =DOCUMENT_PROCESSOR= had been nil on every heading and neither this guard nor #293's could fire. =Assignment.ltiAssetProcessorsConnection= is the source now. =org-canvas--assignment-processors-query= reads =course.assignmentsConnection= a page of 100 at a time, each node's =_id= and its processors' =_id=, =title= and =externalTool { _id name }=, and =org-canvas--assignment-processors-map= keeps the result as a hash by assignment id — an empty list for a column GraphQL answered with none. It is read once per command and forgotten on =org-canvas--operation-start-hook=, the checkpoint map's pattern (#216): a pull, a drift report, a pull-at-point each make one request whatever the number of assignments, and nothing read in one command reaches the next (#72, #141). The remote-fn prefers the GraphQL answer; an assignment it did not answer for (created after the read) falls back to the REST =asset_processors= key, and a refused read (one warning, then =refused= for the rest of the command, the #171 rule) falls back for all of them. =org-canvas--assignment-describe-processor= names a GraphQL node by its title and the tool it launches, =Turnitin (tool 41668)= — the tool id recurs across columns, where the processor's own id does not — and keeps =Turnitin (asset processor 12345)= for a REST entry. The spec also declares =:remote-known-p= and =:compare-p= (=org-canvas--assignment-document-processor-known-p=): when neither source answered for an item, a pull leaves the property as it is and the drift report does not compare it, rather than reading silence as "no processor". The query is a read, so it runs under =org-canvas-read-only=, and nothing about the push changes: no payload carries =asset_processors= (Hard Rule 5).

* A Wanted Document Processor Is Declared, Compared, Never Sent (issue #293)

*The gap #184 left.* =DOCUMENT_PROCESSOR= records what Canvas holds, so a column where the browser step was never taken looked exactly like one where Turnitin was never wanted: nothing in Org could say the syllabus promised it, and neither validate nor the drift report had anything to compare. On course 297530 (2026-09-18) the Global Challenge Essay was the one essay the syllabus sent through Turnitin, and it had no processor. A course copy, a re-created column or a tool reinstall drops one just as silently.

*The shape: an intent property, held against the observed one.* =WANT_DOCUMENT_PROCESSOR= is an ordinary string on the assignments registration that declares =:intent-of "DOCUMENT_PROCESSOR"=. The registry key is the whole mechanism, so the next browser-only attachment gets the same treatment by declaring one line. Such a property is compared and never sent: =org-canvas--pull-apply-spec= skips it (a pull would otherwise erase the declaration with the very observation it is checked against), the assignments parse never reads it, so it never reaches the payload or the payload hash (a test holds both), and Hard Rule 5 is untouched — there is still no path by which =asset_processors= leaves the package. =org-canvas--intent-satisfied-p= is the one match: case-insensitive substring of the declared name in the observed text, since the observation carries an id and whatever name the tool gives itself (=Turnitin (asset processor 12345)=), and the declaration is the word a person types.

*Two checks, two clocks.* =org-canvas--validate-check-intent= is offline, so it compares against the =DOCUMENT_PROCESSOR= the last pull wrote: on a stamped heading with nothing matching it warns, naming what was recorded and the browser step. It is not push-only (#168) — a column missing its processor is the course's state whatever you do next — and it is silent on an unstamped heading, where there is no column to attach to yet. =org-canvas--diff-compare-intent= reads what Canvas says now, through the observed spec's own =:remote-fn=, and an unmet declaration is a field row on a =CHANGED= entry, counted as drift so =org-canvas-diff-batch= exits non-zero. A field row also keeps the entry out of stamp adoption (#257), which is right: adopting a stamp would not attach anything.

*The reverse is a note, not drift.* A processor Canvas holds that no heading declares is a legitimate state the file has not adopted. =org-canvas--diff-entry-notes= reports it as a =NOTE= row in the result's =:notes=, which =org-canvas--diff-count= does not see; the feature header reads "N divergence(s), M note(s)" and a report of notes alone still says "No drift". Before the first pull after an attach, the =:canvas-owned= =DOCUMENT_PROCESSOR= row already covers the change, and the intent row stays quiet because the declaration is met.

*An instance that never reports the field.* The probe on 2026-09-18 found no =asset_processors= key on the assignment GET at all, with or without =include[]=asset_processors=, so on such an instance the observed side does not exist and every declaration is unmet. The diff says so instead of claiming Canvas holds nothing: its Canvas column reads =(not reported by Canvas)= when neither source answered and =(none; attach it in the web UI, B opens the edit page, then pull)= when Canvas answered with an empty list. Which one is the spec's own say (=org-canvas--registry-remote-present-p=, through its =:remote-known-p=), not the REST key's presence. Since #350 the answer comes from GraphQL, which that instance does report, so the check works there unchanged; =(not reported by Canvas)= is left for a refused GraphQL read on an instance that also omits the REST key.

*Rejected: making =DOCUMENT_PROCESSOR= itself typeable as the intent.* A property that a pull overwrites cannot also be the file's opinion; the first pull on a column without a processor would delete the promise. Two properties keep "what should be" and "what is" apart, which is what lets each check say which side is wrong.

* Canvas-Owned Submission Types (issue #167)

A freshly pulled, unmodified =assignments.org= failed =org-canvas-validate= once per classic quiz — 20 errors on Clemson CPSC 3720 F26, all =SUBMISSION: invalid value(s) 'online_quiz'=. Nobody typed it: every classic quiz and every graded discussion owns a shadow assignment, Canvas reports its =submission_types= as =online_quiz= or =discussion_topic=, and =org-canvas-pull-assignments= wrote that down faithfully into a file its own validator then rejected. Twenty false errors buried the four real ones (#164's superseded twins) in the same report, in exactly the situation — adopting an inherited course — where validate has the most to say.

The values are legitimate /input/, so they are declared as input: =org-canvas--canvas-owned-submission-types= is a =:read-only-values= list on the SUBMISSION property registration, a registry key =org-canvas--property-to-validate-prop= threads into the validate spec, where =org-canvas--validate-entry-properties= appends it to =:values= before the enum checks run. =org-canvas--assignment-parse-submission-types= stopped warning about them for the same reason — it fired on every parse of every quiz-backed heading. The generated Property Reference marks them "(set by Canvas: ...)" rather than listing them as things to type.

*The push is where the line is drawn, and it is drawn at create, not at update.* Canvas's own enum for =assignment[submission_types]= includes both values, and a quiz-backed assignment updated through the assignments API is the ordinary case — Canvas keeps the quiz and its assignment in step — so an update sends the value through untouched and nothing was made to fail that works today. A /create/ cannot work: an assignment with no =CANVAS_ID= and =SUBMISSION: online_quiz= is a quiz, and the assignments endpoint is not what brings one into being. =org-canvas--assignment-check-owned-submission=, called from the payload builder beside =org-canvas--validate-date-ordering=, stops that one with the owning file named (=quizzes.org=, =discussions.org=) instead of letting Canvas make of the request whatever it makes.

Do not "fix" this by adding the two values to =org-canvas--valid-submission-types=: that is the push-side list, and it is what keeps the create guard honest.

* Quiz Publish Sequencing

Classic quizzes keep =published= *out* of the quiz payload entirely; =org-canvas--quiz-settle-publish-state= applies it in finalize /after/ =org-canvas--quiz-sync-children= writes the questions. Canvas computes =points_possible=/=question_count= (and the backing assignment's points) on a publish transition, not on question insert, so publishing on the create POST froze an empty quiz's totals at zero (issue #59). Omitting the key also leaves an existing quiz's state untouched on a PUT. For a quiz that was /already/ published, =org-canvas--quiz-refresh-totals= GETs it and republishes only when =org-canvas--quiz-totals-stale-p= sees the remote count /behind/ what was written — a higher remote count means orphan questions, not staleness — and only when =unpublishable= is t; with submissions it warns instead.

* A Push Compares What Canvas Stored With What It Sent (issue #349)

A copied anonymous survey pushed as a named one, and the same push sent =SCORING_POLICY: keep_latest=, which Canvas answered with =keep_highest=; both reports said "synced", and only the next =org-canvas-diff= showed the scoring policy. A survey's anonymity is a promise to its respondents, and a response submitted named cannot be made anonymous afterwards, so this is the one quiz setting a silent miss must never cover.

*=ANONYMOUS_SUBMISSIONS= is a registered quiz property.* It parses, is sent, pulls and compares like the other booleans, with two differences. A written =false= is sent as false, not left out (=org-canvas--quiz-explicit-boolean=): a heading that says "named" means it, where the older booleans only ever send =true=. And a pull corrects a drawer that says =true= when Canvas holds the survey named (=org-canvas--quiz-pull-set-kept-boolean=), where the older booleans leave a stale =true= in place, so the next push cannot quietly change it back. =create_quiz= and =edit_quiz= in the OpenAPI spec omit the field though the Quiz object carries it, and a PUT of it worked on the live course, so the contract test lists it as a justified exception. Validate warns, push-only, on an /unstamped/ =survey= or =graded_survey= that does not set it (=org-canvas--validate-quiz-anonymity=, run from the quiz structural check): its push creates the survey, and Canvas creates it named. A stamped survey is left alone, since its push sends nothing about anonymity and changes nothing.

*The echo check is registry-driven and warns only.* Canvas answers a create or update with the object as it stored it. =org-canvas--registry-warn-echo= (core-sync) takes a feature's property registration, the payload's object and that reply, and logs one =[Verify]= warning per property the payload carried that came back different, naming both values in their Org spelling. The stored side is read through =org-canvas--registry-remote-field=, so a =:remote-fn= answers for a nested or renamed field (Hard Rule 18), and the comparison follows the drift report's: numbers by value, CSV lists as sets, booleans with false and null agreeing, timestamps to the minute. A property the push never sends (=:canvas-owned=, =:intent-of=, =:local-only=, =:pull-only=) and a =link= are left out; so is a field the reply does not report, which is also why a dry run, whose sentinel reply reports nothing, is silent. Quizzes call it from =org-canvas--quiz-verify-response=, in finalize, with the payload rebuilt from the parsed data; another module can call it from its own finalize when a live course shows the need. It never fails the push: the item exists and must be stamped, and whether Canvas's value or the file's is right is for the instructor, who now hears about it at push time rather than at the next diff. Why Canvas kept =keep_highest= for that survey is not known; the check reports it rather than working around it.

* Rubrics Update In Place (issue #123)

A rubric push used to /delete/ whatever carried the title and POST a fresh one. Associations belong to the old rubric id, so every assignment silently lost its rubric — and the rubric assessments students were graded with would have gone with it; on the course this was found on, only the essay's lack of submissions kept it from being data loss. =org-canvas--rubric-push-to-api= is now the generic =org-canvas--push-to-api= on =rubrics=: a CANVAS_ID is PUT to =rubrics/ID= (Canvas updates the criteria in place, keeping the id, its associations and its assessments), a heading without one creates, a title Canvas already holds goes through the duplicate-title guard (#85) instead of a DELETE, and a stale id 404s into a POST. =org-canvas--rubric-finalize= unwraps the =rubric= key and delegates to =org-canvas--finalize-item=, so rubrics finally stamp like everything else; =org-canvas--rubric-warn-recreated= says so loudly if the id comes back different, the one case where linked assignments still need a re-push. *The Rubric API object carries no =updated_at=* (checked against =documentation/architecture/canvas-openapi3.yaml=), so the conflict check can never fire for a rubric — it costs one GET and is left in for uniformity, not for detection.

* Rubric Updates Keep Their Ids and Their Assignments (issues #255, #256)

#123's update in place held for the essay rubric it was found on, which one assignment graded with. The Closer Rubric (138462, attached with =use_for_grading= to 25 closer columns) answered a one-line wording change with a /new/ rubric, "Closer Rubric (1)", and kept 138462 and all 25 associations as they were; a second PUT without =rubric_association= in the payload forked again. The rule on Canvas is that a rubric more than one assignment grades with is copied, never updated, whatever the request carries. org-canvas stamped the copy, so the drift report called the original EXTRA while every closer still used it, and the #123 warning said the assignments had lost their rubric when nothing had moved (#255). The second finding came while repairing it: =org-canvas--rubric-build-criterion= sent no =id= for a criterion or a rating, and Canvas mints one for everything it is not handed (=Rubric#unique_item_id=), so /every/ in-place update rotated every criterion id — orphaning each =rubric_assessment= already entered, which reference =criterion_id=, and every =** Rubric= table in a grading file, which keys its rows by that id (#252) and would push =rubric_assessment[_old]= at a rubric that no longer has it (#256).

Both are settled in the push, before the generic PUT. =org-canvas--rubric-push-to-api= reads the rubric as Canvas holds it once, =rubrics/ID?include[]=associations= (=org-canvas--rubric-fetch-live=; a failed read is a warning, not a stop), and:

- =org-canvas--rubric-pin-ids= writes each criterion's and rating's id into the payload. Every criterion heading carries a =CANVAS_CRITERION_ID= (=org-canvas--rubric-criterion-id-property=): finalize stamps it from the response, whose =data= lists the criteria in payload order (=org-canvas--rubric-stamp-criterion-ids=), and a pull writes it beside =OUTCOME=. The stored id wins when the live rubric still lists it, so a reworded criterion keeps its id and its assessments; a heading without one — the first push after this change — takes the live criterion at its position when the descriptions match, else the first of that description anywhere, so a reorder is not a rotation; and a stored id Canvas no longer lists is sent back anyway, since Canvas keeps any id it is handed and a criterion wiped by a bad PUT (the issue's repair script did that) comes back under the id the grading tables know. Ratings are not stored: they match by description and points, then by description, within their criterion, the default Full Marks/No Marks pair included; Canvas keeps them sorted by points, so position means nothing. What matches nothing is new and Canvas mints it. The ids live in the push, not the payload builder, so the payload hash is content only and the first stamp does not look like an edit.
- =org-canvas--rubric-push-update= takes the surplus assignment associations off before the PUT and puts them back after it — /all but one/, so the rubric never stands without any and Canvas's =update_rubric= callback cannot garbage-collect it, and one association is the state #123 proved updates in place. Each is deleted through =rubric_associations/ID= (the association's own id, which the include carries; an assignment's =rubric_settings.id= is the rubric's) and restored by =org-canvas--rubric-restore-association= with the flags it had (=use_for_grading=, =hide_score_total=, =hide_points=, =hide_outcome_results=, =purpose=) on the /original/ rubric id, inside an =unwind-protect=, so a failed PUT still leaves the assignments graded by the rubric they had. An association that could not be taken off is not put back; one that cannot be put back is an =[ERROR]= naming the assignment to push again. The PUT then lands on a rubric one assignment grades with, and Canvas updates in place.

Two hazards the live repair met are documented rather than coded around. A PUT carrying =rubric[title]= but no =rubric[criteria]= wipes the criteria (Canvas reads missing criteria as none; =points_possible= becomes 0) — org-canvas always sends them, but a repair script must too. And a =use_for_grading= association sets its assignment's =points_possible= to the rubric's total, so a rubric push can move column points without any POINTS edit: =org-canvas--rubric-warn-points-moved= compares the total before and after the PUT — no further request — and warns, naming the count of assignments grading with the rubric, when it changed. The #123 warning now says what actually happens when the id comes back different, in both cases it can: the twin the 404 recovery updated, or a copy Canvas made anyway — the previous rubric, where it still exists, keeps its associations and their assessments; rubrics.org names the new id; re-push the assignments to move them, or restore the id and delete the copy.

=org-canvas--rubric-dissociate-all=, which =org-canvas-delete-all-rubrics= runs first, still deletes through each assignment's =rubric_settings.id=, which the finding above says is the rubric id rather than the association's; it predates this and is left for its own issue. A dry run reads nothing and previews the PUT alone.

* Bulk Publish

=org-canvas-publish-module= / =-unpublish-module= set =PUBLISHED= on the module /and on the heading that owns each linked object/ — resolved by =org-canvas--module-item-target=, which returns =(FILE . POSITION)= rather than a Canvas id. Publish state belongs to the object (issue #47), so it is written where the object is declared, never inferred from a module item at push time; SubHeaders and external URLs have no object and are set in place. =PUBLISH_AT= on a module is org-canvas's own release schedule (never sent to Canvas): =org-canvas-apply-scheduled-releases= runs at the start of =org-canvas-sync=, before tier -1, so objects it publishes are pushed by the same run. A module /item/ may carry its own =PUBLISH_AT=, which outranks its module's: =org-canvas--module-item-held-p= holds such an item back from any publish — scheduled or by hand — until its date arrives, and =org-canvas--module-release-items= releases it then. Holding applies only to publishing; unpublishing a module takes scheduled items down with it. An item released inside an unpublished module is warned about, never fixed by publishing the module (issue #47 again). Mechanics live in modules.el, commands in org-canvas.el (they offer to sync, which modules.el must not require).

* A Page's PUBLISH_AT Is Canvas's, and Owns the Published State (issue #379)

Canvas publishes a page by itself at =wiki_page[publish_at]=, the one content type it schedules this way; a module's =PUBLISH_AT= is org-canvas's own, applied by a sync after the date (Bulk Publish, above), because Canvas has no such field for modules. A page heading's =PUBLISH_AT= is therefore a registry property with =:api-key "publish_at"=, pushed in the =wiki_page= wrapper and pulled back. Same name, different mechanism: the name says what the instructor wants, and each file's manual section says who acts on it.

What Canvas does with it was read from the canvas-lms source rather than probed, since a probe would have to publish and unpublish a page on a live course (=ScheduledPublication=, included by =WikiPage=; =WikiPagesApiController#get_update_params=). *A request that changes the published state clears =publish_at=.* The controller turns =published= into =workflow_state= before save, and the =before_save= hook, seeing =workflow_state= change, drops the schedule. Only a change counts, which is why the web UI's publish button cancels a schedule. *A new =publish_at= with the state untouched schedules.* A future time unpublishes the page and queues a job for that time; a past one publishes it now. *A nil =publish_at= unpublishes.* Clearing the field is not neutral. *The scheduled publish keeps =publish_at=*, marked implicit, so course copies can shift it. *All of it is behind the account's =scheduled_page_publication= flag*; with the flag off the column is stored and nothing else happens.

Four rules follow. *A heading with =PUBLISH_AT= never sends =published=* (=org-canvas--page-drop-published-when-scheduled=, the payload's =:post-build-fn=). =PUBLISHED= defaults to true, so a waiting page would otherwise be published by the first push and its schedule wiped by the second. *The payload never sends a null =publish_at=*: a heading without the property omits the key, as every registry property does, because a null would unpublish a page that is live. The cost is that Canvas keeps a schedule a push only stops mentioning; publishing (=PUBLISHED: true=, the default) cancels it, and keeping the page unpublished while cancelling it is done in the web UI. *=PUBLISHED= is not compared on a scheduled page* (its =:compare-p=, =org-canvas--page-published-comparable-p=): it reads false until the time and true after, and neither is the file's opinion. *A pull that finds =publish_at= deletes =PUBLISHED=* rather than write the false Canvas reports for a waiting page, which would read as an intent the push ignores. Validation warns, push-only, about =PUBLISHED: false= beside =PUBLISH_AT=, the state =org-canvas-unpublish-module= leaves on a linked page, and about =PUBLISH_AT= on the front page.

The publish is a save, so it moves the page's =updated_at= past =CANVAS_UPDATED_AT=: the next sync leaves the hash skip and asks, and the drift report lists a =CHANGED= row with nothing compared differing. That is the #257 case, and it is left to #257's verb (=org-canvas-diff-adopt-stamps=) rather than re-baselined automatically. A rule that recognized a release by the time alone would also hide an edit made in the web UI before the release.

=wiki_page[publish_at]= is newer than the OpenAPI fixture, so it is a justified exception in =org-canvas-contract--exceptions=.

* A New Module Header Is Published by a Second Request (issue #279)

A SubHeader or ExternalUrl item has no object behind it, so its heading's =PUBLISHED= goes into the item payload itself (=module_item[published]=, always for a self-owned type; see Bulk Publish above). Canvas honours that key on the update endpoint and ignores it on the create endpoint: a POST with =published: true= answered with the item and ="published": false=, the sync logged =POST successful=, stamped the id, and the header stayed invisible to students. On a live course that was 123 objectives headers across 16 modules, all created hidden in one run that reported nothing but success — the silent miss the bulk-publish work (#47) was meant to end, on exactly the batch where nobody clicks 123 publish icons.

=org-canvas--module-item-ensure-published= wraps the result of =org-canvas--module-item-push-to-api=: for a self-owned type whose reply carries a =published= other than the one the payload asked for, it PUTs that flag alone to the new id and returns the PUT's reply, so what is stamped and logged is the item as it is. It sits around the whole request, not the POST alone, because the item can also be created by the re-POST after a 404 or found by the search after a timeout, and Canvas ignored the flag on those creates too. One extra request per new header, none for an existing one (a PUT's reply agrees with its payload) and none for a foreign type, whose flag belongs to its object. It cannot loop: the PUT's reply is returned whatever it says. A failed PUT is one warning and the POST's reply, never a failure: the item exists and its id must be stamped, or the next sync creates a twin; with the id stamped, the next sync is a PUT, which carries the flag and lands. The alternative — doing it once in finalize for every self-owned item whose stamped reply says unpublished — would have put a Canvas write in the finalize stage, which stamps and does not write to Canvas.

* Module Items Reconcile Cross-Module Moves (issue #105)

Canvas has no cross-module move (the module id is in the item URL), so a block moved under another module heading in modules.org used to work only by accident: a PUT against the wrong module 404s and is retried as a POST, and the old copy stayed behind either way. =org-canvas--module-sync-items= now lists the module's items once (=org-canvas--module-remote-items=, which returns =unknown= on a failed request /or a malformed list/ — deleting on a misread would be the worst outcome, and generic test mocks return junk for every GET) and: =org-canvas--module-item-disown-foreign-id= clears the id of a heading the module does not hold so it is created here, remembering the old id in the run context's =:module-items-moved= (which dies with the run, issue #141); =org-canvas--module-reconcile-departed= deletes an unclaimed remote item only when it has demonstrably moved — another module's heading claims it (=org-canvas--module-item-claim-elsewhere=) or it is in the moved list — and warns about any other unlisted item rather than pruning it (children are never pruned unasked; quiz questions follow the same rule). Since #352 the delete-and-create is the fallback: a claimed item is first moved with GraphQL's =reorderModuleItems=, keeping its id ("A Module Item Moved Between Modules Keeps Its Id", below). Items get their own =org-canvas--module-item-finalize=: they used to go through the module finalize, whose post-fn re-ran the child sync with the /item's/ id as a module id — a no-op then, a 404 per item once the child sync fetches. =org-canvas--validate-module-item-ids= (the module-items =:file-fn=) warns when two item headings claim one id.

* Module Items Adopt a Twin Before Creating, and the Drift Report Sees Them (issues #177, #179)

The assignment level has asked, before any POST, whether Canvas already holds an item of that title since issue #85; the item level did not. =org-canvas--module-item-push-to-api= chose POST whenever the heading carried no =CANVAS_ID=, and an unstamped item heading is the likelier case — a git checkout that reverts a stamped modules.org (the #133 recovery), or a batch run that dies between the POST and the stamp. Clemson module 781703 ended up with two Assignment items for content 2563803, positions equal; students saw the assignment twice, and every later sync logged the #105 reconcile's "left in place" warning about a stray the sync itself had made. The fix fits inside the per-module reconcile, which already has the module's item list: after =org-canvas--module-item-disown-foreign-id=, =org-canvas--module-item-adopt-twin= looks in that list for an item of the heading's type and content — content id, or page url, or for a SubHeader, an ExternalUrl and anything else without content, the title (=org-canvas--module-item-same-content-p=) — that none of this module's headings claim, and puts its id on the heading, so the ordinary push is a PUT and the ordinary finalize writes the stamp. Nothing is fetched twice. The adopted id goes into the run context's =:module-items-adopted= (a key of =org-canvas--sync-ctx-keys=, so =plist-put= mutates in place), and the reconcile counts it as claimed: a dry run decides on the adoption and logs it, =org-canvas--module-item-push-to-api= answers with the dry-run sentinel, =org-canvas--module-item-finalize= stamps nothing, and the unstamped-but-adopted item is still not called unlisted. Two candidates — the already-duplicated case — adopt the first by position, then id (=org-canvas--module-item-twins=), and one warning names the rest; nothing is deleted (children are never pruned unasked). An id a sibling heading already carries is never adopted, so two headings with the same content take the two twins rather than fighting over one. The retry pass had no item list and did not adopt; it does now (#308, below).

The report side is the same blind spot from the other direction. =org-canvas--diff-feature= compared module ids only, so with 5864661 unclaimed and 5864670 stamped it called Modules clean and the divergence total counted nothing. Rather than teach the generic feature comparison about children, diff.el keeps a small table of child checks by feature name (=org-canvas--diff-children-fns=); =org-canvas--diff-feature= runs Modules' — =org-canvas--diff-module-items=, one item request per module the file claims, the same shape as the sync's reconcile — and hands its result back as =:children=, which =org-canvas-diff= reports right after the parent. The child result is a section of its own named "Module Items": an item id and a module id are different things, so an acknowledgment lives in =org-canvas-diff-known-extras= under ="module-items"= (with the usual STALE-ACK when the id is gone), the EXTRA row says which module the item sits in, and =k= on the row deletes through =modules/ID/items/ID= (=org-canvas--diff-delete-target=), not through a feature URL that would have been the module's. An item claimed by another module's heading is a pending move the next sync settles (#105), not an extra. The count feeds =org-canvas-diff-batch='s exit code as any other row does, and nothing is written. =org-canvas-prune-module-items= is the asked-for delete: it lists the items of every synced module, names the ones no level-2 heading claims, and asks once — =org-canvas-prune-modules= only ever looked at whole modules, and orphan cleanup walks the flat feature registry, where a nested endpoint does not fit.

* The Module Item Retry Pass Adopts a Twin Too (issue #308)

The end-of-run retry pass (=org-canvas--module-retry-pending-items=) was the one create path #179 left out. An unstamped item heading whose link target had no Canvas id is skipped by =org-canvas--module-sync-items= and remembered in =:module-items-pending=; when the target gains its id later in the run, =org-canvas--module-retry-single-pending= re-parses the heading and pushes it. With no =CANVAS_ID= that push was a POST, and nothing asked the module first, so a module that already held the item — a lost stamp, or a heading whose first pass had just adopted a same-titled twin in memory — got a second copy.

*The retry looks, as the module pass does.* =org-canvas--module-retry-adopt= runs before the push: a stamped heading needs nothing and is PUT as before; an unstamped one reads its module's item list through =org-canvas--module-retry-module-state=, a per-pass cache so each module is read once however many of its items were pending, and hands it to the same =org-canvas--module-item-adopt-twin= the module pass uses. The claimed ids are the module's heading stamps at retry time plus the ids adopted earlier in this pass (the cache keeps them, since a dry run stamps none), so two pending headings with one content take one twin between them, as siblings do in the module pass. A list that cannot be read is =unknown=, never empty (Hard Rule 16), and then the unstamped item is not POSTed at all: it stays pending with a warning naming the module. Updating by id is safe blind; creating is exactly what the lookup exists to prevent, and the next sync picks the item up.

*Why the first pass does not stamp what it adopted.* The issue offered two fixes: stamp the id adopted in the module pass before skipping, or adopt in the retry. Only the second closes the path. A heading can reach the retry with no in-memory adoption at all (the plain lost-stamp case, where the target gained its id this run), so the retry needs the lookup whatever the first pass does. And the first pass's adoption is the weaker one: with no content id, =org-canvas--module-item-same-content-p= falls back to the title, so an item of the same name linking other content would have been stamped for good. The retry decides with the content id in hand. The first pass keeps its in-memory adoption, which is what stops the reconcile calling the twin unlisted.

*Dry run.* The retry never wrote to Canvas under a dry run (=org-canvas--module-item-push-to-api= guards itself), but it refreshed the module's =PAYLOAD_HASH=, saved the file, and counted the item as a success. It now skips the refresh and the save when the push answered with the dry-run sentinel, and =org-canvas--sync-reclassify-skip-as-success= takes the counter to credit, =:dry-run= in a dry run (Hard Rule 15).

* Every Create Path Adopts a Twin Before It POSTs (issue #179, follow-up)

Module items were the first child level to adopt, not the only one that needed to.  Reading every create path on ef31226 found the same gap wherever a push does not go through =org-canvas--push-to-api=: classic quiz questions and question groups, New Quizzes and their items, outcomes and outcome groups; the generic 404-on-PUT recovery, which re-POSTed without looking; and four generic-path features (classic quizzes, discussions, announcements, assignment groups) that declared no =:find-fn=, so a push at point — outside a sync's snapshot — was never guarded.

The child levels share two helpers in core-sync: =org-canvas--child-twins= filters a parent's remote list (a list, a vector, or =unknown= when it could not be read) down to the items a predicate accepts and no sibling heading claims, ordered by position then id, and =org-canvas--adopt-child-twin= gives an unstamped entry the first one's id, names the rest, and deletes nothing.  Module items keep their own spelling in modules.el because theirs also feeds the run context.  The parent's list is fetched once per sync of that parent and only when a child lacks a stamp (=org-canvas--quiz-remote-questions=, =org-canvas--new-quiz-remote-items=); a list that cannot be read adopts nothing and says so.  A quiz question matches on =question_name=; a New Quiz item on the first paragraph of its body with tags stripped, which is what the push sends the heading as (=org-canvas--new-quiz-item-remote-title=).  Question groups are not adopted: Canvas has no endpoint that lists a quiz's groups.

New Quizzes are top-level, so they get the generic guard's semantics rather than a silent adoption: =org-canvas--new-quiz-guard-duplicate= lists the course's New Quizzes (one request, only for an unstamped quiz, never during a dry run) and hands the answer to =org-canvas--resolve-duplicate=, so the strategy, the batch fallback and a capital answer in the run context all apply; =skip= comes back as the symbol =duplicate=, which the pipeline counts as it does for any other feature and =org-canvas-sync-new-quiz-at-point= reports as a =user-error=.  Outcomes and outcome groups already had search-by-title functions, called only after a failed POST; =org-canvas--outcome-update-or-create= calls them before the POST, and on a 404 looks once more before creating.

The 404 recovery is the same decision from the other side: the stamped id is gone, and if the title lives on under another id — a course copy, or a create whose stamp was lost — that is the item to update.  =org-canvas--handle-404-retry= asks the module's =:find-fn= first (=org-canvas--recovery-find-twin=, which reads the id through =org-canvas--push-item-id= so pages adopt by url) and PUTs to the twin; only a miss re-POSTs.  A failed lookup is logged and falls through to the POST, as before.  =org-canvas-duplicate-title-strategy= set to =create= switches every one of these lookups off, as it does the generic guard's.

* The Drift Report Compares Bodies (issue #83)

The description is set directly on the payload, outside the property specs, so =org-canvas-diff= could not see it. Modules that push a body declare =:body-api-key= on =org-canvas-register-properties= (assignments/quizzes =description=, pages =body=, announcements/discussions =message=); pages add =:body-list-params '(("include[]" . "body"))= because the pages index omits bodies unless asked, and quizzes a =:body-fn= because their description is only the text before the first question. Local bodies come from =(org-canvas--export-subtree-body-to-html t)= — the OFFLINE flag skips link /and image/ resolution, and image resolution uploads; a report must never write. Both sides go through =org-canvas--diff-html-to-text= (tags dropped, entities decoded, whitespace collapsed) so markup-only differences stay invisible. Its whitespace class is explicit, not =[[:space:]]=: that class goes by the current buffer's syntax table, and in a Lisp buffer newline is comment-end, so the same string normalized differently depending on which buffer was current. A remote item lacking the field, or a failed export, means "not compared", never drift. A CHANGED row with no field differences now carries a line saying the change is in something uncompared.

* By-Design Extras (issue #98)

A synced course never read zero: Canvas scaffolding and deliberate web-UI objects sat as permanent EXTRA rows, so =org-canvas-diff-batch= could not do cron monitoring. Three valves, broad to narrow: structural =:skip-fn=s on the feature registry suppress scaffolding — the root outcome group (no =parent_outcome_group=), the stock "Assignments" group (skip-fns only ever hold back /unclaimed/ items, so a managed group of that name is still compared), and classic-quiz shadow assignments (=quiz_id= present) — counted in the footer the #81 way, and protecting the same objects from orphan cleanup; =org-canvas-diff-excluded-features= skips a feature wholesale with a visible "not checked" line; =org-canvas-diff-known-extras= (=(FEATURE ID &optional NOTE)=) acknowledges individual ids, counted once in the footer, with a =STALE-ACK= divergence — which counts, deliberately — when an acknowledged id stops existing so the list cannot rot. Both defcustoms affect the diff only; prune still lists acknowledged items. A fourth valve is automatic (issue #102): announcement and page attachments land in Uploaded Media as unclaimed files, and the known-extras list grew by hand forever. =org-canvas--diff-feature= records =:referenced-files= — the =/files/<id>= ids the body field of every item embeds — for each feature with a =:body-api-key= (the bodies are already fetched for the #83 comparison), =org-canvas--diff-syllabus-references= adds the syllabus (the one extra GET), and =org-canvas--diff-apply-references= moves matching Files extras into a =:referenced= count rendered as a "Referenced media" footer line. Runs after every feature is diffed, since registry order puts Files before the body features. =org-canvas-diff-scan-references= (default t) turns it off. *Excluding a feature does not exclude it from that scan* (issue #111): announcements are the body feature most often kept out of the report and the one whose attachments land in Uploaded Media, so =org-canvas--diff-excluded-result= still lists an excluded feature that has a =:body-api-key= — one read-only request, no rows, =:references-scanned= recorded so the "not checked" line says the bodies were read.

* The Drift Report Has Verbs (issue #103)

=org-canvas--diff-render= still returns a string, and batch output is unchanged, but each row is inserted by =org-canvas--diff-insert-row=, which stamps the text with an =org-canvas-diff-row= property =(:feature NAME :entry ENTRY)=; text properties survive =buffer-string= and =insert=, and =princ= drops them. The interactive buffer is in =org-canvas-diff-mode= (derived from =special-mode=): =RET= =org-canvas-diff-visit= (heading by id property for MISSING/CHANGED, by title for UNCLAIMED, =browse-url= of the =:html-url= that extras now carry), =a= =org-canvas-diff-acknowledge= (edits =org-canvas-diff-known-extras= in memory, then hands the /whole new list/ to =org-canvas-diff-acknowledge-function=, default =customize-save-variable=; on a STALE-ACK row it drops the entry), =k= =org-canvas-diff-delete= (confirms, then the feature's item URL and =:delete-data=, as orphan cleanup does), =p= =org-canvas-diff-pull= (runs =org-canvas-pull-at-point= in the heading's buffer), =g= re-runs, =TAB=/=S-TAB= walk rows by stepping over property runs (a CHANGED row spans its field lines). An action rewrites its row in place via =org-canvas--diff-rewrite-row=, keeping the property, rather than re-fetching everything. No magit-section dependency: the rows are plain text properties.

* A CHANGED Row With Nothing to Compare Adopts the Stamp (issue #257)

Some writes Canvas makes on its own bump =updated_at= on entries whose content did not move: a metadata-only touch of a file (the case #94 answered for files with =:modified-field=), the association bump a rubric leaves on its assignment (the case #124 restamps inside finalize, and #131 met by hand before that), and a course-wide one — setting =:POST_POLICY:= in settings.org runs =setCoursePostPolicy=, and Canvas rewrites the policy of every assignment in the course, so the next report listed all 77 as =CHANGED (no compared property differs; ...)=. The report was right each time: Canvas is newer than the baseline, nothing compared differs, and there is nothing in Org to change. A push would send the same content again (and walk into the conflict check), a pull would rewrite the same text. What the entry needs is a new baseline, and three times the fix was a one-off script over =org-map-entries=, one list GET and =org-canvas-org-set-property=, reinvented each time.

=org-canvas-diff-adopt-stamp= is that script as a row action, and =org-canvas-diff-adopt-stamps= as a batch command that runs the comparison itself (=org-canvas--diff-collect-results=, the read =org-canvas-diff= was already doing, now shared). Three rules. *Only a row with nothing to compare qualifies* (=org-canvas--diff-adoptable-p=: kind =modified=, =:remote-newer=, empty =:fields=, a string =:updated=); a row where a property differs is refused by the key and counted, not adopted, by the batch — adoption must never paper over real drift. *The hash stays.* =CANVAS_UPDATED_AT= takes the entry's =:updated= (already the feature's =:modified-field=, so files adopt =modified_at=); =PAYLOAD_HASH= is untouched, because the local side did not change and the next sync should still skip the entry — dropping the hash, as a pull does, would push every adopted entry once for nothing. *Nothing is sent*, and the report itself still writes nothing (#83): =a= reads context-sensitively — acknowledge on EXTRA/UNCLAIMED/STALE-ACK, adopt on CHANGED — so the one verb that means "accept what Canvas holds" stays on one key, but it is a verb, never a side effect of rendering. The settings push that causes the course-wide case logs a warning naming the batch command; settings is a feature module and cannot require diff.el, so it names the follow-up rather than running it.

* The Drift Report Deletes Rows in Batch, After Checks and a Snapshot (issue #345)

After a calendar reshuffle (course 297530, pinned to 750dc5e) the report listed nine EXTRA rows: six module items, one assignment and two rubrics left over from dropped sessions. The instructor approved deleting all nine, and =k= was the only way in, one =y-or-n-p= per row. So a script did it: it rebuilt =org-canvas--diff-delete-target='s choice between a module item's URL and the feature's item URL, read each object, checked that the assignment had no submissions or scores and that each rubric had no Assignment association, wrote the object's JSON to a file, and only then sent the DELETE. The report already knew every target; what the script added was the checks and the snapshot, and both belong to any delete, not to one caller.

=org-canvas-diff-delete-rows= takes selectors — =(:feature NAME :id ID)= or =(:feature NAME :all t)= — resolved against =org-canvas--diff-collect-results=, the comparison the report and =org-canvas-diff-adopt-stamps= already share (or a =:results= list a caller computed once), and never prompts. Four rules.

*Only EXTRA rows.* An UNCLAIMED or MOVED row has an unstamped heading the next sync pairs with it — it adopts the twin (#179) or, for a move, leaves the copy — so deleting it in batch would race a sync over an object Org means to keep; =k= still offers them, one at a time, with the row in front of the operator. A selector on any other row answers =not-extra=, one that names nothing =not-found=; neither sends a request.

*Read before delete, and refuse what takes work with it.* =org-canvas--diff-delete-inspect= reads the object at the URL the DELETE will go to (a rubric with =include[]=associations=, an assignment with its =:item-params=) and runs the feature's guard from =org-canvas--diff-delete-guards=. An assignment is held back when its submissions list shows one turned in or one scored or graded, or Canvas's =has_submitted_submissions= says so: deleting it deletes the gradebook column. A rubric is held back when an =Assignment= association names it: its assessments belong to the id (Hard Rule 7). The reason is named in the outcome, and =:force= overrides it. An empty reply is refused too, since there would be nothing to snapshot. =k= runs the same checks and puts the reason into its question — cheap, since the one read is the object the snapshot needs anyway — rather than refusing, because the operator is there to answer.

*An owned assignment is held back too (#366).* The submission check alone let through the assignment another object owns while nobody had submitted yet: a new graded discussion's, or a New Quiz's before it opens, which stays an Assignments EXTRA row whenever the New Quizzes section is excluded or unread (#313). Deleting it deletes or breaks the quiz or discussion. The Assignments guard, =org-canvas--diff-delete-assignments-guard=, now asks first the predicate prune and the orphan scan leave such an assignment by (#319): the assignments feature's =:delete-skip-fn=, reached through =org-canvas--feature-delete-skip=, never a copy of its logic. It reads the fields that predicate reads — =quiz_id=, =submission_types= (=online_quiz=, =discussion_topic=), =is_quiz_lti_assignment= and the external tool's launch URL — all on the assignment the inspect step already GETs at the delete URL with the feature's =:item-params=, so no request is added, and an owned assignment is refused without listing its submissions. The reason names the owner: "the assignment belongs to discussion 'X' (a graded discussion, in discussions.org)" from the embedded =discussion_topic=, "quiz N (a classic quiz, in quizzes.org)" from =quiz_id=, or "a New Quiz, in new-quizzes.org", the category from =org-canvas--assignment-owner=, which diff.el declares rather than requires, as it does the modules.el pairing functions (#299). As with the other checks, =:force= deletes it anyway and =k= names the owner in its question. A New Quizzes row keeps the submission check alone: its object is the quiz, read at the quiz service, and deleting it is deleting the owner, which is what the row asks for.

*Snapshot, then DELETE.* =org-canvas--diff-delete-execute= writes the object's JSON, pretty-printed, to =<time>-<feature>-<id>.json= under =org-canvas-diff-delete-snapshot-directory= (nil means =canvas-snapshots/= under the course directory, resolved when used, as the submissions directory is) and sends the DELETE only after the write succeeded. The core-sync "snapshot" is the in-memory remote list a sync reads for its conflict check; it holds list replies, not the single object a rebuild needs, and never touches disk, so it did not fit and the file writer is new. Both =k= and the batch write one.

*Dry run and read-only.* Under =org-canvas--dry-run= the objects are read and checked, and the outcome is =dry-run=: no snapshot, no DELETE (Hard Rule 1; the command takes selectors, so it is not in =org-canvas-dry-run--sync-commands=, which runs each entry with no arguments over the demo course — the diff specs cover it instead). A course marked =org-canvas-read-only= would refuse the DELETE at the transport anyway; =org-canvas--check-writable= runs before the snapshot too, so a refused delete leaves no file claiming it happened. Each row's failure is caught and recorded as =failed=, and the next row goes on.

The report itself is untouched: rendering still writes nothing (Hard Rule 19), and deleting is a verb the operator names.

* The Drift Report Lists Pending Creates and Pairs Moved Items (issue #294)

The report answered only half of "what would a sync do": what Canvas has that Org lacks (EXTRA) and what both hold differently (CHANGED). A heading with no Canvas id — which the next sync POSTs — got no row. After a week-long slide of a course calendar in Org (course 297530, 2026-09-22) the report showed 56 EXTRA module items and nothing of the 57 rebuilt item headings, three assignments, two rubrics and one assignment group the next sync would create, and finding those took a hand script over the Org files.

*A PENDING row per unstamped heading, counted apart.* =org-canvas--diff-feature= returns =:pending=, one =pending= entry per local entry without its id property (an empty value is no id, as =org-canvas--sync-collect-entries= reads it), naming the property the sync would stamp. The Module Items pass does the same for level-2 headings, with the module each sits under. =org-canvas--diff-pending-p-fns= narrows a feature whose file holds headings the sync never creates: a files.org folder heading carries no id and is not uploaded (=org-canvas--diff-file-heading-p=). A heading an UNCLAIMED or MOVED row already names is left out, so one change is one row. *Pending creates are not drift*: they stay out of =org-canvas--diff-count=, so =org-canvas-diff= returns and =org-canvas-diff-batch= exits on divergences alone, the section header reads "N divergence(s), M pending create(s)", and a footer line counts them. The report exists to say whether Canvas has drifted from what Org says; an unpushed heading is Org ahead of Canvas, which is what a sync is for, and a cron job that went red whenever an instructor drafted next week would be switched off. The one pending create that /is/ drift in disguise — a create whose stamp was lost — is already an UNCLAIMED row, and that one counts.

*Why the moved items never paired: two causes.* The Module Items pass (#177) built its extras and returned them; it never called =org-canvas--diff-pair-unclaimed= at all. And had it, the pairing compared the heading text from =org-get-heading= — which, with the flags diff passes, keeps link markup on every Org version in use (checked on Org 9.8: =[[file:assignments.org::*Closer][Closer]]= comes back whole) — against Canvas's plain title. A module item heading is always a link, so no item could pair; a files.org heading is too. The fix is at the local entry: =org-canvas--diff-local-entry= records =:match-title=, the title as a reader sees it (=org-canvas--diff-display-title=: a link's description, a bare heading link's target heading, a bare file link's file name, statistics cookies dropped — the name the sync gives Canvas), and all pairing compares that. =:title= stays the =org-get-heading= text, which is what the existing row lookups search for.

*Pairing module items is one to one, and knows the module.* =org-canvas--diff-module-item-pair= gives each extra at most one unstamped partner, preferring a heading in the item's own module: that pair is UNCLAIMED, worded for items, since the sync adopts a same-content twin itself (#179) and =org-canvas-adopt-at-point= does not reach level 2. A partner under another module makes the pair MOVED, with the old module (=:where=, =:module-id=, so =k= deletes the stale copy) and the new (=:to=). The row says what the sync would do — create it in the new module and leave this copy — and how to make it a move instead: stamp the named id on the heading, and the #105 reconcile creates it in the new module and deletes the old copy (since #352 the sync moves it instead, keeping its id; see below). A SubHeader pairs only within its module, since its title is all it has and "Readings" recurs every week by design. MOVED rows count as divergences, as UNCLAIMED rows do: Canvas holds an item where Org does not put it.

*Still read-only.* Every addition is a read of the Org files the report already opened; nothing is written (Hard Rule 19). A PENDING row carries its file and line, and =RET= goes there, checking the heading still is the one named and otherwise finding it by title; =a= and =k= refuse it, since there is no remote object. Left for later from the issue, and done in #296: the identifying fields on EXTRA assignments and groups (points, due, group, =needs_grading_count=) and an assignment-group weight total line.

* Extra Assignments and Groups Say What They Are (issue #296)

An EXTRA row named a title and an id, and knowing what an instructor had made in the web UI — a 20-point assignment in a new 10% group, due tonight, 89 submissions waiting — took a hand =GET= per row.  And a Canvas-only group hid a weight problem no row stated: Org's groups sum to 100 without it, Canvas's to 110, and nothing in the report added them up.  Split from #294, whose entry above left both undone.

*No request is added.*  Every field is in the list replies the report already holds.  =org-canvas--diff-feature= keeps its reply on the result as =:remote-items=, and =org-canvas--diff-apply-extra-details= runs after every feature is diffed, as the referenced-media pass (#102) does, because each feature needs the other's list: an assignment names its group by =assignment_group_id=, which only the groups reply turns into a name, and a group's assignment count is a tally over the assignments reply.  When the other list was not read (excluded, or its request failed) the detail degrades rather than fetches: the group is named by id, the count left out.  An assignment prints its group, points, due date (in the course zone, as an Org timestamp), publish state and =needs_grading_count= — the last from the index, which returns it to a teacher by default; a group prints its weight and count.  The line goes under the EXTRA row, inside the row's text property, as a CHANGED row's field lines do.  Only EXTRA rows get it: an UNCLAIMED or MOVED row already names the heading that is the item.

*The weight totals line is not drift.*  =org-canvas--diff-weight-totals= sums the =WEIGHT= of every group heading (the registry's =:query=, pending ones included — they are what Org says the course will be) against the =group_weight= of every group Canvas holds, the stock "Assignments" group the =:skip-fn= hides included, since its weight counts toward the grade all the same.  A difference is a =WEIGHTS= line under the section, rendered even when the section has no rows.  It stays out of =org-canvas--diff-count=, so =org-canvas-diff-batch= exits as before: each cause of the difference is already a row — an EXTRA group or a CHANGED weight, both counted — or a pending create, which #294 decided is not drift; counting the line too would count one change twice.  The one cause with no counted row is a weighted stock group, which the footer's "Not checked" line names.  The line cannot say whether the course weights by group at all (=apply_assignment_group_weights= is a course setting, another request), so it says it matters only when it does.  Read-only throughout (Hard Rule 19).

* The Drift Report Pairs Module Items by Content, as the Sync Adopts (issue #299)

#294 paired an EXTRA module item with an unstamped item heading by title; the sync adopts a twin by content (#179: =org-canvas--module-item-same-content-p=, the same type and content id or page url). The two disagreed on exactly the case the report exists for: a same-titled item that links different content read as UNCLAIMED, "the next sync adopts it", while the sync created a new item beside it — and the row hedged ("if the unstamped heading links the same content") because the report could not tell. Now the report asks the sync. =org-canvas--diff-module-item-content= runs the sync's own item parser, =org-canvas--module-item-parse-entry=, on each level-2 heading, and =org-canvas--diff-module-item-match= hands its result and the remote item to the sync's own predicate. A pair by content id or page url, or a SubHeader or external URL (whose title is its content), is =content=; an item whose link target has no Canvas id yet still pairs by title — the sync's predicate does the same — but the row carries =:by-title= and says "paired by title only", since which content the target gets is not known until it is synced. A side effect worth having: an item Canvas has since renamed still pairs when it links the heading's content.

*Why declare, not move and not copy.* Diff is a command file and must not require a feature module it does not drive. Three ways to reach the resolver: copy it into diff.el, move it to core, or =declare-function= the two modules.el functions. A copy is how the report and the sync came to disagree in the first place, and would drift again. Moving it means taking some fifteen functions — the link resolver, the heading search, the files.org path lookup, the file-to-type table, the parse and transform stages, the predicate — out of the module whose pipeline they are, for one caller. Declaring calls the code the sync runs, so the two agree by construction; the cost is a runtime dependence on modules.el being loaded, which =org-canvas= guarantees (it requires every module), and diff.el already declares functions from =org-canvas.el= the same way. If the parser is absent or signals, the heading's =:content= is nil and it pairs by title as before, marked by-title.

*Still read-only (Hard Rule 19).* The parser reads the linked Org file through =org-canvas--find-file-noselect=, which the report already uses for every course file; it sends no request and stamps nothing. It does log, as a sync stage would ("[Stage 1: Parse] Processing Item", "Unresolved link"), which in a report would read as a sync having run, so =org-canvas--logger= is bound to nil around it.

* A MOVED Row Stamps Its Paired Heading, and a Stamped Move Is a RELOCATE Row (issues #342, #343)

A MOVED row (#294) named the item id to stamp and said which module the heading sat in, but nothing stamped it. After a course moved every item from Week 06 on one week later, the report printed 48 MOVED rows, and the stamping was a script that parsed the row text and searched each destination module for a heading of the item's title. Seven of the 48 could not be found that way: the columns had been renumbered ("R6: Arguing Both Sides" on Canvas, "R7: Arguing Both Sides" in Org), and the report had paired those by content (#299) without saying which heading it paired. Once stamped, the 48 then disappeared from the report, which came up with six unrelated EXTRA rows. The next sync, though, would find each id missing from its heading's module (=org-canvas--module-item-disown-foreign-id=), create the item there with a new id and delete the old copy. That is 48 POSTs and 48 DELETEs, and 48 ids changing under anything that stores them.

*The row carries its partner.* =org-canvas--diff-module-item-paired= puts the partner heading on the MOVED entry: =:file=, =:line=, =:partner-heading= (the raw heading text, link markup and all) and =:partner-title= (what it shows). The row prints the shown title and line, so a renumbered pair can be read, and =s= (=org-canvas-diff-stamp-move=) finds the heading again. It tries the recorded line first, accepting it only when the heading there has the same raw text and still has no =CANVAS_ID=. If that fails, it looks for an unstamped level-2 heading with that text under the module the row names (=:to=). It never searches by the item's title, because the title is the thing a renumbering changes and "Readings" occurs in every week. It refuses when any heading in the file already carries the id, since two headings claiming one item is worse than none. A row paired by title only asks first, because nothing proves that pair. =S= and =org-canvas-diff-stamp-moves= stamp every MOVED row paired by content. They run the comparison themselves, as =org-canvas-diff-adopt-stamps= does, confirm unless in batch, list the by-title rows as HELD rather than stamping them, and report STAMPED, CLAIMED and NOT FOUND rows in a buffer of their own. The transient's =J= runs the bulk form.

*Stamping writes =CANVAS_ID= and nothing else, and sends nothing.* It is the second local write in diff.el, alongside stamp adoption (#257), and follows the same rule: a separate key and command, never something rendering does (Hard Rule 19). =PAYLOAD_HASH= is not touched. The module's hash covers its items' properties but deliberately leaves out their ids (=org-canvas--module-items-digest=), and moving the heading had already changed that hash.

*A stamped move is a RELOCATE row, counted apart.* =org-canvas--diff-module-item-relocations= indexes every listed item by the module that holds it. A stamped level-2 heading whose id sits in a module other than its own becomes a =relocate= entry, including a heading under a module not yet on Canvas, whose items the sync will disown the same way. The row says the sync recreates the item in the heading's module with a new id and deletes this copy. The rows sit under =:relocate=, are counted in the section header and a footer line, and stay out of =org-canvas--diff-count=, as PENDING rows do. They are Org's pending work, not Canvas drifting from Org, and a course mid-reshuffle should not turn =org-canvas-diff-batch= red. The row is there because the report is the only warning that the ids will change. =RET= visits the stamped heading and =b= opens the old copy. =a=, =k= and =s= refuse the row: the heading claims the item, and deleting the old copy by hand would leave the sync's own delete nothing to find.

*The MOVED row now describes the recreate.* It used to say "stamp CANVAS_ID … to move it instead", which reads as a move that keeps the id. Canvas cannot move an item between modules (the id's URL names the module, #105), so the row now says that with the stamp, the next sync recreates the item there with a new id and deletes this copy. (Superseded by #352, below: the sync now moves the item and keeps its id.)

* A Module Item Moved Between Modules Keeps Its Id (issue #352)

The REST API cannot move a module item: the module id is in the item's URL, so #105 settled on delete-and-create, and #343 made the report warn that every stamped move changes an id. Canvas's GraphQL has a move. =reorderModuleItems(input: {courseId, moduleId, itemIds, oldModuleId, targetPosition})= sets the items' module in one call, and the item keeps its id, which is what a student's progress through the module and any link to the item hang on.

*What the mutation does, from the source, not a live run.* Read in =app/graphql/mutations/reorder_module_items.rb= at canvas-lms =1c9f0bb8= (the schema says only the argument types). =itemIds= lists the items to move, not the target module's whole order: every one must exist in the course and sit in the source module, which is =oldModuleId= when given and the target module otherwise, or the mutation refuses with "Items do not belong to source module" before writing anything. The writes run in one transaction, so all the items move or none does. =targetPosition= is 1-based: the first item lands there and the rest follow it, the items already at or after it shift down, and both modules are renumbered 1..n afterwards. Without =targetPosition= the items land at the top. A refusal comes back in the payload's =errors=, not as a top-level GraphQL error.

*Scope: the move, not in-module order.* The issue offered the mutation for in-module ordering too, in place of the per-item position PUTs. It is not used there. Each item is PUT anyway, for its title, indent, requirement and publish flag, and that PUT carries its position, so ordering costs no request today; a reorder call would add one per module and save none.

*Both sync orders.* Which module holds an item is known from one side only, so there are two entry points, and the rest of #105 stays as the fallback.

- The module the item left syncs first. Its reconcile finds the item unclaimed here and claimed by another module's heading (=org-canvas--module-item-claim-elsewhere=, which now also returns that module's =CANVAS_ID= and the heading's position). =org-canvas--module-item-move-departed= moves it there, at the heading's position, where it used to delete it. If that module has no Canvas id yet (it is new, created later in the run), nothing is sent and the item stays where it is; the next case moves it once the module exists.
- The module the item arrived in syncs first. Its heading carries an id the module's list lacks. =org-canvas--module-item-settle-foreign-id= asks =moduleItem(id)= for the item's module (=org-canvas--module-item-home=, a read through =org-canvas--graphql-query=), confirms with a REST read of =modules/HOME/items/ID= that the item is live and in this course (a deleted item may still resolve over GraphQL, and moving it would be a write for nothing), and moves it in at the position the sync is about to PUT it at. The heading keeps its id, and the ordinary PUT then updates the item in its new module.

The moves made this run go into the run context's =:module-items-relocated= as =(ITEM . MODULE)= pairs, so the other side does not try again: in a real run the second module's list already reflects the move, but in a dry run nothing moved, and without the pairs each move would be previewed twice.

*Every failure falls back to #105, and says so.* No Canvas id on the target, an unreadable home, a home equal to this module, a failed REST read, a refused mutation or one that errors: each leaves the old behaviour in place, create here and delete there (=org-canvas--module-item-disown-foreign-id=, =org-canvas--module-delete-departed-item=), with a warning naming the reason. One item per mutation keeps a failure to one item. A mutation that failed in transit may have landed, so before falling back =org-canvas--module-item-move= reads the item's module again; if it is the target, the move stands and nothing is created. Otherwise a duplicate could appear beside the moved item.

*The guards.* Nothing happens while the module's list is =unknown= (Hard Rule 16): the move is a write on the strength of that list, like the delete it replaces, and an item is moved only when a heading claims it. The mutation goes through =org-canvas--graphql-mutate=, so a dry run logs "Would move item …" and sends nothing, and a read-only course refuses it at the transport (Hard Rule 1). The reads go through =org-canvas--graphql-query= and a GET. A move is a write made from the module finalize's post-fn, so it calls =org-canvas--finalize-note-remote-write= (#124); the module finalize names no endpoint, so this costs no request, and Canvas's module object has no =updated_at= to restamp. No counter was added: the item's own PUT is its success, as before, and the delete a move replaces was never counted either (Hard Rule 15 is about counters a run populates).

*The report says what the sync now does.* The RELOCATE row, its footer, the MOVED row's advice and the stamp commands' lines said the sync recreates the item with a new id. They now say it moves the item there, keeping its id, and the RELOCATE and MOVED rows add that a refused move still recreates it (=org-canvas--diff-move-outcome=). RELOCATE rows stay uncounted: they are Org's pending work either way.

*Contract.* Both documents are in the GraphQL contract test, and =Module=, =ModuleItem=, =ReorderModuleItemsInput= and =ReorderModuleItemsPayload= were supplemented into the fixture from the canvas-lms SDL at =1c9f0bb8=; the next introspection should replace them. The test also runs =org-canvas--module-item-move-send= and =org-canvas--module-item-home= with the senders mocked and checks their variables: =itemIds= a vector, the position always an =Int=.

*Verified live on 2026-09-27* (course 297530, the mutation sent by hand from a teacher token, the module sync itself not run): =reorderModuleItems= was accepted, the item kept its id, landed at =targetPosition= and left the source module, and =moduleItem(id:)= resolved it. The completion requirement was dropped by Canvas: a =must_view= item arrived in its new module with none. Canvas keeps requirements on the module, keyed by item id (=ContextModule#completion_requirements=), and the mutation neither carries the old module's entry across nor adds one to the new module.

*So a move is followed at once by the requirement, restored by the sync's PUT.* =org-canvas--module-item-restore-requirement= PUTs =module_item[completion_requirement]= (type, and =min_score= when the heading has one; built by =org-canvas--module-item-requirement=, which the item payload uses too) to the item in its new module, right after a move that went out, in both orders. It is not left to the new module's own item PUT, because that PUT does not always follow. When the old module moves the item, the new module may never reach its item loop this run: the runner skips a module whose =PAYLOAD_HASH= matches, and a hash can match after a move (stamping a MOVED row writes only =CANVAS_ID=, which the items digest leaves out), or the sync may have been of the old module alone. When the new module moves the item in, its own PUT follows unless the heading is still pending its link, and then nothing would set the requirement until the retry pass or the next sync. The requirement is read from the heading (=org-canvas--module-item-requirement-props=: =COMPLETION_REQUIREMENT= and a positive =MIN_SCORE=, never for a SubHeader), so a pending heading gets it too. A heading with no requirement sends nothing more. In the order where the new module moves the item in, the requirement goes out twice (once after the move, once with the item's PUT). That costs one request per move, and moves are rare. A dry run names the requirement it would set; a failed PUT is a warning, and the move stands.

*Still not verified live* (coverage.org, "Watch on First Live Use"): the sync's own run of a move, that the restoring PUT brings the requirement back in the browser, and that a student's progress on the item survives the move.

* Assignment Reads Ask for the Assignment's Own Dates (issue #273)

Canvas applies an assignment's overrides to the =due_at=, =lock_at= and =unlock_at= it returns from the index and the show, and for a teacher, who can see every override, it applies the most lenient one. The first extension written from a heading's overrides table (#224 worked as designed) therefore turned the assignment's own dates into the one student's on every read the package made: =org-canvas-diff= called =R4: Agency= CHANGED with =DUE_AT= four days later than the file, =org-canvas-pull-at-point= or the conflict prompt's pull would have written the extension into the heading as the base due date, and the next push would have sent it to everyone. The full pull was worse still: =org-canvas--override-emit-table= drops a row whose dates match the parent's, so with the substituted dates the extension row read as redundant and was dropped, and the next =org-canvas-sync-overrides= would have deleted the override for not being in the table. Probed 2026-09-14 on course 297530: =GET assignments/2563804= answered =due 2026-09-19T03:59:00Z=, with =override_assignment_dates=false= =2026-09-15T03:59:00Z=, the date in the file.

Every read of an assignment now carries =override_assignment_dates=false=, spelled once as =org-canvas--assignment-read-params= and declared three times: =:list-params= on the feature registration (the drift report, the sync's remote snapshot, adopt and the orphan scan list through =org-canvas--feature-list-params=), =:item-params=, a new registry key resolved by =org-canvas--feature-item-params= that =org-canvas-pull-at-point= and the conflict check read one item with (the check's response is what the pull option writes), and =:params= on =org-canvas-define-pull=. The overrides table was never affected: it reads =assignments/:id/overrides=, which returns the overrides themselves. =all_dates= is not asked for, since Org holds the base dates and the table the overrides. Classic quizzes are deliberately left alone: their serializer substitutes override dates only for a reader who has been a student in the course, and neither quiz operation documents a parameter to turn it off — the read-parameter contract test says so, and would flag the parameter as undocumented if it were added there. That test (=org-canvas-contract-test.el=, "Canvas read-parameter contract") checks every registered feature's =:list-params=, =:item-params= and =:body-list-params= against the query parameters the OpenAPI spec documents on its list and show operations, since a misspelled or unsupported query parameter is silently ignored by Canvas and nothing else in the code path would notice.

* Timestamps Compare at Minute Precision (issue #176)

An Org timestamp has no seconds field. A deadline set in the Canvas web UI does: the end-of-day picker stores =2026-09-10T03:59:59Z=, which pull writes as =<2026-09-09 Wed 23:59>= because that is all the file can say. =org-canvas--diff-values-equal-p= compared the two as exact instants, so the row was a permanent =DUE_AT= divergence with no =(Canvas updated ...)= suffix — pull rewrote the same minute, and the only thing that cleared it was a push, which sends =:00= seconds and moves a live deadline by 59 seconds. The =timestamp= branch now truncates both sides to whole minutes since the epoch (=org-canvas--diff-time-minute=) before comparing. It is a truncation, not a tolerance: =xx:59= and =xx+1:00= render as different minutes in the file and stay drift. Every registered =:type timestamp= property (assignment and calendar dates) goes through this one function, so the rule covers them all. The conflict check and the payload-hash skip are untouched — they compare =CANVAS_UPDATED_AT= against Canvas's own =updated_at= (seconds on both sides), and the hash is of the local payload alone; the one Org-minute baseline, the =#+LAST_SYNCED= header, already rounds up to the next minute for the same reason.

* Cross-Course Links Are the Validator's Business (issue #172)

A course copied forward carries links to the shell it came from; they resolve for the instructor, who is enrolled in both, and 404 for every student. org-canvas noticed exactly one narrow case: =org-canvas--rewrite-canvas-file-urls= matches =org-canvas--canvas-file-url-re=, which requires =/files/<digits>=, so a hotlinked *file* got a pull-summary entry and a link to another shell's *page* passed in silence. On CPSC 3720 F26 that was two links seen and one missed — and the missed one was the deciding difference between the two =Sprint 1= twins #164 reports, invisible without grepping for it by hand.

*A validate check, not a pull-time fetch.* =org-canvas--validate-cross-course-links= is pure string work over the Org files: no request, so it runs on a read-only course (#168) and in =org-canvas-validate-batch= (#169) like everything else in validate. It anchors on =org-canvas--validate-canvas-host= — the host of the configured instance — so a link to some other site is nobody's business here, and compares the course id in the path with =org-canvas-course-id=. Top-level =/users/= and =/accounts/= routes are reported too; a course-scoped =/courses/ID/users/...= is the course check's business, which is why the alternation anchors both directly after the host.

*Warnings, never errors, and never suppressed.* A link to a shared department page or a prerequisite course is occasionally meant, so it is a warning. But it is not marked =org-canvas--validate-push-only=: a dead link is the course's state, true whether or not you ever push, which is exactly the adoption signal #168 set out to keep.

*Scanned once per file, not once per spec.* Two features can register the same file — modules and module items both name modules.org, as do quizzes, outcomes and new quizzes with theirs — so the scan lives in =org-canvas--validate-run-all-specs= behind a seen-file list rather than in =org-canvas--validate-spec=. Per spec, every foreign link in those four files would be reported twice.

The report lists each link and then groups them by target (=org-canvas--validate-cross-course-summary=), because the useful question about course-copy residue is which shell it came from, not which link came first. Complements #164: that finds duplicated items, this finds items pointing at the wrong course.

*The pull does not fetch them (issue #390).* The one pull-time case above kept costing: the body rewriter GETs =/api/v1/files/ID= for a file id not in files.org, and for a link into another shell that GET can only 403. Pulling pages on course 295790 reported the same file of course 208463 once per page linking it, as a non-fatal error attributed to files.org, and with #155's wording — your role or your token scopes — that sent the reader to check permissions for what validate already calls a link into another course. =org-canvas--rewrite-resolve-file-id= now compares the URL's =/courses/N/= with =org-canvas-course-id= (=org-canvas--rewrite-foreign-course=) before any request: a foreign link is left exactly as it is, logged as one warning per file id naming the course, and never reaches the pull summary, since the validator's warning is the user's signal. A URL naming no course, or a course matching the configured one, is fetched as before. A same-course fetch that fails is remembered too: =org-canvas--rewrite-unresolved-ids= holds each id given up on (=failed= or =foreign=), the negative half of the successes the caller's cache keeps, so a broken link repeated across bodies costs one request and one summary record. It is forgotten on =org-canvas--operation-start-hook= unless =org-canvas--inhibit-log-clear= is bound, so a standalone pull starts afresh while the sub-pulls of =org-canvas-pull-all= or the master sync share one set; nothing it holds outlives the command that learned it. What a failed fetch records is decided by =org-canvas--rewrite-record-failure=: a role refusal (=org-canvas-permission-error=) is a =skip=, as =org-canvas--safe-pull= counts a whole type since #155, and anything else an =error=; either names the file whose body held the link (=org-canvas--rewrite-body-file=, the buffer the pull is converting in, such as pages.org), not files.org, which the link never came from.

* Validation Is Read-Only Aware (issue #168)

Run over a pulled mirror of Clemson CPSC 3720 F26 with =org-canvas-read-only= set, validate produced 102 findings of which 52 protected a push the course had declared it will never make: 32 "timestamp is in the past" warnings (on a Fall section pulled in September, every historical date is /supposed/ to be in the past — it is a faithful record, not a mistake) and, once #167 removed the 20 false =online_quiz= errors, the pre-first-sync link warnings. Adopting an inherited course is the workflow where validate has the most to say and where its signal-to-noise is worst.

=org-canvas--validate-push-only= marks a finding as push-protecting; =org-canvas-validate= drops the marked ones when =org-canvas-read-only= is set, counts what it dropped, and says so in a line of its own — suppression is visible, never silent. =org-canvas-validate-all= (transient =V=) keeps them, for the moment you are about to clear the flag and adopt the course for real. On a writable course the two commands are identical.

*What is marked, and what is not.* Marked: the past-timestamp warning, and the =:pending-sync= link warning ("link target has no CANVAS_ID (sync target first)"), whose whole subject is a sync that will not happen. Not marked, and this is the line: anything true of the course whatever you intend to do next — title collisions and superseded twins (#164), date /ordering/ (a due date before its unlock date is wrong on any course), an =external_tool= naming no tool, drop rules, weight sums, quiz point totals, malformed property syntax. The test to apply to a new check is not "is this a warning" but "would a reader of a course they will never write to want to know".

* Rubric Assessments Come From the Grading File's Table (issue #250)

The grading file showed a rubric's criteria at the top and, per student, a read-only table of whatever assessment Canvas held, and could produce none: with every human-graded column in a course carrying a rubric under =use_for_grading=, grading from Org gave a bare total and empty rubric cells, so rubric grading stayed SpeedGrader-only. The submission update endpoint takes =rubric_assessment[<criterion_id>][points|comments]= beside or instead of =posted_grade=, and the bulk endpoint takes the same object per student under =grade_data=, so the one-PUT / bulk split of =org-canvas--submissions-send-grades= carries the assessment as one more field of each student's entry (=org-canvas--submissions-grade-fields=).

- Each student gets a =** Rubric= table: =| Id | Criterion | Max | Score |=, one row per criterion in the rubric's order, pre-filled from =rubric_assessment=, and under it one =- <id> :: comment= item per criterion (the comment was a fifth column until #263, below). The id column is the key: a row is matched to its criterion by id, never by position or description, so a deleted or reordered row cannot score the wrong criterion, and a rating is never typed — Canvas picks it from the points. Rows and items are always rendered on a rubric assignment, empty or not, so the grader has cells to fill.
- The baseline is =:CANVAS_RUBRIC:=, a twelve-character digest of the assessment as pulled or pushed (=org-canvas--submissions-rubric-digest=): every scored or commented criterion as =id=points|comment=, sorted by id, so the digest of the table as typed and of the assessment as Canvas returns it agree whenever their content does. A digest rather than the values because a comment can hold anything a property value cannot, and because the table itself shows the values; the property only has to answer "did this change?" and, in the conflict check, "did Canvas move?". A student with no assessment has no property and an empty table digests to nil, so an emptied table is not a change: clearing an assessment is SpeedGrader's, since a partial =rubric_assessment= would silently drop the unmentioned criteria and org-canvas never sends one it did not read.
- When the rubric is used for grading (=CANVAS_RUBRIC_USE_FOR_GRADING=, written at pull time from the Assignment object's top-level =use_rubric_for_grading= — the field the drift report compares; =rubric_settings= holds only the rubric's id, title, points and display flags, and reading the flag there wrote =false= for every assignment, issue #253), Canvas derives the grade from the assessment, so the rows' total becomes =SCORE= at push (=:score-derived=) unless the grader edited =SCORE= to the same total; an edited =SCORE= that disagrees with the total is a =user-error= before anything is sent, since both cannot be right. Without =use_for_grading= the score and the assessment are independent fields of one request.
- Validation is in the collector, not the sender: a Score cell that is not a number or exceeds the row's Max stops =S= for everyone before the first request. A re-pull carries such a cell over as typed (below), so it is still there, and still stops the push with its name, when the grader comes back to it. A partly filled table is allowed — Canvas accepts a partial assessment — and the confirmation says how many are partly scored.
- Rubric rows carry over a re-pull the way notes and drafts do (=org-canvas--submissions-rubric-carryover=), and so does a typed =SCORE= (issue #281, below). When the re-pulled =CANVAS_RUBRIC= is not the baseline the rows were typed against, the heading is marked =CONFLICT=, because the rows shown are the grader's and not what Canvas holds.
- The conflict check compares the live digest only for a change that sends rows: a score-only push is not held against a rubric that moved, and a file pulled before the table existed, with no =CANVAS_RUBRIC= at all, still pushes scores.
- The completion rule fills every row at its Max for full credit, so completion columns keep their rubric cells populated, and leaves the rows empty for a 0.

* Rubric Comments Are Items Under the Table (issue #263)

Under the feedback rules a course graded by, a rubric comment is two or three sentences plus a "Where to look" pointer: 300 to 700 characters, the widest cell 711. #250 put it in the table's fifth column, and a table cannot show that: with =truncate-lines= the Comment column sat past the right edge of a 188-column window, with =visual-line-mode= every row wrapped four times and the Score column stopped being scannable. The instructor's first question was "where are the comments" — they were there, off the right edge. Org's two escapes are both wrong here: =org-table-wrap-region= splits the cell across id-less rows, which the reader drops, so a push would send the first line and silently discard the rest; a width cookie folds the column on display, but every pull re-renders the table and throws the cookie row away. There was also a data limit: =org-canvas--submissions-table-cell= flattened every newline in a comment pulled from Canvas, and a typed cell could hold none, so a two-paragraph comment was impossible in either direction.

* A Comment Is Paragraphs, in Both Directions (issue #264)

A submission comment is prose and the grading file held it in a one-line slot both ways. =** Comments= rendered every comment through =org-canvas--html-to-org-inline=, which collapses newlines to spaces, so a two-paragraph comment came back as one line; =** Comment to post= was read by =org-canvas--submissions-section-text=, which dropped blank lines along with the template's =#= lines, so a two-paragraph draft reached Canvas as one paragraph with a line break in it. Same family as #263: the container was a line where the content is paragraphs.

- A pulled comment is a description item whose text is the full conversion (=org-canvas--submissions-body-text=, so #266's hard-break rule applies, with the heading block markers dropped as the inline path drops them). A one-line comment stays on the item's line after the author and date; one with more lines starts under it, indented two spaces, a blank line between paragraphs kept — the label is long, and a paragraph that starts under it reads as a paragraph. =org-canvas--submissions-item= is the one formatter, shared with #263's rubric items.

A property is a slot for a value; the way out (pull again, or set =CANVAS_SCORE= to Canvas's value) is in the manual and in the push's closing message, which names how many were marked.

* A Grading File Body Wants the Break, Not the Markup (issue #266)

Canvas's editor writes =<br>= whenever a student presses Shift-Enter, and some browsers on Enter; pandoc's Org writer renders each as a line ending in =\\=. In the text-entry closers of one course that was 39 lines of 3399 in one file, in two shapes: a sentence with the marker hanging off its end, and a line holding nothing but =\\= where two breaks met. * The Grading Queue Counts Rows, Never Columns (issue #283)

The weekly question, "which columns need pulling, grading or posting?", was answered by a hand script reading every column's submissions, because nothing in the package holds all three states at once: Canvas has the submissions, the grading file has when it was last pulled, and the instructor has the rest. =org-canvas-submissions-status= is that script as a command, one read-only Org table through =org-canvas--report-display=, so a batch Emacs prints it the way the script did.

- The counts come from =assignments/:id/submissions=, one row per student, not from the assignment's =needs_grading_count=: that field says nothing about posting, and nothing about what arrived after the grading file was pulled, which is the column the instructor was missing. One paged read per column is the price, and the report says so.
- Next is derived from per-row predicates, never from column differences. "Submitted minus graded" is wrong the moment a missing row carries a typed zero (graded, not submitted) or an excused row carries no submission: 90 submitted and 95 graded can still hide ten ungraded uploads. So =:ungraded= counts rows submitted and unscored and =:unposted= rows scored and unposted, and the verb is the first that applies of pull (submitted rows, no grading file), refresh (submitted after =PULLED_AT=), grade, post. A scored row is one with a numeric =score= or =excused=, the same reading the grading file gives.
- =PULLED_AT= is read from the grading file on disk, never through a visited buffer: the pull writes and saves it in the same breath, so the disk is right, and a report over seventy columns should neither visit seventy files nor touch one the grader has open. The comparison is at the minute the file records, so a submission in the pull's own minute may count as new once; a refresh clears it, and missing a late upload would cost more.
- An unreadable column (a 403 on one endpoint, issue #171's shape) is one warning and a row of =?=, and the rest of the report goes on. Unpublished and =not_graded= assignments stay out: nothing can be submitted to the one or graded on the other.
- Nothing is written, not even a file under the submissions directory, and no name, score or user id reaches the report: it is counts, so it is safe to leave on screen.

** A Mean and a Median Beside the Counts (issue #352)

Each column also shows Canvas's mean and median score, read from GraphQL's =Assignment.scoreStatistic=. The statistic is a column fact placed beside the row counts, never one of them: nothing in Next, the summary line or the sort reads it.

The query sends =filter: {gradingPeriodId: null}= as a variable; without the explicit null, Canvas answers only the current grading period's assignments, and a course with grading periods would lose most of its columns.
- *Null means none graded.* A live check on 2026-09-25 found the statistic filled on every column with a graded submission, posted or hidden, and null on exactly the columns with =gradedSubmissionsExist: false=. So a null is a dash, never an error, and so is a column the read did not name.

* A Re-Pull Keeps Typed Scores (issue #281)

A refresh of a grading file carried notes, drafted comments and unpushed Rubric rows over the re-render and dropped typed =SCORE= values, behind a =y-or-n-p= — "N unpushed score change(s) will be lost; Re-pull anyway?" — that a batch Emacs cannot answer and an interactive grader has to answer yes to in order to see the late rows. The one kind of unpushed grading the refresh did not keep was the one the guard existed to protect; on one column that was fifteen zeros typed on missing rows, re-applied from a backup.

The typed score now carries over like the rows (=org-canvas--submissions-score-carryover=): a =SCORE= whose parsed value differs from its =CANVAS_SCORE= — a 0 typed on a missing row that never had a =CANVAS_SCORE= included — is written back after the render, with the =CANVAS_SCORE= it was typed against as its baseline. When the freshly pulled =CANVAS_SCORE= is that baseline, nothing moved and the score simply comes back. When Canvas now holds the typed score, the same grade was pushed meanwhile and nothing is written. When Canvas holds something else, someone graded in SpeedGrader since, and the heading is marked =CONFLICT= with the push's own wording (=score: Canvas has 93=, or =no grade=), because the =SCORE= shown is the grader's and the way out is the push's: pull again, or set =CANVAS_SCORE= to Canvas's value. (That advice did not survive: the refresh had already re-baselined =CANVAS_SCORE=, so the next push sent the stale score. #440, below, holds a marked heading back from every push until =t= or =k= resolves it.) The score is restored after the rubric rows, so a heading where both moved is marked for the score, the order the push's check uses.

With nothing left to lose, the guard is gone from the grading file's re-pull and refresh. It stays on the summary table, whose typed cells a re-render does erase, and there it never calls =y-or-n-p= under =noninteractive=: the edits are named in a message and the refresh goes ahead, since a prompt a batch Emacs cannot answer is a hang, not a safeguard (the same rule as the conflict prompt's =skip= fallback, issue #72).

* Submission Commands Take Their Target as an Argument (issue #280)

Every submissions entry point was interactive only: the pull and open commands chose their target with =completing-read=, and refresh and download-all acted on the current buffer, which only those two knew how to set up. A batch caller that knew the assignment id — six columns in one sitting, an MCP server reading grading files, an agenda generator — chained three double-dash internals and a hand-rolled buffer setup, one refactor away from breaking.

The rule now: a command takes its target as an optional argument and prompts only when it is nil. =org-canvas-pull-submissions= takes an id (an integer or a string of digits, one request through =org-canvas--submissions-fetch-assignment=) or an exact name (found in the course's list, the same list the prompt offers), and a DOWNLOAD flag that makes the grading file the view and downloads every attachment; =org-canvas-open-submissions= takes a path or a name under the submissions directory, the file's or the assignment's; =org-canvas-submissions-refresh-file= visits, refreshes and returns the buffer, sharing its body with the interactive refresh. Each returns the buffer, so a script goes on in it with =with-current-buffer=. A target that matches nothing is a =user-error= that names it, never a silent fallback to the prompt, since a batch caller cannot answer one.

The prompts live in the resolvers (=org-canvas--submissions-resolve-assignment=, =org-canvas--submissions-grading-file-path=), not in a sexp =interactive= spec: a sexp spec blanks undercover's line counts for the whole body (the bisection is in the memory notes and on =org-canvas-submissions-apply-completion-rule=). The DOWNLOAD flag has no prefix-argument binding for the same reason; interactively it is =D= in the file. Push still confirmed before it sent, and a script that meant it bound =y-or-n-p=; #381 (below) gave the push an entry point of its own.

* A Script Pushes Grades by Name, and Posts Only When It Says So (issue #381)

#280 left the push interactive. Three attendance pushes from =emacs --batch= on 2026-09-28 each rebuilt its state by hand: turned =org-canvas-submissions-mode= on, set the private =org-canvas-submissions--current-view= to =detail= (a file visited without it went down the summary branch and found no changes), and stubbed =y-or-n-p= globally. That stub answered both questions the push asks, "Push?" and then "post them now?", so a script could not push without posting. Posting is the one step students see.

*The entry point.* =org-canvas-push-submission-grades= takes ASSIGNMENT and an optional POST, the #280 shape: an id (an integer or a string of digits) or a path or name as =org-canvas-open-submissions= takes it, and a prompt for the file only when ASSIGNMENT is nil. An id is found in the =CANVAS_ASSIGNMENT_ID= header of each file under the submissions directory (=org-canvas--submissions-grading-file-for-id=), so no request is spent resolving a name, unlike the pull's resolver; an integer no file names is a =user-error=, and a string of digits that matches no header falls through to the file-name lookup, which refuses it by name. The file is visited through =org-canvas--submissions-visit-grading-file= (mode on, context recovered), its view set to =detail=, pushed without a question, saved, and a plist returned: =:pushed= (grades Canvas stored), =:state= and =:message= from #382's outcome, =:late=, =:comments=, =:conflicts=, =:posted=. The issue suggested =&key post=; an optional positional argument keeps the signature the same kind as =org-canvas-pull-submissions='s DOWNLOAD.

*Posting is its own argument.* The push itself no longer posts or offers to: =org-canvas--submissions-push-all= returns its plist and leaves posting to the caller. The script posts only with POST non-nil, and then only when the grade send is =completed=, or sent no grade at all (a column pushed earlier and posted now). A failed, unconfirmed or dry-run send never posts, the #382 rule. =org-canvas--submissions-post-assignment= is the posting shared with =P=, and answers nil under a dry run, when =org-canvas--graphql-mutate= sends nothing.

*The two questions go different ways.* The push question now goes through =org-canvas--confirm=, the batch convention since #287 and #346: =org-canvas-assume-yes= or a batch Emacs answers it yes, which only confirms what the caller asked for. The post offer after =S= does not. It is asked only interactively; in batch the push says the grades are held and how to post them, and =org-canvas-assume-yes= does not answer it, since that option covers prompts that "merely confirm the operation the user already asked for", and a push is not a request to post. The interactive command and the script share =org-canvas--submissions-push-current=, which confirms or not by its argument.

*The view comes from the file.* =org-canvas--submissions-ensure-context= reads a buffer that visits a file with a =CANVAS_ASSIGNMENT_ID= header as the detail view even before it holds a student. The summary table is never saved, so no summary buffer has both.

* A Push Takes Some Rows of a Grading File (issue #441)

The push was all or nothing. On 2026-10-01 two grading files held about a hundred scored, unpushed rows each under a standing instruction that no grades go up yet, and the instructor released four rows by hand. A script did it with six internals (the change at point, a re-read of the student, the single-grade PUT, the baseline record, the comment post, the draft reset) and its own copy of the conflict check.

*One plan, restricted.* =org-canvas--submissions-push-plan= is what =S= sends, collected once: the grade changes and drafts after the #440 hold, the push's own conflict check, the sent-comment edits, the Comment Bank, and with ONLY, a list of user ids, every one of those restricted to the students named (=org-canvas--submissions-only-rows=). =org-canvas--submissions-push-current= and =org-canvas--submissions-push-all= take the plan, so the at-point push, the restricted script push and the full push are one path: the same check, the same confirmation, the same baselines, the same save. Nothing about a row is sent outside it.

*What a row is.* Its score, Rubric rows, late status, drafted comment and sent-comment edits — everything kept under the student's heading. The Comment Bank belongs to no row and is left out of a restricted push; a grader who wants it sends =S= or =B=.

*No posting with a restriction.* Posting releases every grade the column holds, so =org-canvas-push-submission-grades= refuses POST beside ONLY, and =s= never offers to post. Partial release is the point of the restriction; a post would undo it.

*Nothing is ignored silently.* An id in ONLY with no heading in the file is returned under =:missing=, one whose heading has nothing to send (no change, no draft, no comment edit, not held) under =:unchanged=, and both are named in the closing message. The shell's =push-grades= exits 1 for either, as it does for a grade that did not land, a held conflict or an unsent comment change.

*The signature.* The issue suggested =:only= as a keyword; =org-canvas-push-submission-grades= takes positional optional arguments (#381 chose POST that way, after #280's DOWNLOAD), so ONLY is the third: =(org-canvas-push-submission-grades ASSIGNMENT nil '(5001 5002))=. Ids may be integers or strings of digits; anything else is a =user-error= before the file is read. =s= is =org-canvas-submissions-push-at-point=, a bare =(interactive)= for undercover's sake, finding the student from anywhere in the subtree (=org-canvas--submissions-student-at-point=, shared with #440's =t= and =k=).

*The dry run says what each row would send.* Under =org-canvas--dry-run= the push logs, and returns as =:would-send=, one line per student: the grade fields as JSON exactly as =org-canvas--submissions-grade-fields= builds them for =update_grades= or the PUT, the late status, and the comment. =push-grades --dry-run= prints those lines on standard output. Nothing else changes about the dry run (#442).

* A Dry Run of the Grade Push Changes Nothing (issue #442)

A dry run over twelve grading files on 2026-10-01 left ten of them changed on disk: every draft under =** Comment to post= had moved under =** Comments= as =- *You* <time> :: ...=, with no =[id]=, and the files were saved, so the real push that followed found no draft to send. Reading the code showed worse than the report: the draft step called =org-canvas--submissions-post-comment=, a plain =org-canvas-api-request= PUT that no dry-run guard sits in front of, so the dry run sent the comments as well (a spec pinned the two PUTs before the fix). * A Bulk Grade Push Waits for Canvas's Job (issue #382)

=update_grades= does not store grades; it queues a job and answers with a Progress object. The push used to ignore that answer: it recorded every =CANVAS_SCORE= baseline, said "Pushed 102 grade(s)" and offered to post while the job was still running. On Attendance 01 (2026-09-28) a read-back at once found 2 of 102 scores; 36, then 50, a few seconds later; all of them after about a minute. Had the job failed, the file would have claimed every score as Canvas's, and the next push would have seen nothing to send.

*The push waits for the job.* =org-canvas--submissions-send-grades= now returns an outcome. A single PUT that returned is =completed=, since that endpoint stores the grade before it answers. The bulk endpoint's Progress is followed by =org-canvas--submissions-await-progress=, which reads =GET /api/v1/progress/:id= every =org-canvas-submissions-progress-interval= seconds (2) until the job is =completed= or =failed=, or =org-canvas-submissions-progress-timeout= seconds (180) have been waited. Each read goes through =org-canvas-api-request=, so it is paced and retried like any other request, and each pause goes through =org-canvas--wait=, which is also what the specs stub, so no test sleeps. The address is built on =org-canvas-base-url=, never taken from the reply's =url=, so the token only goes to the configured instance.

*Only a completed job records anything.* A failed job (with Canvas's =message=), a wait that ran out, a progress read that failed, or a reply that is no Progress object at all (no =id= and =workflow_state=) leaves every score and rubric baseline as it was, offers no posting, and opens the closing message with what happened: "Canvas did not apply 2 grade(s) (…); nothing recorded", or "2 grade(s) sent but not confirmed (still running after 180s); nothing recorded, pull to check". The late statuses, the drafted comments and the Comment Bank travel in requests of their own and are recorded as before (=org-canvas--submissions-record-late-only= for the statuses of rows whose grades did not land). A job that finishes after the timeout is not an error the file hides: the grades stay changes, and a re-pull confirms each typed score Canvas has come to hold, the #281 rule.

*Timeout, not an unbounded wait.* 102 grades took about a minute. Three minutes covers that with room to spare, and a grader who knows the instance is slower raises the defcustom. Waiting forever was rejected: a stuck job would hang a batch Emacs, and the outcome of a job that never ends is the same "not confirmed" either way.

*The dry run says the push would be asynchronous.* Under =org-canvas--dry-run= no grade request is sent (Hard Rule 1); the log names the count and, for a bulk push, that it would be a background job the push waits for, and nothing is recorded.

*Contract.* The generated fixture now carries the =Progress= schema under a =response_only= entry (=RESPONSE_ONLY_SCHEMAS= in the extractor, with =query_progress= as its operation), and the contract test checks that the three fields the push reads (=id=, =workflow_state=, =message=) are documented, and that the full documented object is recognised as a Progress.

* A Grade Is Cleared Only by a Typed none (issue #417)

A grading file could not take a grade away. On 2026-09-30 ten Journal 04 submissions were ruled not graded, five of them already scored (unposted) in SpeedGrader; deleting their =SCORE= left the grades on Canvas. An absent, empty or unreadable =SCORE= parsed to nil, and the push sent a nil score as =posted_grade: null= (not the empty string Canvas documents as the clear, and never probed), then deleted =CANVAS_SCORE= as though the grade were gone, so file and Canvas agreed only by accident until the next refresh wrote the grade back. Nothing in the file could ask for the clear on purpose.

*One word clears, silence never does.* =org-canvas--submissions-typed-score= reads a typed =SCORE= against its baseline: absent or blank is the baseline itself, so no change; =none= or =-= (=org-canvas--submissions-clear-words=, any case) is nil, no grade; anything =org-canvas--submissions-parse-score= reads is that value; anything else is a =user-error= naming the student and the value, before anything is sent, the rule the Rubric cells already followed. Deleting a property is too easy to do by accident, and a hand grade entered in SpeedGrader by someone else is exactly what an accidental clear would destroy, so the clear has to be typed. =-= is accepted beside =none= because it is what a grader types in a table cell; =none= is the documented spelling, the word =LATE_STATUS= already uses for "no status". The summary table reads its Score cells the same way, so a blank cell there is no longer a clear either.

*The change is marked, the request is Canvas's own clear.* A change that clears carries =:clear t= (=org-canvas--submissions-clear-change=), and only where there was a grade: a =none= on a heading with no =CANVAS_SCORE= (or snapshot score) is no change. =org-canvas--submissions-grade-fields= sends a clear as =posted_grade ""=, which Canvas reads as no grade, on the single PUT and in the bulk =update_grades= entry alike, so #382's wait for the job, the dry run and the conflict check apply unchanged. The confirmation lists the row as =92 → clear= and counts the clears (=(1 clearing a grade)=), so a clear is never read as a score of nil.

*A landed clear looks like a pulled ungraded row.* Once the grades are recorded, a clear deletes both =CANVAS_SCORE= and =SCORE= (=org-canvas--submissions-record-pushed-at-point=): what a pull renders for a submission without a grade. A re-pull before the clear lands keeps it the way it keeps a typed score (#281, =org-canvas--submissions-score-carryover=), marked =CONFLICT= when Canvas's grade moved under it, and drops it once Canvas holds no grade; a blank =SCORE= is no longer carried at all, since it asks for nothing.

*The rubric assessment is not cleared.* The issue suggested a =rubric_assessment= with empty points beside the grade. #250 decided that clearing an assessment is SpeedGrader's, since a =rubric_assessment= that leaves criteria out drops them and the empty-points form was never probed; nothing here changes that, and an unchanged or emptied table beside =none= sends the grade alone. On a rubric used for grading, =none= beside Rubric rows that did change is a =user-error= (=org-canvas--submissions-rubric-derived-score=): Canvas would derive a grade from the rows the same request asks it to take away.

* A Column Is Scored by Section Window (issue #383)

On 2026-09-28 two attendance columns were graded that way by a Python pass over three files: people.org for each student's sections, the grading file for =SUBMITTED_AT=, and meeting windows typed by hand into the script, though the column's overrides table already held them. A strict window would have zeroed seventeen students plainly in the room (a section opened four minutes early, uploads landing five minutes after the end), so the script ran again with a fifteen-minute grace. The scores went into the file by a regex over =:SCORE:= lines, and nothing in the file said why a student had a 0.

=org-canvas-submissions-score-by-window= is that pass as a command on a grading file, in a command file of its own (=org-canvas-submissions-window.el=) that requires submissions and declares, never requires, the sections.el readers.

*Where a window comes from.* First the assignment's own =#+NAME: overrides= table in assignments.org, Unlock At to Lock At, or to Due At when the row has no lock: a section-timed column already encodes its meeting there, so the window is typed once. The row's first cell is matched to the student by the section's sections.org heading, the key a link names after its =::*= (=org-canvas--section-keys=), which is also how people.org's =SECTIONS= links; a plain name matches a plain name. A group's or students' row gives no section window. For a column without overrides, a section's =MEETS= property in sections.org (=MWF 10:10-11:00=, =Tue 09:05-09:55; Thu 10:10-11:00=) gives the window on the day the work was submitted. =MEETS= is registered on the sections feature with no =:pull-only= and no API key: typed by hand, never pulled or pushed; the sections pull writes only its own properties and so keeps it, and validation warns on one that does not parse, since the scorer ignores it (with a log warning) rather than guess. A table row outranks =MEETS= for the same section, since it is the column's own word.

*Several sections.* A student in a lecture and a recitation has both; the submission is inside when it falls in any of their windows. A section with a rule that does not meet that day (=MEETS= on another weekday) makes the verdict /outside/, not /no window/: the student had a rule and missed it.

*Time.* =SUBMITTED_AT= and the table's cells are Org timestamps the pull wrote in one zone (=org-canvas--time-zone=), and =MEETS= is a wall clock in the course's zone. All three are read as wall-clock minutes (=org-canvas--submissions-window-minutes=, encoding the decoded fields as if in UTC), which keeps their order and differences and makes the result independent of the zone Emacs runs in; converting to absolute time would have needed the zone of each and bought nothing. The specs run the conversion under three zones.

*What is written.* Inside earns the file's =POINTS_POSSIBLE= (or POINTS from the caller); outside and unsubmitted earn 0; a student with no window at all (no section in people.org, or none with a window) is left unscored and listed, since a 0 there would be the package's guess. A =SCORE= already there — typed, or pulled with a grade — is kept unless OVERWRITE, an =EX= row always, and a student who left (=STATUS: left=) is not part of the plan. Full credit also fills the Rubric rows at their Max, as the completion rule does. Each score written gets one =- Window rule:= line under the student's =Notes= (the heading added when the entry has none), naming the time, the sections, the window, the grace and the verdict; a later run replaces its own line, and a re-pull carries it over with the rest of the notes (#281).

*Report first.* The outside, windowless and unsubmitted students are rendered with their times through =org-canvas--report-display= before anything is written, and interactively the write is confirmed; under =noninteractive= the report is printed and the write goes ahead, #281's rule. Nothing is read from Canvas and nothing is sent: the scores go out with the grade push, which still checks for conflicts.

*Arguments.* FILE, GRACE, OVERWRITE and POINTS, following #280: FILE nil means the grading buffer at hand or one chosen in the minibuffer; GRACE nil is asked for interactively (default =org-canvas-submissions-window-grace=) and is the defcustom in batch; a file without =POINTS_POSSIBLE= asks for the points, or is a =user-error= in batch. The spec is a bare =(interactive)=, for undercover's sake.

*Passed over.* Matching a student's answer to their own room's question (the second column's extra check) stays a human's job; the report is where to start it. An "All Sections" row is not a fallback window: a column meant to have one window for everyone is not section-timed.

* A Refresh Says What Changed (issue #282)

A refresh re-rendered the file and said "Refreshing submissions for X..." and nothing more. What had changed since the last pull, the reason anyone refreshes, had to be found by diffing the new file against a copy of the old one: 105 rows that had gained =POSTED_AT=, a graded row that now carried a late second attempt with nothing marking it, a student who had left the course and vanished from the file with no message, a column where nothing had changed at all. The cautious grader kept a backup and diffed, which is the package's job.

The comparison is against the file, not a second fetch: before the re-render each student heading's recorded state is read (=org-canvas--submissions-state-at-point=: attempt, submitted-at, =CANVAS_SCORE=, =POSTED_AT=, status), after it the fetched submissions are classified one kind per student, the kind the grader acts on first (=org-canvas--submissions-classify-change=): a new attempt on a row that carried a grade is /resubmitted/, and its heading gets =CONFLICT= in the push's short style (=attempt: 2 submitted after grading=), since the score no longer describes the file and the push's own attempt check would otherwise only fire at push time; work where there was none is /new/ (a first submission, a later attempt on an ungraded row, a student the file did not have); a =CANVAS_SCORE= that moved is /regraded/; a =POSTED_AT= that appeared is /posted/. The counts go to the echo area on one line, the students to the log one line each, and a refresh that found nothing says so with the previous =PULLED_AT=, since "no change" is also an answer. A first pull, with no heading to compare against, reports nothing.

A student no longer in the pull is reported leaving, and their heading is kept only when the carry-over holds work under it — notes, a draft, Rubric rows, a typed score — since dropping the heading would drop that too, while a heading with nothing local has nothing to lose beyond the line in the summary. The kept heading is rendered from a stand-in submission (=org-canvas--submissions-departed-entries=) carrying the student's id, name and old =CANVAS_SCORE=, so the ordinary render and carry-over produce it — in alphabetical place, with a Rubric table for the rows to land in, the typed score against its own baseline — and =STATUS: left= marks it. The grade collector, the draft collector and the completion rule skip a =left= heading, so nothing is ever pushed for a student Canvas has no submission for; a later refresh keeps the heading without reporting the student leaving again, and the grader deletes it when done. "Always keep" was considered and passed over: a departed student with nothing local would then sit in the file forever, and the summary line already makes them visible.

* A Heading Marked CONFLICT Is Not Pushed Until It Is Resolved (issue #440)

#281 made a refresh carry a typed =SCORE= over and mark the heading =CONFLICT= when Canvas's grade had moved under it, and said the way out was the push's: pull again, or set =CANVAS_SCORE= to Canvas's value. Nothing read the mark. The refresh had already re-baselined =CANVAS_SCORE= to Canvas's grade, so the push's own check (live Canvas against =CANVAS_SCORE=) agreed and the stale typed score went up over the newer one. On 2026-10-01 that would have replaced an instructor's SpeedGrader zero on an authorship question with a grader's 10; on a manual-post column nobody would have seen it until posting. "Pull again" was the override, and a refresh is also the routine way to pick up late uploads, so every conflicted row in a file was overridden by the next routine refresh and push.

*The mark holds the heading.* =org-canvas--submissions-hold-conflicted= runs before the push's own check: a student heading carrying =CONFLICT= sends nothing — not its score, its =Rubric= rows, its late status or its drafted comment — whatever the value says. The values are the #264 ones and come from four writers: the push's check (=score:=, =attempt: Canvas has N=, =rubric: assessed on Canvas since the pull=, =late status:=), the refresh's carry-over restore (=score:=, =rubric: … since these rows were typed=, =late status:=), and the refresh's resubmission mark (=attempt: N submitted after grading=). Every one of them says the typed values were written against a Canvas that has since moved, so every one holds the same things; a per-value rule (a late-status conflict holding only the status, say) was considered and passed over, since the push's own check already skips a student's whole change for any of its reasons and the two should not disagree. The draft is held with the grade because a drafted comment is usually about that grade ("late, minus two") and would contradict a grade Canvas now holds. Sent-comment edits (#419) and the Comment Bank are not held: they are not grade state, and each has its own check against Canvas's text.

*One meaning for =:conflicts=.* The returned plist's =:conflicts= counts the headings held back from this push, whether marked before it or by its own check, and the new =:conflict-names= lists their students; the closing message names them too (=2 conflict(s) not sent (Adams, Alice; Beta, Bob): resolve each with t (take Canvas's) or k (keep mine)=). A marked heading with nothing to send (a resubmission nobody has typed against) is not counted: it holds nothing back. The push still marks what its own check finds, and a dry run marks nothing (#442).

*Two ways out, both on the heading.* =t= (=org-canvas-submissions-take-canvas=) and =k= (=org-canvas-submissions-keep-mine=) each read the student's submission (=assignments/:id/submissions/:user_id= with =rubric_assessment=), so they work whether the mark came from a refresh, whose baselines are current, or from a push, whose baselines are stale. Take Canvas's writes Canvas's score, late status and assessment into =SCORE=, =LATE_STATUS= and the =Rubric= rows (a row Canvas has no entry for is emptied) and their baselines, and keeps what was typed as one line under =Notes= (=- Typed before taking Canvas's grade <time>: SCORE 10; Rubric _7104 6, …=), the issue's "typed rows move to Notes" without a table nobody reads; the draft stays drafted, for the grader to send or clear. Keep mine writes only the baselines (=CANVAS_SCORE=, =CANVAS_RUBRIC=, =CANVAS_LATE_STATUS=, =ATTEMPT=), so the push's own check passes and the next push sends the typed values on purpose: it is "set =CANVAS_SCORE= to Canvas's value" done for every baseline the check compares. Both clear =CONFLICT= and save through =org-canvas--save-buffer=. Neither sends anything.

*The refresh names them.* Its closing line ends with =; CONFLICT on N: NAME (REASON); …=, read from the headings after the carry-over and the resubmission marks, so a late-status conflict, which no change kind counts, is named too.

*Not done.* The issue's optional =SCORE_OVERRIDE= (a ruled score standing beside rubric rows that total otherwise, on a rubric used for grading) did not fall out of this: Canvas derives the grade from the assessment on such a rubric, so it needs its own probe of what Canvas does with a =posted_grade= beside a =rubric_assessment=. Take Canvas's covers the case in the report, a SpeedGrader zero with the rows kept under Notes.

* Similarity Reports Are Read Per Column From GraphQL, and Counted Per Row (issue #351)

A pulled grading file had no Turnitin results: a grader opened SpeedGrader for each student to see the Similarity and AI Writing scores, and a report that had /failed/ — 7 of 43 on R6 of course 297530 (2026-09-25), for a Google-Doc-PDF workflow usually an image-only PDF — stayed invisible until that student's turn. With a document processor attached (#184, #350), the reports are an LTI Asset Processor's, and REST does not carry them; GraphQL does, as =Submission.ltiAssetReportsConnection=.

*The traps.* Two fields look like the answer and are not. =Assignment.hasPlagiarismTool= is =false= on that same assignment, because it describes the legacy plagiarism framework, not asset processors; gating the read on it would never read a report. =Submission.turnitinData= is the legacy plugin's, which is off on the instance (#184). Only =ltiAssetReportsConnection= holds the LTI 1.3 results, so the read asks for nothing else and is not gated on any assignment flag: a column without a processor answers empty report lists, and that is the "no processor" signal.

*One query per column, keyed on the user.* =org-canvas--submissions-reports-query= reads =assignment(id) { submissionsConnection { nodes { userId ltiAssetReportsConnection { nodes { reportType processingProgress result } } } } }=, a hundred submissions a page, following =endCursor= (=org-canvas--submissions-fetch-reports=). =userId= keys a node to its row, since =USER_ID= is what every grading-file path keys on already; the REST submissions and the GraphQL nodes are joined in =org-canvas--submissions-with-reports=, which the pull and the refresh both call (=org-canvas--submissions-fetch-with-reports=). A column where nothing was handed in is not asked. A GraphQL query is a read, so it runs on a course marked read-only (#202).

*The row's properties.* The known report types name their properties, =originality= → =SIMILARITY= and =turnitin_aiwriting= → =AI_WRITING= (=org-canvas--submissions-report-properties=); any other type is written to =REPORT_= and its name upcased, so a second processor lands somewhere a grader sees rather than being dropped. The value is the result for =Processed= (=33%=, or =processed= when the tool gives none), =failed= for =Failed=, =not processed= for =NotProcessed=, and =pending= for the LTI spec's in-flight states and for any progress value not yet known — the report exists and has nothing final to say. Two reports of one type (a report per uploaded file) are joined with a comma, keeping both — on the current attempt only since #436, which also adds the error code to =failed= and writes =none= for a missing report. The properties are Canvas's and are rewritten by every render; they are not part of the carry-over, so a refresh moves =pending= to =33%= and drops a report Canvas no longer holds, while typed scores, Rubric rows, notes and drafts come back as before (#281).

*Counted per row, never per report.* The =Reports:= line (=Reports: 36 processed, 7 failed, 0 pending=) counts students, as the grading queue does (#283): a row is failed when any of its reports failed or was not processed, else pending when any is pending, else processed. Counting reports would have read 72 processed on the issue's column, a number nobody grades by. The line sits under the =Assignment:= line of the grading file and under the statistics of the summary table; the summary of a saved file adds it up from the headings' properties, so it needs no request. =org-canvas-submissions-status= asks the same query for each column someone submitted to and adds a =Reports:= line summed over them that names the columns where a report failed (=failed in R6 (7)=), one query per such column, which is the price of seeing a failure before the grading starts.

*Nothing when there is nothing.* A column with no report writes no property and no line, in the file, the summary and the queue. A failed read — a GraphQL error or a transport error — is one warning in the log and the pull goes on without the reports, the same as a column with no processor (the #171 rule, and the checkpoints read's shape in discussions.el). The contract fixture had no =Submission= or report types (=Assignment= came with #350), and the instance's introspection needs a token, so =Submission=, =SubmissionConnection=, =LtiAssetReport=, =LtiAssetReportConnection= and =TotalCountPageInfo= were added from the canvas-lms SDL with #350's =extract-canvas-graphql-contract.py --supplement=, which leaves every type already there as the instance described it and records the added ones, with their ref, under =provenance.supplements=; the next semester's regeneration from the instance replaces them.

* Reports Are the Current Attempt's, a Failure Names Its Code, and a Missing Report Reads none (issue #436)

#351 read every report on the submission. On course 297530 (2026-10-01, 358 submissions on four columns) that mixed attempts: eight submissions had four reports, two on the files the submission carries now and two on a file a resubmission replaced, and the grading file showed them as =31%, 12%= — which #351's docstring had called "a report per uploaded file". All 79 =Failed= reports carried =errorCode: EULA_NOT_ACCEPTED= (the student had not accepted Turnitin's agreement, not an image-only PDF as #351 guessed), and the pull dropped the code. 53 AI Writing reports answered =--%= and 7 =*%=, both =Processed=, so both counted as processed. And 14 handed-in files had no report at all, indistinguishable from a column without a processor.

*The current attempt, by canvas-lms's own rule, applied here.* Two ways were open. =ltiAssetReportsConnection(latest: true)= filters on the server; the reporter read its description, and canvas-lms's loader (=Loaders::SubmissionLtiAssetReportsLoader=, ref =318f2ad0=) shows what it does: keep a discussion entry's report (the loader keeps only each entry's latest version in either mode), and a file's report when its =attachmentId= is among the submission's =attachment_ids= /or/ its asset's =submissionAttempt= equals the submission's =attempt=. The other way is to read =asset { attachmentId submissionAttempt discussionEntryVersion { _id } }= with the submission's =attempt= and =attachments { _id }= and apply that rule here (=org-canvas--submissions-report-current-p=); the reporter verified the attachment match on the live data, where =submissionAttempt= was null on every report. The client-side rule was chosen, for three reasons: it is the one checked against a live course; it keeps the replaced reports in hand, so #437's report can count them; and one rule differs on purpose — an asset with neither a file nor a discussion entry and no attempt (a text entry whose asset did not record one) is kept, where =latest: true= would drop it, since showing a report is the safer error than hiding one. A report naming another attempt is dropped. =latest= stays unset (its default, =false=).

*A failure says why.* =errorCode= is read, and a =Failed= or =NotProcessed= report is written =failed (EULA_NOT_ACCEPTED)=, =not processed (CODE)=; a comma, a parenthesis or whitespace in a code becomes one space, so the value still splits at its commas when a summary reads the file back. The counts recognise the prefix, so the row is still failed. =--%= and =*%= are written verbatim, as Turnitin shows them: =--%= is an AI Writing report Turnitin could not score (too little qualifying prose) and =*%= its asterisk for 1 to 19 percent. =--%= is counted apart, as /unscored/; =*%= is a score and counts as processed.

*A missing report on a processor's column reads none.* A handed-in row (GraphQL =submittedAt=) whose connection is present but holds no current report is written =:SIMILARITY: none= — but only when the assignment has a processor, since otherwise every row of every column without one would say it. Whether it has one is asked with a one-field query (=org-canvas--submissions-processors-query=, =assignment(id) { ltiAssetProcessorsConnection { nodes { _id } } }=), and only when some handed-in row lacks a report, so a column where every file has its report costs nothing extra; a caller that already knows (#437, from #350's course-wide read) says so and is not asked. A failed processor read is one warning and the rows stay blank. A null connection — Canvas's answer when the processor feature is off, or for a discussion submission without the discussions flag — is not "no report", and stays silent.

*Counted per row, still.* #351's rule holds: a row counts once, now in one of five buckets in this order — failed (any report failed or was not processed), pending, none, unscored (a report answered =--%=), processed (=org-canvas--submissions-report-count-keys=). The =Reports:= line names the two new ones only when some row falls in them (=Reports: 36 processed, 7 failed, 0 pending, 4 unscored, 3 without a report=), so a column with neither reads as it did. The grading queue sums the same keys over its columns, and its =failed in R6 (7)= still names only the failures, the count a grader acts on first.

*What still needs a live look.* The rule was read from the canvas-lms source, the file case was checked against the reporter's live data, and nothing else: a discussion column with the processor (the =lti_asset_processor_discussions= flag), an online text entry (whether its asset records =submissionAttempt=), and a group assignment (whose reports include the groupmates' submissions, whose files a group submission shares) have not been seen on a live course. The contract fixture gained =LtiAsset= and =DiscussionEntryVersion= with =--supplement= from the canvas-lms SDL at =318f2ad0=.

REST's single-submission PUT does take =submission[seconds_late_override]=, but a second write path for one field, meaningful only under =late=, did not fit cleanly; it is left for when a course needs "count this as one day late". So the read asks =users/self= for the id first (the way messages.el resolves =TO: Self=), and the docs say plainly that a TA grading in the browser sees their own library, not the instructor's; the issue's "TAs would then use the same wording" does not follow from the schema. A created item carries the column's =assignmentId=, which the input accepts; whether SpeedGrader then lists it only on that column is for a live run to say.

*A section, not a file.* The bank lives under a level-1 =* Comment Bank= heading in the grading file, after the rubric and before the students, with no =USER_ID=, so every loop over the students passes it by as it passes =* Rubric= (#265). One list item per saved comment: =- 4821 :: text= for one on Canvas, labelled with its id, and =- text= for one to create; a longer comment continues on indented lines, as a Rubric comment does (#263), and is normalized the same way before any comparison. The pull writes the heading with a template (=org-canvas-submissions-comment-bank-template=, nil to leave it out) and nothing else: reading the bank on every pull would add a request and a =users/self= to each of them for something most columns never use, so the grader reads it in with =B= (=org-canvas-submissions-pull-comment-bank=) when wanted. A refresh carries the section over as it stands (=org-canvas--submissions-bank-carryover=), since everything in it is the grader's or was read in on their request.

*A baseline, so an edit has a side.* The heading's =CANVAS_COMMENT_BANK= property holds each labelled item's text digest as last read or written. A labelled item whose text digests to its entry is settled; one that does not was edited here. =S= reads the bank before sending anything and then, per pending item: an unlabelled item whose text the bank already holds is labelled with that id instead of created (the duplicate guard's rule, Hard Rule 20); any other is created and labelled with the id Canvas answers; an edited labelled item is rewritten only when Canvas's text is still the baseline, and an item edited in SpeedGrader too is left with a warning pointing at =B=; a label the bank no longer holds is left with a warning saying how to create it again. =B= is the mirror: it adds what the bank holds and the section lacks, labelled, and gives an unedited labelled item Canvas's text, while an item edited here keeps the grader's.

*Nothing is deleted unasked.* Removing an item from the section sends nothing, since a missing line is as likely a tidy-up as an intent, and the bank is shared with every other column the grader marks (Hard Rule 16's spirit). The one delete is =x= on a labelled item (=org-canvas-submissions-delete-comment-bank-item=), after a =y-or-n-p=, and the line goes only once Canvas answers without errors.

*Failures stay local.* A bank that cannot be read (the =users/self= GET or the query failing) is one warning and nothing is sent to it, since without the read there is no duplicate guard; the push's message says the bank was not read. One refused mutation is one warning and that item stays pending, the others go through. The mutations go through =org-canvas--graphql-mutate=, so a dry run labels nothing and a course marked read-only sends nothing, and each reply's =errors= list is read, since GraphQL answers a refusal with a 200.

* A Sent Comment Carries Its Id, and Only Its Author Changes It (issue #419)

On 2026-09-30 a course rewrote every unposted comment to a new feedback style before posting. Rubric comments and =Comment to post= drafts could be rewritten in the file and pushed, but some seventy submission comments already sent — by the instructor, by a TA in SpeedGrader, by earlier pushes — sat under =** Comments=, which the pull rendered read-only, and the one comment writer was the draft's POST. Posting a second comment gives the student two versions; replacing seventy by hand in SpeedGrader defeats the file. Canvas has the two calls it takes, =PUT= and =DELETE= on =courses/:course_id/assignments/:assignment_id/submissions/:user_id/comments/:id=, the PUT taking the new text as a top-level =comment= (=SubmissionCommentsApiController#update=, =params.permit(:comment)=).

*The id goes in the label.* #264 made a comment a description item, =- *Author* <time> :: text=, its later paragraphs indented under the label; the id joins the label in brackets, =- *Author* <time> [48213] :: text=, so the item keeps its shape and the text its place. The reader (=org-canvas--submissions-sent-comments=) matches only items that carry an id and takes a label with no =::= in it, so a comment text holding =[5] ::= in an old item is never read as a label; an item without an id — every item of a file pulled before #419, and the =*You*= record a posted draft leaves, since the reply's comment is not matched back to the draft — is left out, and nothing can change it until a refresh renders it with its id. The item's text is read and normalized exactly as a Rubric comment's (#263), since it is the same kind of item.

*A baseline, so an edit has a side.* The student's heading gets =CANVAS_COMMENTS=, each id's text digest as last pulled or pushed, the shape of =CANVAS_COMMENT_BANK= (#352). The digest is taken of the text as the item shows it — Canvas's comment through the grading file's conversion, then the item normalization — so an untouched item always digests to its entry, and the push's re-read of Canvas digests the same way. An item whose text no longer digests to its entry was edited here; an item the baseline does not name cannot be told edited and is not. The pull converts each comment once for both, through a cache bound around the render.

*A deletion is a mark, never an absence.* =- DELETE *Author* ...= marks one to delete, a word typed after the dash where it cannot be missed. Removing the line sends nothing, the rule of the Comment Bank and of #417's absent score: a missing line is as likely a tidy-up as an intent, and a refresh brings it back, which doubles as the way to discard an edit. An emptied item is not a deletion either, and not sent: Canvas would store an empty comment, and the way to delete is the mark.

*Only the author's.* Canvas's policy (=SubmissionComment=, canvas-lms =bf50faf2=) lets only a comment's author update it, while any grader who can modify comments may delete one; the push holds deletions to the author too, so a TA's comment stays the TA's. The file does not record authors' ids, and knowing the grader's own at pull time would cost every pull a =users/self= for something most columns never use; so the push, when it has comment changes, reads =users/self= once and the column's submissions once, and checks each change against what Canvas holds before the confirmation: a comment by someone else, one whose text on Canvas no longer digests to the baseline (edited in SpeedGrader since the pull), one gone, or an emptied item is refused. A refused change is one warning, one line in the confirmation's listing, a count in the question and the closing message, and is left in the file as typed; it is never sent. A read that fails refuses every change, since neither author nor baseline could be checked. The read runs before the question, as the grade conflict check does, so the question counts only what will be sent.

*What Canvas stored.* After a PUT the item shows the text Canvas answered, converted as a pull would, and that becomes its baseline (#349's rule); a reply without one keeps the item's. After a DELETE the item and its baseline entry go. One refused request is one warning and the item stays pending; the others go through. The changes go after the late statuses and before the drafts, so an edited comment is in place before a new one lands. Under =org-canvas--dry-run= nothing is sent and nothing in the file changes (Hard Rule 1), and a course marked read-only refuses at the transport as for every write (#163).

*A refresh keeps what was not sent.* Before a re-render the changed items are collected with the baseline each was changed against (=org-canvas--submissions-comment-edits-by-student=) and written back over the fresh items by id: an edit Canvas already holds is confirmed and nothing is written; otherwise the grader's text or mark comes back with its old baseline, so a comment Canvas changed meanwhile is refused by the next push instead of overwritten, and the refresh's log says so. A comment Canvas no longer holds takes the change with it, and the warning quotes the text typed, the only copy. This is #281's rule for typed scores, kept outside the score carry-over so the two do not share code.

*Contract.* The vendored OpenAPI spec lacks both operations, so the fixture generator carries them as a supplement transcribed from canvas-lms's =@API= documentation at =bf50faf2= (=SUPPLEMENT_OPS=, written with ="supplement": true=), and refuses to run once the spec gains them; the request-body contract checks the PUT's body against it and the DELETE for having none.

The posted-draft record also moved: it was inserted after the run of lines starting with =- =, which ended inside a longer comment's indented paragraphs and cut them from their item, a comment the push would then have read as edited; it now goes after the section's last line.

*A comment-only push (issue #425).* Fixing the wording of feedback already sent and deciding when grades go out are separate decisions, and the full push made them one: a grader holding twelve columns' grades while rewriting their comments had to call the three internals by hand, and the script's own =save-buffer= then met a "changed since visited" question in batch, so the new baseline was never written. =org-canvas-push-submission-comment-edits= (=C=, and =push-comments= on the command line) sends the rewritten and =DELETE=-marked comments and nothing else: no score, rubric row, late status, draft or Comment Bank item, and never a post. It is the full push's comment phase on its own, not a copy of it: =org-canvas--submissions-pending-comment-edits= (collect, then check) feeds both, the question is =org-canvas--submissions-confirm-push= with nothing but the comments, the sends are =org-canvas--submissions-apply-comment-edits=, and =org-canvas--submissions-comment-edit-result= gives both the same counts (=:edited=, =:deleted=, =:refused=, =:failed=, =:dry-run=), so a refusal rule or a count added to one is in the other. The file is saved through =org-canvas--save-buffer=, whose freshness guard is what the script lacked. A course marked read-only refuses once, before the question, rather than per comment at the transport; a dry run is let through, since it sends nothing. The target is taken as =org-canvas-push-submission-grades= takes it (#381) — the grading buffer at hand, else an id or a name, nil asking — but the question stays, through =org-canvas--confirm=, which batch answers: unlike the grade push, nothing here is offered afterwards that a script would need to opt into. Drafts under =Comment to post= were left out: posting one is already =c= or the full push, and a draft-only push would need its own answer to whether a draft may go before its grade.

* A Grading File's Comments Export, Import and Check as Data (issue #438)

On 2026-09-30 and 2026-10-01 two course-wide passes rewrote some 1,600 Rubric row comments across twelve grading files, and both ran on scratch Python scripts that parsed the Org text with regular expressions: one pulled each student's rows, draft, sent comments and notes into JSON for a rewriter, the other checked the rewritten text and wrote it back, then proved nothing else had moved. The package already had the parser — the push reads every one of those texts on its way to Canvas — but not as "give me this file's comments" or "set this student's row comment". =org-canvas-submissions-comments.el=, a command file above =org-canvas-submissions= as the window and status files are, is those scripts as three commands.

*One parser.* Export reads through the push's own readers: =org-canvas--submissions-rubric-rows= (the table and the =- ID ::= items of #263), =org-canvas--submissions-comment-draft=, =org-canvas--submissions-sent-comments= (#419) and the Notes section's text. Import writes through its writers: =org-canvas--submissions-rubric-set-comment= for a row, =org-canvas--submissions-rewrite-sent-comment= for a sent comment. The draft's normalization was pulled out of =org-canvas--submissions-section-text= as =org-canvas--submissions-section-normalize=, so the import compares a new draft exactly as the push will read it. The one writer of its own is the draft's: =org-canvas--submissions-set-section= deletes the section through its trailing blank lines and adds one back only before a heading, which grows the file by a line when the draft is the last section of a student; the import replaces only the section's text, keeps its =#= lines (the template) above it, and leaves the blank lines that follow alone. Testing it found =org-canvas--submissions-section-region= signalling "Invalid search bound" for a section heading with nothing under it that ends the student (a =Comment to post= whose template was deleted), which stopped the push as well; such a section is now an empty region at the end of its heading line.

*Keyed, and touching nothing else.* A row is found by (user id, criterion id), a draft by user id, a sent comment by (user id, comment id). The input has the export's shape and may carry only the keys to change; a key absent is untouched, a key present with null empties the row comment or the draft. A text equal to the file's, after the same normalization the push applies, is no change, so importing an unchanged export leaves the file byte for byte as it was, and changing one of each moves exactly those lines. The student headings are collected as markers before anything is written (Hard Rule 9), and each change re-reads its section, since an earlier write moves the positions. A key that matches nothing — a user, a criterion, a comment id, a student with no =Comment to post= — is named in the result and the echo area, and the batch command exits 1 on it, since a rewriter that invented or mistyped a key needs to hear so.

*A sent comment is imported as a hand edit.* Since #419 an edited item is one whose text no longer digests to its =CANVAS_COMMENTS= entry, and #425's =C= sends exactly those. The import rewrites the item's text, keeps its label, id and =DELETE= mark, and leaves the baseline alone, which is the state a hand edit leaves; =C= then sends it, and its checks (only your own comments, none edited on Canvas since, none gone) refuse what they would refuse of a hand edit. The import does not check authors itself: the file records none, and #419 deliberately left that read to the push. An emptied text is refused, as the push refuses an emptied item: deletion is the =DELETE= mark, never an absence (#419).

*Posted students are kept back.* The scripts skipped them on export. Export now includes them, with =posted= holding =POSTED_AT=, since a check or a rewriter may want to see them; import keeps back every change under a posted grade and names each one, unless =ALLOW-POSTED= (=--posted=). A student who has read a comment would find it silently rewritten by the next push; a correction after posting is still possible, but as a choice, not as a side effect of a bulk pass. Refusing outright was rejected (the occasional correction is legitimate) and so was allowing with a warning (the warning scrolls past in a pass over twelve files).

*A draft line starting with =#= is refused.* Org reads it as a comment and the push leaves it out, so writing it would put text in the file that never reaches the student.

*Dry run.* Each change is worked out by comparison before anything is written, so a dry run reports the same counts and names the same keys and writes nothing; the batch =-n= binds =org-canvas--dry-run= for it as it does for the pushes.

*The check, and what fails it.* A deducted row (score below max, both numbers) without a comment, and any text matching a regexp in =org-canvas-submissions-comment-flag-regexps= (empty by default), are errors: the first is the course's standing rule, and the regexps are a course's own rules, typed on purpose. A sentence of =org-canvas-submissions-comment-sentence-min-length= characters or more given word for word to more than =org-canvas-submissions-comment-shared-threshold= students is a warning: a stock sentence is sometimes meant ("See the feedback guide for the rubric levels."), and a batch check that failed on it would teach its user to ignore the exit status. Only errors make =check-comments= exit 1, as only errors fail =org-canvas-validate-batch= (#413). Posted and departed students are not checked: their comments are either already read or never going to be. The script's other checks — length, a next-step marker, banned verbs on one kind of row — were particular to one feedback guide; the regexps cover the ones a pattern can state, and the rest stay with the course.

*JSON in and out.* The consumer is a script or a language model, so JSON is the real interface: keys in snake_case (=user_id=, =criterion_id=), every id a string as the file spells it, arrays always arrays (an empty =rows= is =[]=), =delete= a boolean. Import accepts the export's object or a bare array of students, ids as strings or numbers. Through =json.el= rather than =json-serialize=, which an Emacs built without native JSON lacks.

* The Roster Marks Who Left, and Only on Canvas's Word (issue #290)

=org-canvas-pull-people= upserted everyone the roster read returned and, by the pull-only rule, deleted nothing for being absent. A student whose enrollments were deleted therefore kept =ENROLLMENT_STATE: active= for the rest of the term: the roster read asks for active, invited, inactive and completed, and a deleted enrollment is none of those, so the heading was simply never reached again. The only sign was the pull's count (108) disagreeing with the file's (109), and the state was found with a hand script against the enrollments endpoint with =state[]=deleted=. The grading files had got the same rule in #282 (=STATUS: left=); the roster had not.

After the upserts the pull collects, as markers, every heading whose =USER_ID= the roster read did not return (=org-canvas--people-absent-headings=), and reads each one's enrollments on its own: the same course index with =user_id= and every =state[]= Canvas documents (=org-canvas--people-departure-params=). Only that user's rows in a role the roster lists count, whatever else comes back, so an ignored =user_id= cannot mark anyone either. The verdict (=org-canvas--people-departure=) is one of three:

- /departed/: rows exist, and none is in a state the roster read asks for. =ENROLLMENT_STATE= becomes the states Canvas gives (=deleted=, =rejected=), and =DEPARTED= the latest =updated_at=, which is stable, so later pulls rewrite the same value.
- /absent/: no row at all. =ENROLLMENT_STATE: absent=, and =DEPARTED= the pull that first found it so; a heading already =absent= keeps its date.
- /unverified/: a row is in a state the roster asks for (the roster read missed the person), a row is =creation_pending= (enrolled, with no account yet), a row carries no state, or the read failed. Nothing is written, and the closing line names the heading as left unchanged.

Asking the per-person read for every state, the listed ones included, is what makes the third case possible. The issue suggested asking for =deleted=, =completed= and =inactive= only; with that, a roster read that came back short would have sent every missing person's read back empty and marked them =absent=, which is Hard Rule 16's misread-list-as-empty mistake one level down. Asking for everything, a person the roster read dropped comes back =active= from their own read and is left alone. The same rule covers the empty roster: a course always has its teacher, so an empty read with a =people.org= that holds =USER_ID= headings is a misread, and the file is left untouched (the empty-file note, which overwrites, is kept for a file with no person in it). The cost is one request per missing heading on every pull, departed ones included, which is a handful in a term and lets a state change (=rejected= to =deleted=, a re-enrollment) show up without a special path; a person listed again is upserted as before and loses =DEPARTED=.

The departures go in the closing line, one per heading with its state and date, as the issue asked, since a departure nobody reads about is the silence the issue was about. Nothing downstream changed how it resolves a name: a departed heading still carries its =USER_ID=, a grading file or an override written against it still means that person, and hiding it would turn "left the course" into "not found". Instead =org-canvas-validate= warns (=org-canvas--validate-departed-people=, reading =org-canvas--people-departed-state-p= from core) when an override row, an accommodations row or a message's =TO= names someone whose state lists neither =active= nor =invited=; the override and accommodation warnings are push-only, like their not-found siblings.

People is pull-only and deliberately not a registered feature — registering it would put the roster in the drift report, the orphan scan and prune — so its read parameters live in the module's own constants. The contract fixture gained a =pull_only= entry for =list_enrollments_courses= (=PULL_ONLY_READ_OPS= in the generator), and the read-parameter contract checks both reads against it, =user_id= included (Hard Rule 13's check, without the registry).

* A List Pull Marks the Headings Canvas Deleted, on Canvas's Word (issues #392, #399)

A re-pull of a live course reported =Assignments pull complete: 52 items.= while =assignments.org= held 56 headings with a =CANVAS_ID=: four assignments had been deleted on Canvas, and the pull, which upserts what the list returns and nothing else, never reached their headings again. Nothing in the log named them; a count against the API did. #290 had fixed the same shape for the roster only. In a writable course the stale headings were worse than silent: a push PUT to an id Canvas no longer had, and the 404 recovery (=org-canvas--handle-404-retry=) re-created the item under a new id, undoing the deletion without a word.

Every list pull now runs =org-canvas--pull-mark-unlisted= after its upserts: those generated by =org-canvas-define-pull= (announcements, assignment groups, assignments, discussions, grading schemes, group categories, pages, rubrics) since #392, and the pulls with code of their own (classic quizzes, New Quizzes, modules, outcomes, files, calendar events) since #399. It collects, as markers, each stamped heading of the feature's top level whose id the list read did not return — the ids of every item the read returned count as listed, the ones a =:skip-fn= held back included, since those are on Canvas — and reads each one on its own at the registry's item URL with its =:item-params= (Hard Rule 13). The read is =org-canvas--pull-item-read=, which returns the item or =gone= and signals anything else; the verdict (=org-canvas--pull-item-state=) is one of three:

- /gone/: a 404 (=org-canvas--api-not-found-p=, which reads the status off the end of the signalled message; =org-canvas--404-error-p= matches =404= anywhere, an id included, too loose to mark anything on), or a reply whose =workflow_state= is =deleted=. The heading gets =CANVAS_DELETED=, an inactive timestamp of the pull that first found it so, kept on later pulls. The heading and its text stay: the mirror may be the only copy.
- /present/: Canvas serves the item. The list read missed it (or a page's old slug still resolves); nothing is written.
- /unknown/: any other failure, a 403 or a 500 included, logged. Nothing is written.

The closing line names the gone headings with their dates, and the ones left unmarked, as #290's does; each gone heading is also a =gone= record in the pull summary, a section of its own in =org-canvas-pull-all='s report. A heading the list returns again is upserted as before, and the upsert removes =CANVAS_DELETED=: =org-canvas-org-save-sync-state=, through which every pull stamps an id, the hand-written ones included, drops it (#399), as =org-canvas--conflict-pull-local= does for a pull at point or from the conflict prompt, since Canvas answered with the item.

A misread list must never mark anything (Hard Rule 16). Deciding on each heading's own read means a list that came back short costs requests, not headings. The same rule covers the empty list: =org-canvas--pull-emit-empty-file= overwrites, so a list read that came back empty used to replace a file of headings with the "Canvas returned 0 items" note. Now the note is written only to a file holding no heading at all; otherwise the empty list goes through the same per-heading reads, and a course whose items really were all deleted gets every heading marked rather than erased.

"Top level" is =LEVEL=1=, where the pull writes, joined with the property registry's =:query= when that names another level (=org-canvas--pull-gone-query=): assignment groups sync as level-2 headings under a container, and a deleted group there is marked too. Child levels — a rubric's criteria, a quiz's questions — are never matched: they have their own reconcilers, and Hard Rule 16 keeps them unpruned. A feature with no registry entry to read an item from marks nothing, since there is no item URL to ask.

A pull at point (and a pull by name, and the drift report's pull) reads its heading through the same =org-canvas--pull-item-read=: where it used to fail with the 404, it now marks that heading =CANVAS_DELETED=, keeps its text, saves, and says so (#399). It never marks another heading. A pull by name reports the heading's outcome as =deleted=, and =org-canvas-pull-headings= counts those apart from the pulled and the failed. Any other failure still signals.

What a mark means elsewhere:

- The sync skips the heading before parsing it (=org-canvas--sync-skip-deleted=), counted as a skip and named among the skipped titles with "(deleted on Canvas)", so the full sync's summary shows it; a push at point or by name refuses it with a =user-error= saying how to proceed: delete the heading, or remove =CANVAS_DELETED= and its id to create it again. Removing the mark alone brings back the old behaviour, a PUT that 404s and is recovered, which is then the user's explicit choice.
- =org-canvas-validate= warns on a marked heading (=org-canvas--validate-canvas-deleted=). The finding is about the course, not the push, so it is not push-only and a read-only course hears it too. Its checks that pair or count headings across a file leave out a marked heading, and one under a marked heading, by the rule the push skips it with (=org-canvas--sync-deleted-stamp=, the one definition): the duplicate-title check (#164), which paired four deleted assignments with the live twins the instructor had kept and raised three false errors on a live course; the module-item id check; the group weight sum; the assignment count the drop rules are measured against; and the grading-scheme ids a =GRADING_STANDARD_ID= may name (#402). The heading's own warning covers it.
- The drift report's MISSING row adds "a pull marked it CANVAS_DELETED ...". The row still counts as drift: the file and the course disagree until the heading is deleted, and the report must never write (Hard Rule 19).
- =org-canvas-status= shows a "Deleted on Canvas: N" count per file.

=CANVAS_DELETED= is sync state, like =CANVAS_ID= and =CANVAS_UPDATED_AT=, so it is named once in =org-canvas--prop-canvas-deleted= and documented with the common properties rather than registered per feature; #290's =DEPARTED= is a roster word and the roster keeps it.

** The pulls with code of their own (issue #399)

Each custom pull calls the helper once its upserts are done, before it writes the file header and saves, and appends =org-canvas--pull-gone-suffix= to its closing line. The helper accepts either a feature registry name or an entry, and a query naming the headings the list answers for when the default (=org-canvas--pull-gone-query=) would be wrong. Each item URL below was checked against =canvas-openapi3.yaml=:

- /Classic quizzes/: level-1 quiz headings, read at =/courses/:course_id/quizzes/:id=. Questions are never matched.

- /Outcomes/: level-1 group headings only, at =/courses/:course_id/outcome_groups/:id=, the registry entry's item URL. Every custom sync already runs through =org-canvas--sync-process-entry=, so a marked heading is skipped by a full sync of each; New Quizzes' hand-written push at point refuses one through =org-canvas--sync-refuse-deleted=, the guard the generated at-point runtime uses.

That a deleted item's own read is a 404 (or a deleted state) comes from reading Canvas's controllers, not a live course, for these types as for #392's.

Group categories needed one repair on the way: Canvas serves a category at the unscoped =/group_categories/:id= only, so the course-scoped item URL the registry derived from =:endpoint= 404ed for every category, which would have marked every unlisted one gone. The registry entry now names =org-canvas--group-category-item-url= as its =:item-url-fn=, which also fixes pull at point and the orphan cleanup's delete for them.

* A Push Takes Its Heading by Name, Not Only from Point (issue #287)

The at-point commands were the only per-entry push, and they are interactive by design: point, current buffer. A batch script that wanted to push two named headings — a due date moved on one assignment, an objective reworded on one page — opened the course file itself, searched for the heading by regexp, called the at-point command and saved: twelve lines rewritten in every push script since the course started, each a place to get it wrong (a regexp that matched =R10= for =R1=, a heading found in the wrong file, a save skipped after the stamp). Issue #280 was the same gap on the submissions side.

=org-canvas-define-sync= now generates a third command beside the sync and the at-point one: =org-canvas-sync-<singular> (TARGET &optional BY)=. The file is the module's =:file=, the headings are those its =:query= selects, and TARGET is matched exactly against the heading's text as written (=org-complex-heading-regexp= group 4, so a file heading that is a link matches by its markup on every Org version) or as =org-get-heading= reads it, or with BY =canvas-id= against the module's =:id-property= — =CANVAS_URL= for a page, =CANVAS_ASSIGNMENT_ID= for a New Quiz — so the macro hands the property down as a spec key. Zero matches and several are both a =user-error= naming the file: a script must never push the wrong heading, and two headings with one title are a file to fix, or a job for the at-point command, never a guess. The heading found, the existing =org-canvas--push-at-point-runtime= runs at that position and saves, so the two commands cannot drift apart: the at-point command was left as it is rather than rewritten as "sync the heading at point by its title", since a title that appears twice in a file would have broken a command that worked on point.

The runtime now records what it ended as in the context's =:outcome= — =synced=, =unchanged=, =conflict=, =pulled=, =duplicate= or =dry-run= — because a caller without an echo area needs the answer as a value. Recording the dry run showed the runtime finalizing the sentinel: under =org-canvas--dry-run= an at-point push would have stamped =CANVAS_ID: dry-run= into the heading, which no one had run because =org-canvas-sync-dry-run= is a full sync; it now reports the dry run and stamps nothing (Hard Rule 1).

=org-canvas-sync-headings= takes a list of =(FEATURE . TITLE)= or =(FEATURE TARGET BY)=, resolves every feature first through a registry the macro fills (=org-canvas--sync-heading-fns=, plural or singular name), so a misspelt one stops the batch before anything is sent, then runs each in its own =condition-case=, reporting one redacted line per heading and a closing count, and returns the outcomes. It does not pace between headings itself: every request already goes through =org-canvas--api-pace=. Nil as a target asks for a title with completion, and under =noninteractive= is a =user-error= rather than a read of standard input. New Quizzes, whose at-point command is hand-written, register a hand-written =org-canvas-sync-new-quiz= that finds the heading the same way and calls it.

* A Push of One Assignment Sends Its Overrides Table (issue #380)

An overrides table sits under its assignment heading and reads as part of it, but only =org-canvas-sync-overrides= sent it, and that reconciles every table in =assignments.org=, PUTting every override Canvas holds again whether or not its row changed. A section's due time moved less than an hour before the section met: the heading's dates and its section row were edited together, =org-canvas-sync-headings= said =synced=, and the section still closed at the old time. A push reporting success while the dates students see are unchanged is a silent partial push.

*The push of one heading reconciles that heading's table.* =org-canvas-define-sync= takes a new option, =:after-heading=, a function of the run context that =org-canvas--push-at-point-runtime= calls with point on the heading once the push went through — =synced=, =unchanged= or =dry-run=; a push stopped at a conflict, a pull or a duplicate sends nothing more. Both the push at point and the push by heading run through that runtime, so both get it, and the whole-file sync never does: the master sync still reconciles overrides at Tier 1.75, once, after sections and assignments. An =unchanged= push counts, since the table is not in the payload hash, and a table edited alone must still be sent. Assignments pass =org-canvas--assignment-sync-heading-overrides=, which calls =org-canvas--override-sync-entry= — the one heading's reconcile, now shared with the whole-file loop — through a =declare-function=, never a require. That reconcile keeps the baseline as #348 made it: a heading clean before the override writes is restamped after them. The runtime keeps the heading as a marker that advances on insertion, since finalize may insert =#+LAST_SYNCED= above a file's first heading and leave point on the header.

*The result says so.* What the function returns is kept as the context's =:heading-report= and merged into the =org-canvas-sync-headings= result: =:overrides= is the =(CREATED UPDATED DELETED)= counts, or =failed= when the reconcile signalled — the assignment itself is on Canvas by then and its outcome stays =synced= — and =:note= is printed after the outcome on the heading's closing line. A heading with no table, or with no =CANVAS_ID= under a dry run, adds nothing.

*An unchanged override is not sent.* The reconcile compares a claimed override's =due_at=, =unlock_at= and =lock_at= with the row's before its PUT, as instants, so a zone spelled differently still matches; a blank cell matches only an absent date, because the PUT sends only the dates the row fills and Canvas clears the ones it omits. A match is left alone and counted nowhere, but still claimed, so it is not deleted either. This covers the whole-file sync too, which now writes only what changed.

The issue's scratch script, calling the private helpers by hand, is what the change does. A separate public command for "this heading's overrides only" was not added: it would be a second name for the same push, with its own dry-run obligation, and a table is never meant to be sent without its heading's dates.

* An Override-Only Push Restamps a Drifted Heading (issue #410)

#348 restamps a heading's =CANVAS_UPDATED_AT= after its override writes only when the heading agreed with Canvas before them: a heading that had already drifted keeps its stamp, so a web-UI edit stays visible as drift. The commonest web-UI edit is itself an override. Two extensions were given in the web UI, which moved the column's =updated_at=; the rows were copied into the Org table and the heading pushed by name. The assignment was skipped as unchanged (its hash matched), the two overrides were PUT, and the heading was dirty by #348's test, so the stamp stayed at the day before. The next drift report, two seconds later, called the column CHANGED "in a field this report does not compare", and every extension after that would do the same, each leaving a false CHANGED row and a conflict prompt at the next real push.

*A drift the overrides explain is restamped.* The reconcile now takes a =:mismatch-fn=. On a heading that had drifted before the writes, after them, it reads the assignment once more and hands the reply to that function, which answers the heading's own fields Canvas holds otherwise. None means the moved =updated_at= can only have been the overrides the reconcile has just matched, and the stamp moves to the reply's =updated_at=; a field that differs keeps the stamp, and the log names it, so the next push still reports the conflict. The comparison is the push echo check's (#349): the payload the runtime built for the heading — kept on the context as =:heading-payload=, sent or not — against the read, by the registry, so a nested or renamed field is no false alarm. A dry run reads and compares nothing, as before.

*Only a push by heading passes the function.* Assignments' =:after-heading= builds it from the context's payload; =org-canvas-sync-overrides= over the whole file passes none and keeps #348's rule exactly, because there the assignment's own fields may hold unpushed edits — the master sync has already put every drifted heading through the conflict prompt at Tier 1 before the overrides run at Tier 1.75. The issue's diagnosis was that the skip path lacked the restamp; the restamp was there and declined by design, and the rule it lacked was a way to tell an override-only drift from any other.

* The Drift Report Compares Overrides Tables (issue #411)

=org-canvas-diff= compared every registered property and the body, and an override is neither: a per-student extension given in SpeedGrader moved the column's =updated_at= and nothing the report compared, so the row read CHANGED with "no compared property differs", and the extension itself was never named. A read-only GET of the assignment's overrides was the only way to learn what Canvas held. Since #380 a push by heading reconciles the heading's table, so an extension the report could not show was deleted by the next push of that heading — =2 deleted= — had the rows not been copied first. The one Canvas-side edit a by-heading push destroys was the one edit the report could not show.

*A child pass under Assignments, costing no request.* The Assignments list is read with =include[]=overrides= — added through the property registration's =:body-list-params=, the key pages use for =include[]=body= (#83), checked against the spec by the read-parameter contract (#273) — so every assignment arrives with its overrides and the pass makes no request of its own. It is a child check like Module Items (#177) and New Quiz Items (#322), reported in a section named *Assignment Overrides* right after Assignments. Every stamped heading's =#+NAME: overrides= table is parsed by the sync's own parser and each row paired with a Canvas override by the sync's own claim (=org-canvas--override-find-existing=: a section row by its section, a group row by its group, a student row by the same set of students), both declared from sections.el, never required, as diff declares modules' functions (#299). A Canvas override no row claims is EXTRA, and its row says the next push of that heading deletes it; a row Canvas lacks is MISSING, which the next push creates; a claimed override whose dates differ is CHANGED with the dates, compared as the reconcile compares them (#380), so a row the push would not send is not a row that differs. An EXTRA whose dates are the assignment's own says so, since a pull writes no row for it. A stamped assignment whose reply carries no =overrides= key makes the section "could not check", never a course without overrides (Hard Rule 16). A heading a pull marked deleted is left out, as the sync leaves it (#402).

*The rows have their own kind and their heading.* Every row is kind =override=, with its state (=extra=, =missing=, =changed=), its assignment (=:where=, =:assignment-id=, the assignment's =html_url=) and its heading's file and line. So =RET= visits the assignment heading, =b= opens the assignment's page, and =p= pulls the heading — the table is part of it, and the assignment pull writes Canvas's table whole — which is how an extension is adopted without a hand copy. The other verbs refuse: an override is deleted by dropping its row and pushing the heading, so =k= has nothing to add, and an acknowledgment would hide what the next push destroys. The section is excluded as ="assignment-overrides"=. A pull over a heading now removes the table it holds before writing Canvas's, since an assignment with no description left the body, and so the old table, alone, and the fresh table landed under the stale one.

*A push by heading asks before deleting.* The reconcile's delete step takes a confirm flag, which only the by-heading push sets: with overrides Canvas holds that the table lacks, it asks with =y-or-n-p=, naming who loses what, whatever =org-canvas-assume-yes= says — a student's extension is not recoverable from Org once gone — and under =noninteractive= keeps them, since a batch push of one heading has no one to answer and must not delete an override no one has seen. The counts gain a fourth number, the overrides kept, which the closing line names as =N kept that the table lacks= when there are any. =org-canvas-sync-overrides= over the whole file still deletes them without asking, as it always did: the whole-file sync is the deliberate reconcile, and its report is the drift report run before it. A dry run asks nothing, since it sends nothing.

* A Pull Takes Its Heading by Name Too (issue #346)

#287 gave pushes a caller without a point; pulls kept only =org-canvas-pull-at-point=. Taking Canvas's version of one heading from a batch Emacs — the approved "Canvas is right" half of a drift report's CHANGED row — meant finding the heading by regexp, redefining the private =org-canvas--confirm= for the rest of the session, pulling and saving.

*The pull twin is generated where the push one is.* =org-canvas-define-sync= also emits =org-canvas-pull-<singular> (TARGET &optional BY)= for a feature with a single-item pull: one that hands the macro =:pull-item-fn=, or says =:pull-heading t= because it registers its pull-item function apart from the sync (classic quizzes, which keep the pull out of the conflict prompt, #295). Outcomes have no single-item pull and get none. New Quizzes, whose sync by heading is hand-written, get a hand-written =org-canvas-pull-new-quiz=. The heading is found by the same =org-canvas--sync-find-heading=, with the module's own =:file=, =:query= and =:id-property=, so a title matches exactly as it does for a push; the errors say to pull, not sync, a repeated title at point.

*The at-point pull's own pieces do the work.* =org-canvas-pull-at-point= was split into a target (=org-canvas--pull-at-point-target=: the feature for the file, the climb to the level-1 entry for a =:pull-whole-entry= feature, the stamp, and the refusal of a heading without one) and the fetch (=org-canvas--pull-at-point-1=, through =org-canvas--conflict-pull-local=, which restamps =CANVAS_UPDATED_AT= and drops =PAYLOAD_HASH=). Both moved from org-canvas.el to org-canvas-core-sync.el, since generated commands live in feature modules, which may require only core. The at-point command keeps its confirmation between the two; the pull by heading has none, because naming the heading is the answer, and saves the file afterwards, which the at-point command leaves to the user. Under =org-canvas--dry-run= it reads and writes nothing and answers =dry-run=; otherwise =pulled=. The issue's other option, a NOCONFIRM argument to =org-canvas-pull-at-point=, would still have left the script finding the heading and saving it.

*=org-canvas-pull-headings= is =org-canvas-sync-headings= with another registry.* Entries are read by the same =org-canvas--sync-headings-entry=, every feature is resolved first (=org-canvas--pull-heading-fns=, filled by the macro), and each runs in the same =condition-case= (=org-canvas--headings-run=, now shared), so a misspelt feature stops the batch with nothing read and one failure does not stop the next.

*The names cannot meet the whole-file pulls.* Those are the plural (=org-canvas-pull-assignments=), these the singular (=org-canvas-pull-assignment=), the same split as =org-canvas-sync-assignments= and =org-canvas-sync-assignment=; none of today's singulars is any other command's name (=org-canvas-pull-quiz= sits beside =org-canvas-pull-quiz-results= without touching it). A feature named by a word with no plural =s=, whose singular would be its plural, would have its whole-file pull silently replaced, so =org-canvas--pull-heading-fn-forms= refuses that at expansion, and a spec checks every registered pull by heading still carries its own docstring.

* A Classic Quiz Pulls Whole, Into One Heading (issue #295)

A survey built in the Canvas web UI showed up in the drift report as a Quizzes EXTRA. The recovery the report points at — write a stub with its =CANVAS_ID=, pull it — refused: quizzes had no single-item pull, and =org-canvas-pull-quizzes= rewrites every quiz in the file, which is not what you run over a file carrying hand comments and other quizzes with edits not yet pushed. What was left was writing the heading and every question drawer by hand from two GETs.

*The single-item pull reuses the whole-file renderers.* =org-canvas--quiz-pull-item= is the quiz's pull-item function: the properties (=org-canvas--quiz-pull-set-properties=), the description and the questions (=org-canvas--quiz-pull-emit-body=, fetching the questions itself since =GET quizzes/:id= does not carry them), and the accommodations table, in that order — the same calls the whole-file loop makes for one quiz, so the two cannot write a quiz differently. It goes through =org-canvas--conflict-pull-local= like every other single-item pull, which renames the heading, stamps =CANVAS_UPDATED_AT= and drops =PAYLOAD_HASH=. The question writers already rewrote children in place by id and appended the rest (#239), so a stub and a stale quiz are the same case. Children Canvas no longer holds are left, as the whole-file pull leaves them (Hard Rule 16). The function is registered with =org-canvas-register-pull-item-fn= only; it is not handed to =org-canvas-define-sync=, so the conflict prompt still offers no pull for a quiz, since a pull in the middle of a quiz push would rewrite the questions the push is about to reconcile.

*=:pull-whole-entry= on the feature registry says what the other two verbs need to know.* A feature whose pull-item function writes a whole level-1 entry, children included, from the remote item alone can do three things the others cannot, and quizzes declare it. =org-canvas-pull-at-point= climbs from a question to its quiz before reading the id, since a question's =CANVAS_ID= is not a quiz's. The drift report's =p= on an EXTRA row writes the item into a new heading (=org-canvas--pull-new-heading=: =org-canvas--pull-upsert-heading= appends it, or reuses a level-1 heading that already claims the id, the id is stamped, then the same single-item pull), where before =p= answered only CHANGED rows; a module item's EXTRA (it carries =:module-id=) is refused, since it belongs under its module. And =org-canvas-adopt-at-point= fills the stub it adopts. Other features stay out until their pull-item function is checked against a bare stub: an assignment's writes properties and a body, but a file heading is a link inside a folder tree, and a module's items live under it.

*Adopt fills only a stub.* Adoption stamps an id and leaves the content to the next sync to verify (#101). For a heading written to claim a web-UI quiz — a title, maybe a drawer — that sync would push the stub's emptiness over the quiz: an empty description, default settings. So a heading with nothing under its drawer, of a feature that pulls whole entries, is pulled after it is stamped; a heading with text or questions of its own is a create that lost its stamp, whose content is the intent, and is only stamped, as before. No prompt: the test is whether there is anything local to lose, and it answers the same in batch.

*A description kept inline stays inline.* =org-canvas--quiz-parse-body-text= reads a =** Description= child or, failing one, the text between the drawer and the first question; hand-written files, the demo course's among them, use the second. The pull used to add a =** Description= child regardless, which then shadowed the stale inline text on every later push. =org-canvas--quiz-pull-emit-body= now rewrites the inline text in place when the quiz holds some and no Description child, keeping the accommodations table that shares the region, and uses the Description child otherwise. The whole-file pull takes the same path.

*A name no question can be told apart by is numbered.* Every question of a survey built in the web UI comes back with =question_name: "Question"=. The pull matches children by =CANVAS_ID= first, so six headings of one name would not have been merged, but they read as one question six times and the unstamped-by-title fallback of =org-canvas--pull-find-child= could take the wrong one. =org-canvas--quiz-pull-name-questions= renames a question whose name is blank, or shared with another question of the same quiz, after its place in Canvas's order (=Question 4=, =Dup 5=); a unique name is kept. The heading is the question's name on push, so the next push sends the numbered names back — a visible, harmless rename, and the only way the file and Canvas agree on a name afterwards.

* A Question Pulls in the Format Its Push Reads (issue #407)

The pull wrote every question type as the checklist the push reads for a multiple-choice question. For a matching question Canvas returns each pair on the answer (=left=, =right=, =match_id=) and the distractors as the extra entries of the question's =matches= array; the pull kept only =text=, the left side, so a pulled matching question was three =- [ ]= lines with no right sides and no distractors, and the push's matching parser skips checkbox lines, so a re-push created the question with no answers at all. All 21 matching questions of a pulled course had that shape, and =org-canvas-validate= had nothing to say. The same generic checklist stood for a numerical answer (whose =text= is empty, so the line was =- [X]=) and for a blanks or dropdowns question (its blank ids dropped, so the nested parser found nothing).

*=org-canvas--quiz-insert-answers= dispatches on the question type and writes what the parser of that type reads.* A matching question's pairs as =- left = right=, then the distractors bare: the =matches= entries no answer's =match_id= names. A numerical answer as =- [X] 42= or =- [X] [1, 10]=; an exact answer with a margin becomes the range it accepts, which grades the same, and a precision answer its approximate value with a warning in the log, since the push has no spelling for either. Canvas can hold several accepted numerical answers, the pull keeps them all and the push reads the first, as before. A blanks or dropdowns question is grouped under its blank ids in the order Canvas first names them. Every other type stays a checklist, checked where the weight is positive. The question alist is now passed in for its type and its =matches=; a call without it writes the checklist, so nothing else changed. The round-trip specs pull a question through =org-canvas--quiz-pull-insert-question= and parse the heading back through =org-canvas--question-parse-entry=, which is the check the issue asked for.

*A distractor is a field on the question, not an answer.* The push sent a =- text= line as an answer with =answer_match_left= alone, which Canvas takes as a pair whose right side is empty. Canvas's API carries distractors as =matching_answer_incorrect_matches=, one string, newline-delimited, seeded into every dropdown beside the right sides (the =Answer= schema of =canvas-openapi3.yaml=). =org-canvas--question-build-matching-answers= now returns the pairs alone, =org-canvas--question-matching-distractors= the bare lines, and the payload builder joins them onto the question when there are any. Without this the pull fix would have turned dropped distractors into empty pairs.

Since #295 a classic quiz whose description is written directly under its heading keeps it there on a pull. But the accommodations writer (#230) still put its =#+NAME: accommodations= table straight after the property drawer, so a pull that found extensions left the table /above/ the rewritten description: =org-canvas--quiz-pull-replace-inline-description= wrote text then table, and =org-canvas--accommodation-write-table= deleted the table and wrote it back at =org-end-of-meta-data=. * A New Quiz Pulls Whole Through a Pull-Only Entry (issue #297)

The same shape now serves them: =org-canvas--new-quiz-pull-item= writes the properties (=org-canvas--new-quiz-pull-set-properties=) and the items (=org-canvas--new-quiz-pull-items=, which fetches them) -- the whole-file pull's own writers, so the two cannot write a quiz differently -- through =org-canvas--conflict-pull-local=, and declares =:pull-whole-entry=. Pull-at-point climbs from an item to its quiz, and adopt-at-point fills a stub it adopts, exactly as for a classic quiz. The quiz's instructions were not written at first, because the whole-file pull did not write them either; #309 added them to both paths (below).

* A New Quiz Pull Writes Its Instructions Where the Push Reads Them (issue #309)

Neither New Quiz pull wrote the quiz's =instructions=, so pull-at-point on a heading with local text left stale instructions in place and the file never showed what Canvas held.

*The quiz's own text is the instructions, and a pull replaces exactly that.* The push reads the text between the heading's drawer and its first item (=org-canvas--new-quiz-parse-body-text=) and sends all of it, HTML-exported, as =instructions=; there is no =** Description= child as for a classic quiz, and nothing else in that text is read by any sync. =org-canvas--new-quiz-pull-instructions= replaces the same region -- bounded by =org-canvas--pull-entry-text-bounds=, moved to core from the classic quiz's inline-description writer (#295), which it served already -- with the reply's HTML through =org-canvas--html-to-org-with-rewrite=, so a heading in the instructions becomes a =#+begin_hN= block (Hard Rule 22) and a Canvas file URL a local link. The items below it are not touched, and a re-pull of the same instructions is a no-op. Replacing rather than inserting beside is what keeps the text from being duplicated or shadowed: two copies would both be pushed. A named block written in that text by hand is instructions like the rest of it -- the push sends it -- so it is replaced by what Canvas holds, not kept beside it. Empty or null instructions empty the text, matching a push, which sends none from an empty heading; a reply without the field leaves the text alone, since a missing key says nothing about Canvas. Both paths now call one writer, =org-canvas--new-quiz-pull-entry= (properties, instructions, items).

*A round trip is a fixed point.* A spec pulls instructions carrying a heading, a paragraph and a list, pushes the heading's parse into a payload, and pulls that payload's =instructions= back: the file is unchanged, and the body the push read is the text the pull wrote. New Quizzes are still not in the drift report (#297), so there is no body comparison to join yet.

*Adoption prefers =assignment_id=.* =org-canvas--adopt-stamp= read =id= (or =url= for pages) regardless of feature. The rest of the New Quizzes module reads =assignment_id= first and =id= only as a fallback (=org-canvas--new-quiz-remote-id=), and the stamp is =CANVAS_ASSIGNMENT_ID=, so adoption was the one place trusting that the quiz service's =id= is the assignment id -- believed, not verified on a live course. A feature's =:id-field= may now be a list of fields tried in order (=org-canvas--item-id-value=), which adopt-at-point passes to the stamp and uses for its claimed-id check and its candidate list; the New Quizzes pull entry declares =(assignment_id id)=. Every other feature's =:id-field= already named the field the stamp read, so nothing else changes. Whether the two ids ever differ is still open; if they do, this reads the right one.

* A Survey's Results Are Its Answers, Not a Score (issue #347)

=org-canvas-pull-quiz-results= kept only published quizzes with an =assignment_id=, and an ungraded survey has none, so a survey's answers -- the reason to run one -- never reached =quiz-results.org=, and the closing line ("1 quizzes, 1 with attempts") gave no sign anything was left out. Canvas serves a survey's statistics like any quiz's.

*Which quizzes get a heading.* =org-canvas--quiz-results-skip-reason= decides: an unpublished quiz is left out (=unpublished=), a survey -- =quiz_type= =survey= or =graded_survey= -- is kept with or without an assignment, and any other quiz without one is left out (=no-assignment=; in practice a practice quiz, whose scores go nowhere). Practice quizzes stay out because nothing asked for them and their analysis is the graded kind's with no grade behind it; widening to them is one line when it bites. =org-canvas--quiz-results-fetch-quizzes= now returns every classic quiz, and =org-canvas--quiz-results-partition= splits them into the kept ones and a count per reason.

*What a survey's heading leaves out.* Canvas marks one option of every survey question "correct" and scores against it, so Correct, Difficulty and Discrimination are computed but mean nothing; the table drops the three columns. Responses, the one column that is the answer, names each answer by its text with its count (=Strongly agree 33; Agree 27=, from =question_statistics[].answers[].text=), since "33*, 27, 17" by position says nothing when there is no right answer to star. Semicolons part the answers because an answer's text may hold a comma; an answer with no text is =#N= by position. The drawer drops =MEAN=, =HIGH=, =LOW= and =STDEV=; =STUDENTS=, =DURATION= and =GENERATED_AT= stay.

*A graded survey is treated as a survey.* It has points and an assignment, but Canvas awards them for completing it, whatever was answered: every taker's score is the same, so the score spread only repeats the points possible, and the per-question scoring rests on the same arbitrary "correct" option as an ungraded survey's. Rendering it as a graded quiz would put numbers in the file that look like an item analysis and are not one. The one fact its score carries, who took it, is =STUDENTS= here and the gradebook per student. A graded survey was already pulled before this change (it has an assignment); only its rendering changes.

*The closing line counts what it left out.* "Quiz results pull complete: 3 quizzes, 2 with attempts; skipped 4 (2 unpublished, 1 without an assignment, 1 statistics refused)", the statistics Canvas refused (#171's per-quiz warning) counted in the same place. A pull that writes nothing says the same after the empty-file note; a pull that skipped nothing keeps the old line.

*Nothing else keys the file by =assignment_id=.* Each heading carries =QUIZ_ID=, the quiz's own id; the title links to the =quizzes.org= heading whose =CANVAS_ID= is that quiz id; and the file is derived, rewritten whole by every pull, so there is no stamp, refresh or upsert that could miss a quiz without an assignment. =org-canvas-pull-quiz-submissions= reads =quizzes/:id/submissions= by quiz id and never filtered on an assignment.

* A New Quiz Item Is Pushed Only as a Type It Can Build (issues #337, #340)

An item's =TYPE= used to pass through =org-canvas--validate-property=, which logs a warning and falls back to =choice= for a value outside the valid list. A typo such as =mutliple-choice= therefore pushed a choice item with no answers, validation's error notwithstanding, and =fill-in-the-blank= and =hot-spot= were in the valid list with nothing behind them: fill-in-the-blank had no slug or answer parser at all, and hot-spot pushed its prompt with =scoring_algorithm= "None" and no regions, while the manual's table promised "Coordinate data (advanced)".

*A type the push cannot build fails its item.* =org-canvas--new-quiz-item-check-supported= replaced the fallback: no =TYPE= is still a =choice= item, a type in =org-canvas--new-quiz-unsupported-types= signals =org-canvas-validation-error= with its own reason (=fill-in-the-blank= names =short-answer=, #337; =hot-spot= says to edit the item in Canvas, #340), and any other value outside =org-canvas--valid-new-quiz-types= signals naming the valid ones. The item loop, =org-canvas--sync-new-quiz-items=, already catches an error per item, so the item is counted failed with one logged line and the rest of the quiz's items still sync. Nothing is sent for a refused item; a stamped one keeps what Canvas holds.

*Fill-in-the-blank is invalid; hot-spot is pull-only.* The two differ in whether a pull can write them. No Canvas slug maps back to =fill-in-the-blank= (a =rich-fill-blank= item pulls as =short-answer=), so it left the valid list and validation calls it an error. A hot-spot item made in Canvas does pull as =TYPE: hot-spot=, and an error on every such heading would be the #167 mistake again, so the value moved to =org-canvas--new-quiz-pull-only-types=, which the registry declares as the property's =:read-only-values=: the enum check accepts it, the generated Property Reference lists it as Canvas's to set, and =org-canvas--validate-new-quiz-item-type= (the items' =:structural-fn=) adds a push-only warning that the item is not pushed. Unlike assignments' =online_quiz=, an update is refused as well as a create: sending the prompt alone would strip the regions Canvas holds. The pull writes a hot-spot item's prompt as its heading, as for every type, and nothing else: the Org file never holds the regions, which is why a push has nothing to send. Hot-spot also left =org-canvas--new-quiz-prompt-only-types=, since how its prompt ends is a question for when it can be pushed.

*Implementing hot-spot needs a live probe.* The regions live in the item's =interaction_data= and =scoring_data=, whose shape for a hot-spot item has not been observed: nothing in the OpenAPI spec or the contract fixtures describes it. Building it means creating a hot-spot item in the web interface, reading it back from =/api/quiz/v1/courses/:id/quizzes/:quiz_id/items=, and deciding an Org form for the image and its regions; until then a guess would push items Canvas either rejects or scores wrongly. The read half of that probe was done on 2026-09-25 and #365 acted on it (below); the image upload is still unprobed, so the push still refuses.

* A Hot-Spot Item's Regions Are Pulled as Canvas-Owned Properties (issue #365)

After #340 a pulled hot-spot heading held its prompt and nothing else, so the file was no record of which region scores, and the drift report had only the prompt to compare. The live capture in #340 gave the shape: =interaction_data= holds =image_url= (a quiz-service S3 address under =item_media/=) and =hotspots_count=; =scoring_algorithm= is ="HotSpot"=; =scoring_data.value= is a list of regions, each an =id=, a =type= (=square= observed) and =coordinates=, a list of ={x, y}= fractions of the image.

*Two properties, not a block.* The pull writes =HOTSPOTS= (=square 0.3156,0.1956 0.7407,0.8362=, regions joined by =; =) and =HOTSPOTS_COUNT=, registered on ="new-quiz-items"= with =:canvas-owned t= and =:pull-only t=. A read-only block under the heading was the other candidate, and #340's comment suggested a drawer; both lose to properties on the layout #333 settled. The text under an item heading is its prompt, up to the answer list, and a hot-spot item's prompt ends where any other type's does, so a block would sit inside the prompt region: the push (were it ever allowed) would send it as =item_body=, the drift report's body comparison would read it as prompt text, and the pull that rewrites the prompt region would have to rewrite the block with it. A property sits in the drawer, which the prompt never reaches, and the registry already gives a Canvas-owned property everything the issue asked for: the drift report compares it even on a silent heading and reads the nested value through a =:remote-fn= (Hard Rule 18), the push echo check and every payload leave it out, validation warns only when it is typed on a heading no sync has stamped, and the generated Property Reference marks it Canvas's to set. That validation check (=org-canvas--validate-check-canvas-owned=) knew only =CANVAS_ID= and =CANVAS_URL= as stamps, and would have warned on every pulled item; it now accepts any id stamp a delete clears (=org-canvas--delete-id-property-names=), =CANVAS_ITEM_ID= among them. One line per item is compact enough: a region is a shape and two to a handful of points.

*The spelling is canonical, so equality is string equality.* =org-canvas--new-quiz-hotspot-format= writes each coordinate rounded to four places with trailing zeros dropped (=org-canvas--new-quiz-hotspot-decimals=; the web editor stored four), in Canvas's region order, without the region ids (ordinals that name nothing in the file). The =:remote-fn= spells the reply the same way, so a coordinate that comes back as =0.31560000000004= compares equal to the file's =0.3156=, and a region moved in the web UI is a CHANGED row naming both spellings. A hand-edited spelling of the same regions (other spacing, extra zeros) would read as drift; the property is Canvas's, and a pull puts it back.

*Compared only where the reply can say.* Each property's =:compare-p= (=org-canvas--new-quiz-item-carries=) holds only for a hot-spot item whose reply carries =scoring_data= or =interaction_data=, the #313 reasoning: a reply of another shape says nothing about the regions and must not read as their removal. For the same reason the pull leaves a property alone when the reply lacks its field. A heading pulled before #365 reads CHANGED ("(unset)" against the regions) until its next pull, which is what a Canvas-owned property is for.

*The image address is not stored.* =image_url= points into the quiz service's media store; it may be signed or short-lived, it is not something a person can act on from the file, and it could leak through a shared course repository. Only its consequences (the regions and their count) are recorded. When the upload flow is probed and hot-spot becomes pushable, the image will need an Org form of its own (a local file, as page images are) rather than this URL.

*Oval and polygon are written, unverified.* Only =square= was observed. The encoding is generic, a shape name then one =x,y= per coordinate the reply holds, so an =oval= (presumably its bounding box) and a =polygon= (its vertices) are written by the same rule; if either turns out to carry its geometry under other keys, its line would show the shape name alone, which the next probe would catch.

*The scoring algorithm is corrected.* =org-canvas--new-quiz-scoring-algorithms= mapped hot-spot to ="None"=; Canvas says ="HotSpot"=. Nothing sends it while the push refuses the type, but the table now agrees with Canvas for when it does.

* New Quizzes Join the Drift Report Through Their Pull-Only Entry (issue #313)

New Quizzes had no feature-registry entry -- their API is the separate quiz service, and #292 and #297 kept them out so the drift report, the orphan scan and prune would not list them at the course API's endpoint -- so nothing reported a New Quiz built in the web UI (no EXTRA row, and so no =p= to pull it, #295's verb), and nothing compared a New Quiz's settings or the instructions #309 taught the pull to write.

*The pull-only entry opts in; the registry stays as it was.* =org-canvas-register-pull-feature= accepts =:drift-report=, and the New Quizzes entry declares it. =org-canvas--diff-features= is the feature registry followed by every pull-only entry that declares it, and =org-canvas--diff-collect-results= walks that list, so the quizzes go through the same =org-canvas--diff-feature= as everything else: listed through the entry's =:list-url-fn= (=api/quiz/v1/courses/:id/quizzes=), paired on =CANVAS_ASSIGNMENT_ID=, with CHANGED, MISSING, EXTRA, UNCLAIMED and PENDING rows, acknowledgments and exclusion by name. No second drift pass was written: the entry already carried everything the pass needs, and the only thing the shared code lacked was an =:id-field= that is a list, =(assignment_id id)= since #309, which =org-canvas--diff-remote-index= and =org-canvas--diff-unclaimed= now read through =org-canvas--item-id-value=. The orphan scan and prune read only =org-canvas--feature-registry=, so they still never see a New Quiz (Hard Rule 13's resolvers are what the report calls). The row verbs look a row's feature up through =org-canvas--diff-find-feature=, which knows the entry too: =p= on an EXTRA row reaches =org-canvas--pull-new-heading= and the #297 single-item pull, =k= and =org-canvas-diff-delete-rows= (#345) read and delete at the entry's =:item-url-fn= (the quiz service, as =org-canvas-delete-all-new-quizzes= does), refusing a quiz with a submission or score through the assignment's check, since the row's id is the assignment's, and =b=/=B= assemble the assignment pages #292 registered for the file (=org-canvas--diff-web-entry=), since the quiz service sends no =html_url=. =RET= on an EXTRA row now falls back to that assembled page as well, for every feature, rather than refusing a row whose reply carried no address.

*The instructions are the body.* The New Quizzes property registration names =:body-api-key "instructions"= and =:body-fn org-canvas--new-quiz-body-html=, which exports the text above the first item exactly as =org-canvas--new-quiz-parse-entry= does, so the report compares what a push would send, as text (#83). #309 made a pull of that text a fixed point, so a pull clears the row it answers.

*A setting is compared only where the reply carries it.* At #313 the push sent =time_limit=, =shuffle_answers=, =one_at_a_time=, =allowed_attempts= and =scoring_policy= at the top level of the quiz and the pull read them there, a shape no live reply had confirmed, so each spec declared =:compare-p= from =org-canvas--new-quiz-remote-carries=: compared when the reply held the key the push and pull used, silent when it did not (Hard Rule 18). #321's probe showed that key is never there; the settings now read from =quiz_settings=, compared wherever the reply carries that object (below).

*A New Quiz is not also an Assignments EXTRA.* Every New Quiz is an assignment, the assignments list holds them all, and =assignments.org= claims none, so each one -- synced or not -- was already an EXTRA row under Assignments. With a section of their own that is the same object reported twice. =org-canvas--diff-apply-new-quiz-assignments= runs after the other post passes and takes out of the Assignments extras every id the New Quizzes list holds, counting them as =:covered=, which the footer's "Not checked" line names beside the =:skip-fn= counts. It acts only when both lists were read; with New Quizzes excluded or failing, the rows stay as before. It is a report-only move, and it agrees with what prune and the orphan scan do since #319: they leave a New Quiz's assignment alone (=org-canvas--assignment-owned-p=, declared as the assignments feature's =:delete-skip-fn=, not its =:skip-fn=, so the drift report still reads every assignment). The report hides it only where the New Quizzes section reports the quiz instead, so a New Quiz is never an EXTRA offered for deletion twice; with that section excluded or unread, it stays an Assignments EXTRA, as #319 intends, and =k= on it names the New Quiz that owns it, as =org-canvas-diff-delete-rows= refuses it (#366, in the #345 entry).

*Items are not compared yet.* The items under a quiz need a request per quiz and their own pairing (=CANVAS_ITEM_ID=, a title read from the item body), and their rows would need verbs that know the parent quiz, as module items needed =:module-id=. Left for a follow-up, which #322 is (below). Read-only throughout (Hard Rule 19): one list request, and the local body exports offline.

* New Quiz Settings Live Under quiz_settings (issue #321)

The push sent a New Quiz's five settings at the top level of =quiz=, and the pull read them from there. A live probe on 2026-09-25 (course 297530, build 750dc5e, an unpublished probe quiz) settled the shape. A POST of exactly what =org-canvas--new-quiz-build-payload= built -- =time_limit= 17, =shuffle_answers= true, =one_at_a_time= true, =allowed_attempts= 3, =scoring_policy= "keep_highest" -- returned 200 with every setting at its default (=has_time_limit= false, =session_time_limit_in_seconds= 0, =shuffle_answers= false, =one_at_a_time_type= "none", =multiple_attempts= null), and none of the five keys appears at the top level of any reply. A PATCH carrying only =quiz.quiz_settings= came back exactly as sent. So every push of a setting had silently done nothing, and every pull wrote nothing.

*The mapping.* Each setting now travels under =quiz_settings=:

| Org property | =quiz_settings= field | Verified live |
|--------------+-----------------------+---------------|
| =TIME_LIMIT= (minutes) | =has_time_limit= and =session_time_limit_in_seconds= (minutes × 60; 0 or less is =false= and 0) | yes (=true=, 1380) |
| =SHUFFLE_ANSWERS= | =shuffle_answers= | yes (=true=) |
| =ONE_AT_A_TIME= | =one_at_a_time_type=: =question= for true, =none= for false | yes (=question=; =none= is the default) |
| =ALLOWED_ATTEMPTS= | =multiple_attempts=: =multiple_attempts_enabled=, =attempt_limit=, =max_attempts= | N > 1 only (=true=, =true=, 2) |
| =SCORING_POLICY= | =multiple_attempts.score_to_keep=: =keep_highest= → =highest=, =keep_latest= → =latest=, =keep_average= → =average= | =highest= only |

=ALLOWED_ATTEMPTS= of N > 1 sends enabled, limited, N. 1 (and 0, which Canvas has no use for) sends enabled =false=, =attempt_limit= =true=, =max_attempts= 1: a single attempt is multiple attempts off, which is what a fresh quiz reported. -1 (any negative) is unlimited: enabled, =attempt_limit= =false=, no =max_attempts=, the convention a classic quiz's =allowed_attempts= uses. An empty property is unset, as for every other property. =SCORING_POLICY= alone sends a =multiple_attempts= object holding only =score_to_keep=. Unverified: the single-attempt and unlimited shapes, =latest= and =average=, and whether a partial =multiple_attempts= object leaves the fields it omits alone; coverage.org, "Watch on First Live Use", lists them.

*Only what the heading sets is sent.* =org-canvas--new-quiz-settings-payload= puts a setting in only when its property is there, and leaves =quiz_settings= out of the payload when none is, so an unset property never resets Canvas. The two booleans now tell =false= from silence (=org-canvas--new-quiz-setting-boolean=): =SHUFFLE_ANSWERS: false= sends =false=, where before it sent nothing and could not turn a setting off. The payload hash changes for any quiz that sets one of these, so such a quiz pushes once more on its next sync, which is what its earlier pushes should have done.

*The pull and the drift report read the same paths.* Each spec declares a =:remote-fn= reading =quiz_settings=: seconds back to minutes (a whole number when it divides evenly), =one_at_a_time_type= back to a boolean, =multiple_attempts= back to 1, N or -1, and =score_to_keep= back to its =SCORING_POLICY= spelling (an unknown value passes through as Canvas wrote it, for the validator to name). =ALLOWED_ATTEMPTS= declares =:default 1=, so a pull of a single-attempt quiz writes nothing and a re-pull deletes a stale count (the #320 rule, through =org-canvas--pull-apply-spec=); a quiz with no time limit reads 0, the number type's default, and is deleted likewise; the booleans keep #323's registry-keyed defaults. The generated Property Reference had printed any declared default as "true" or "false"; a number's now prints as its value. Where =org-canvas--new-quiz-remote-carries= used to guard the comparison, each spec now declares =:remote-known-p= and =:compare-p= from =quiz_settings= itself: a reply that carries the object is compared and pulled for all five settings, and one without it (or with it null) leaves the properties alone and reports nothing, the #216 rule. =org-canvas--new-quiz-remote-carries= remains for the items' =POINTS=.

*No contract test covers it.* The OpenAPI spec (=canvas-openapi3.yaml=) documents only the course API; the quiz service at =/api/quiz/v1/= is not in it, and the contract extractor lists New Quizzes among the modules it leaves out. The payload specs in =test/org-canvas-new-quizzes-test.el= pin the nested shape instead.

* New Quiz Items in the Drift Report, Paired as the Sync Adopts Them (issue #322)

#313 compared a New Quiz's settings and instructions and stopped there, so an item edited, added or deleted in the web UI left its quiz reading clean. The item pass is the module items' child pass (#177) under a quiz: =org-canvas--diff-children-fns= names =org-canvas--diff-new-quiz-items= for New Quizzes, and its result reports right after them as a section of its own, *New Quiz Items*.

*One request per quiz Canvas still lists.* Only a quiz heading whose =CANVAS_ASSIGNMENT_ID= the quiz list holds is looked into, through =org-canvas--new-quiz-api-endpoint= (=quizzes/:id/items=), as the sync's own item loop does. A reply that is not a list of item objects signals, and the section reads "could not check": a misread list is unknown, never an empty quiz (Hard Rule 16), which would otherwise call every item heading MISSING. The pass fails whole, as the module items' does, rather than quiz by quiz; a partial section would need a way to say which quizzes went unchecked, and one failing read in a course is rare enough to rerun.

*Claims and pairing stay inside the quiz.* An item belongs to one quiz, and the sync PATCHes it at =quizzes/:quiz/items/:id=, so a stamped heading claims only an item of its own quiz; an id it names that its quiz does not hold is MISSING. An unstamped heading is paired with an unclaimed item of its quiz by =org-canvas--new-quiz-item-twin-p=, the predicate the sync adopts a twin with (#179): the item's first paragraph is the heading's title. Headings are taken in file order and each pairs once, as the sync adopts them. Such a pair is UNCLAIMED, with a line saying the next sync adopts it; there is no MOVED row, since the sync never adopts across quizzes. The unstamped headings left over, including those under a quiz not yet pushed, are PENDING. diff.el declares =org-canvas--new-quiz-item-twin-p=, =org-canvas--new-quiz-item-remote-title= and =org-canvas--new-quiz-api-endpoint= and never requires =org-canvas-new-quiz-items=, as #299 declared the modules.el parser.

*What is compared.* The item registration (="new-quiz-items"=) gained what the report needs: =POINTS= reads =points_possible= (=:api-key=), =TYPE= reads =entry.interaction_type_slug= mapped back to the Org spelling (=:remote-fn org-canvas--new-quiz-item-remote-type=), and each is compared only when the reply carries it (=:compare-p=), the #313 reasoning: an item reply of an unconfirmed shape must not flag every item forever (Hard Rule 18). The body is =item_body=, which the Items API nests under =entry=, so the registration names a =:body-remote-fn= (=org-canvas--new-quiz-item-remote-body=), a new optional key =org-canvas--diff-compare-body= reads through =org-canvas--diff-remote-body=; every other feature still reads its body at the top level. The local side is =org-canvas--new-quiz-item-body-html=, the heading and the prompt above the answer list exported exactly as the item parse does (=org-canvas--new-quiz-item-question-text= is now shared by both, and the prompt ends where the item's =TYPE= says, as #335 and #337 made the parse read it; a hot-spot item, which a push refuses since #340, is compared all the same, since its prompt is what a pull writes), offline, compared as text (#83). The answers live in =interaction_data=, whose choice ids every push mints afresh, so they are not compared; that is left for when it bites. =OUTCOME= is a link, never compared. No item carries a conflict baseline, so an item row is never "Canvas updated" and never adoptable (=a= refuses it before looking for a feature).

*Rows that know their quiz.* Every item row carries =:quiz-id= and =:where=, as module item rows carry =:module-id=, and =:container "quiz"=, which the row text uses ("in quiz 'Midterm'"; =org-canvas--diff-container=). A row about a heading also carries =:file=, =:line= and =:heading=, and =RET= finds it the way it finds a PENDING row: an item heading is no feature's own, and titles repeat across quizzes. =k= and =org-canvas-diff-delete-rows= read, snapshot and delete at =quizzes/:quiz/items/:id= (#345's read takes no feature's item parameters, since an item is no feature's own); =b= and =B= open the quiz's assignment page, since an item has none; =p= on a CHANGED or EXTRA item row pulls the whole quiz over its heading (=org-canvas-pull-at-point= on it, which asks first), since a New Quiz pulls whole and its item pull upserts by =CANVAS_ITEM_ID=. Acknowledgments are filed under ="new-quiz-items"=. Nothing in the pass writes (Hard Rule 19).

*An item pulls into a heading and the prompt under it (issue #333).* The item pull used to flatten the whole =item_body= into the =**= heading and write nothing under it, so a question of two paragraphs, a list or an image arrived as one long line. It now writes the layout the parse reads back: the push sends the heading as the body's first paragraph and the text between the drawer and the answer list after it, so the pull splits =item_body= after the =<p>= it opens with (=org-canvas--new-quiz-item-split-body=), writes that paragraph as the heading and the rest, through =org-canvas--html-to-org-with-rewrite=, as the prompt (Hard Rule 22 holds at that chokepoint). A body that opens with no paragraph, or with an empty one, is all heading, as every body was before; a one-paragraph item pulls exactly as it did. The prompt is one region for both sides, =org-canvas--new-quiz-item-prompt-bounds=: the parse reads it, the pull replaces it, and nothing below it is touched, so an existing heading, by =CANVAS_ITEM_ID= or unstamped by its title (#239), is renamed and rewritten in place and keeps its answer list, which the pull used to delete with the rest of the subtree and does not write. A prompt the parse would cut short -- a list, whose first line reads as the start of the answers -- is written as a =#+begin_export html= block of the reply's HTML, which the push sends as it stands. Where the prompt ends is the item's =TYPE='s, one rule for the parse and the pull (=org-canvas--new-quiz-prompt-end-regexp-for=): an ordering item's numbered line ends it as a bullet does (#335), so a numbered list in its prompt goes in the block too, and an essay or file-upload prompt ends at no line (#337), so its list is written as Org and the whole text under the heading is the prompt. Pairing follows the split: =org-canvas--new-quiz-item-remote-title= reads the same first paragraph, so the pull's title match, the sync's twin adoption and the drift report's unstamped pairing agree on what a heading names. Specs pull a two-paragraph item, push its parse, pull that back unchanged, and compare the pushed body with Canvas's as the drift report does, so a pulled item reads clean.

* The GraphQL Documents Are Checked Against the Schema (issue #269)

The GraphQL documents of the time travelled to Canvas as opaque strings — the post-policy mutations, =postAssignmentGrades=, the checkpoints query and =updateDiscussionTopic=; every document added since (#350's processor query, #351's report query, #352's reads and mutations) is held to the same check — with nothing checking that the fields, arguments and input types they name exist. The REST side has had =test/contract/= since the OpenAPI fixture: every =build-payload= is checked against the documented operation. The GraphQL side had mocks, and a mock cannot tell whether =DiscussionCheckpoints= still has a =dates= field of that shape, which is why coverage.org kept the checkpoint mutation on its watch list.

The same design, with the choices the medium forces:

- *Two sources, introspection preferred.* =instructure/canvas-lms= ships =schema.graphql=, regenerated in the commits that touch the Ruby types, and every document checks against it. But the public mirror is stale by months against the instances, so the SDL is a baseline for reading input types while writing a document, and the instance's own introspection (a POST that is a read, so it runs under =org-canvas-read-only=) is what the code actually talks to. The extractor takes either; the fixture records which, with the ref or the host. When a new document reaches types the fixture lacks and the instance is out of reach, =--supplement= adds only those types from the SDL and lists them under the provenance's =supplements=, keeping everything already there; #350 added =Assignment=, =AssignmentConnection=, =ExternalTool=, =LtiAssetProcessor= and =LtiAssetProcessorConnection= this way, so the next introspection should replace them.

For a reached object type every field is kept, with its arguments and deprecation reason, so a document edited to select a sibling field is still checked without regeneration; a type an unused field names is simply absent, and a document that reaches it fails with "is not in the fixture", the cue to regenerate.
- *The documents are read out of lisp/ by the extractor* (the =query (= / =mutation (= string literals), validated with graphql-core before anything is written, and named by symbol in the test, so the two lists cannot drift apart silently: a document changed in lisp is picked up by the next regeneration, and a new file has to be added to both.
- *No GraphQL parser in Elisp.* The documents are short and of a regular shape (most on one line, the longer reads laid out over several), so the test tokenizes and parses them itself — operation, variable definitions, selections, arguments with variables, literals, object and list values — a hundred lines that would not survive a document with fragments or directives, none of which org-canvas writes.
- *The variables side is the real payload check.* The document check proves the string; the callers are run with the sender mocked and what they hand it is checked against the input types: required keys present, a =Boolean!= from =t= or =:json-false= and never nil (nil encodes as null, which the live probe in #202 caught), an =ID!= a string, a list a vector (=json-encode= writes a Lisp list as an object), enum strings valid.
- *What it cannot say.* A feature flag does not shape the schema: =checkpoints= is in the SDL and in the introspection whether or not the account flag is on, since the flag is enforced when the field resolves. The check catches renames, removals and version lag; the first live run still answers "is the flag on".

* Post Policies Are GraphQL (issue #202)

Canvas keeps the grade post policies and the act of posting grades out of its REST API: REST reports =post_manually= on a course (with =include[]=post_manually=) and on an assignment, and can write neither; setting a policy is the =setCoursePostPolicy= and =setAssignmentPostPolicy= mutations, posting is =postAssignmentGrades=. The GraphQL endpoint takes the same bearer token, so =org-canvas--graphql-send= goes through =org-canvas-api-request= and inherits redaction, rate limiting and the read-only guard. Two rules follow. A query is a read and lifts the read-only guard for its one request (=org-canvas--graphql-query=), and refuses a document that is a mutation; a mutation goes through =org-canvas--graphql-mutate=, which keeps the guard and honours the dry run with the sentinel (Hard Rule 1). GraphQL answers 200 with an =errors= array when a field fails, so the sender turns errors into =org-canvas-api-error= naming them rather than returning a partial =data=.

An assignment's =POST_POLICY= is written by pull only when it differs from the course's (=org-canvas--assignment-remote-post-policy=, with the course policy read once and cached): Canvas reports every assignment's /effective/ policy, and stamping that on every heading would make the next push pin each assignment to an explicit policy the course setting no longer reaches. A silent heading inherits, and the drift report compares the property only where it is declared (=:compare-p=). An unrecognised value falls back to nothing, not to the first allowed value as other enums do, because a typo must not flip a gradebook's posting. The grading file records the assignment's effective policy at pull time so the push can offer to post without another request.

** A Posting Schedule Rides the Post-Policy Mutation (issue #352)

=setAssignmentPostPolicy= also takes =postGradesAt= and =postCommentsAt=, and Canvas keeps them as the assignment's =scheduledPost=, posting the hidden grades and comments by itself when each time comes. That lets a grader push a column hidden and name the release time in one sitting. An assignment heading declares it with =POST_GRADES_AT= and =POST_COMMENTS_AT=, both Org timestamps. What the schema and canvas-lms (=318f2ad0=, =app/graphql/mutations/set_assignment_post_policy.rb=, =app/models/scheduled_post.rb=) say Canvas does decided the rest. None of it has been checked against the live instance.

- *Both times, or neither.* =ScheduledPost= requires both (=DateTime!= on each field, a presence validation on each column). Canvas has no default for a missing one, so one without the other is a validate error, and the push refuses the heading before its PUT (=org-canvas--assignment-check-schedule=). It is not sent and left to fail in finalize, after the assignment has already changed.
- *Grades no earlier than comments.* The model rejects =post_grades_at < post_comments_at=. Equal times are the ordinary case: Canvas then posts both together. Validate and the push compare the parsed times, never the strings, because two offsets must not order by spelling.
- *A schedule means manual posting.* The mutation stores a schedule only when =postManually= is true, and drops the times without an error otherwise. So a heading with a schedule sends manual posting whether or not it declares =POST_POLICY=, which pins the assignment's policy. A heading with =POST_POLICY: automatic= beside a schedule is a contradiction, an error in validate and in the push.
- *Silence keeps Canvas's schedule.* When =postManually= is true and both times are blank, the mutation /deletes/ the schedule it finds. Before this change, on an instance with the feature on, every push of =POST_POLICY: manual= therefore wiped a schedule set in the web UI. A heading that says manual and names no times now sends the schedule Canvas holds (=org-canvas--assignment-schedule-held=, from the course-wide read below). A silent heading keeps its schedule, as it keeps every other field it does not mention. org-canvas never clears a schedule. That is the web UI's job, or it lapses once the times pass. When the read was refused, the push sends no times, as it did before. An instance that refuses the read will likely refuse the mutation as well.
- *The feature flag is invisible, so the reply is checked.* Canvas keeps a schedule only when the site-admin feature =scheduled_feedback_releases= is on, and ignores the times without an error when it is off. The mutation selects =postPolicy { assignment { scheduledPost { ... } } }=, and the push compares the times that come back with the times it sent, as moments. When they differ it logs one =[Verify]= warning naming both. The write still counts as a success, as #349's echo check does. Under a dry run nothing is sent and nothing is compared.

*The read.* The REST assignment has no schedule, so the pull and the drift report read it the way they read document processors (#350). One course-wide =assignmentsConnection= query per command, page by page, is keyed by assignment id and forgotten on =org-canvas--operation-start-hook=. It is a query of its own, not a field added to the processor query: a failure in one must not cost the other, and each degrades on its own warning. The paging and the refusal handling are shared (=org-canvas--assignment-graphql-read=). The properties declare =:remote-fn= with =:remote-known-p=. Canvas's schedule, or its absence, is written by a pull. A refused read leaves both properties as typed and the drift report compares neither. The report compares a property only where the heading declares it: a schedule set by hand beside a silent heading is not drift, since the push would keep it. Both times also go into the payload hash (=:hash-extra=), because they travel outside the PUT, so an edit to the schedule alone is not skipped as unchanged (the #242 lesson).

*Unverified live.* The field names come from the schema, and the contract test checks both documents against the fixture, whose =ScheduledPost= comes from the canvas-lms SDL (=318f2ad0=). Whether the flag is on at Clemson, what a refused schedule looks like in the reply, and whether =postGradesAt= comes back in UTC are all unknown until the first live push. A probe that sets a schedule on a sandbox column and reads it back settles all three.

* A Body Never Introduces a Headline (issue #175)

Pulled from Clemson CPSC 3720 F26: Canvas had 26 quizzes, =quizzes.org= had 27 level-1 entries; 55 assignments, 57 entries; three entries carried no =CANVAS_ID=. Quiz "Microservices HW Questions" (683589) had six questions on Canvas and one in the file — the other five hung under a phantom level-1 heading whose title was the quiz description's =<h2>= and whose drawer read =:CLASS: article-title=, pandoc's fingerprint. pandoc renders an HTML heading as an Org headline; inserted under an entry, that headline /ends/ the entry, and everything after it — the rest of the description, the questions — belongs to a new id-less one. A push would then CREATE the phantom as a second quiz and leave the real one short, validate would see only a heading with no id, and nothing in the log said a word.

*The invariant: a body can never introduce a heading at or above its parent's level — in practice, at any level.* =org-canvas--org-body-neutralize-headlines= enforces it at the one chokepoint every converted body passes, =org-canvas--html-to-org=, on the pandoc path and the raw-HTML fallback alike, so a test that mocks =call-process-region= exercises it and one that mocks =org-canvas--html-to-org= itself bypasses it (which is how the count guard is tested).

*The representation: an Org special block, =#+begin_hN= … =#+end_hN=, N being the HTML level.* The headline line and the drawer pandoc wrote under it (=CLASS=, =CUSTOM_ID=) become a block holding the heading text as ordinary Org markup — bold, links and all — and =org-canvas--html-heading-block-filter=, an =org-export-filter-special-block-functions= entry that =org-canvas--with-body-export-settings= installs around every Org-to-HTML export the package performs (the subtree exporter, =org-canvas--org-to-html-string= for quiz descriptions and questions), renders a one-paragraph block back as =<hN>…</hN>=. The round trip is exact in tag and text; the drift report, which compares bodies as text (#83), sees no difference. A referenced =CUSTOM_ID= survives as a =<<target>>= at the head of the block and its =[[#id]]= links become fuzzy =[[id]]= links, so a page's table of contents still resolves. Inline conversions (=org-canvas--html-to-org-inline=: table cells, answers, rubric text) drop the marker lines and keep the text. An instructor can write the block by hand to put a heading in a quiz description, which no Org headline could do.

*Rejected: demoting the headline* (pandoc's =--shift-heading-level-by=, or rewriting the stars), the fix the issue first suggested. The extractors say no. A classic quiz's description is the text from its drawer to =outline-next-heading= — any level — and its questions are its level-2 children (=org-canvas--quiz-parse-body-text=, =org-canvas--quiz-sync-children=); new quizzes read the same way (=org-canvas--new-quiz-parse-body-text=); an outcome's children at any depth are outcomes and groups. A demoted =<h2>= would either become a question on the next push or cut the description short, and there is no depth that is safe for all three. A bold paragraph loses the tag; an =#+begin_export html= block keeps it but leaves raw HTML in the file. The block keeps both.

*The guard.* A pull stamps its id property on every entry it touches, so an id-less level-1 entry that was not there before it began is one it did not mean to write. =org-canvas--pull-check-entry-count= counts them before and after (=org-canvas--pull-idless-entry-count=, one pass over the level-1 headings), logs a =[Pull]= warning naming the file, the count and the items written, and records it in the pull summary as a non-fatal error; it never prompts, so a batch pull runs on. It sits in =org-canvas-define-pull= and in the two custom loops whose bodies carry headings, quizzes and new quizzes. Comparing entries to remote items outright was rejected: local drafts, orphans of items deleted on Canvas and a skipped front page all make those differ on a healthy file.

* A Stranded Body Fragment Is Flagged and Never Created Unasked (issue #391)

#175 stopped new fragments; it could not reach the old ones. A re-pull rewrites each item's own subtree by =CANVAS_ID= and leaves the id-less sibling a pre-#175 pull stranded where it was, so on course 295790 =assignments.org= read the item, its fresh body with the heading as a =#+begin_h1= block, and then the same text again as a level-1 heading with =:CLASS: article-title= and the rest of the old body under it. *The marks.* =org-canvas--body-fragment-reason= (core-org) calls a heading a fragment when it has neither =CANVAS_ID= nor =CANVAS_URL= and either its drawer holds a property only pandoc writes — =CLASS= or a =DATA-= attribute (=org-canvas--pandoc-attribute-property-re=) — or its title, with anchors, =\ast{}= and whitespace folded, is the text of a =#+begin_hN= block between it and the nearest heading above at its level or higher: the item whose re-pulled body now carries the heading the fragment once was. *Rejected: deleting the fragment on pull*, the issue's other option. A pull that removes an id-less sibling whose title matches a block it just wrote would be right on the fragments seen so far and wrong on the first user who typed a heading with that text, and local text is never deleted for looking stale (the orphan cleanup is a separate command for that reason). The warning names the heading; the instructor folds it back into the item above.

The other side of #175. *A SubHeader opens its module.* =content_tag_redirect= knows no =ContextModuleSubHeader=, so =modules/items/ID= for a text header lands on the Modules page under "Didn't recognize the item type for this tag" (=application_controller.rb= 2583), and the API gives a SubHeader no =html_url= at all (=lib/api/v1/context_module.rb= 94). An unstamped one still refuses, and one under an unstamped module falls through to the item address.

*A percent sign is written =&#37;=.* The Files app's router decodes the path and then =generateFolderByPathUrl= runs =decodeURIComponent= on each name again (=ui/features/files_v2/utils/apiUtils.ts= 48), so a folder named =50% Rule= sent as =50%25%20Rule= reaches the second decode as a bare =%= and throws. Canvas's own folder links replace =%= with =&#37;= before encoding (=folderUtils.ts= 30) and the decode side turns it back; =org-canvas--file-folder-web-path= now does the same.

*A New Quiz's edit page is its assignment settings, not the item editor.* =assignments#edit= renders the assignment form for a =quiz_lti= assignment (points, group, dates, assign-to; the React teacher view under =assignment_edit_enhancements_teacher_view=); it redirects only classic quizzes, graded discussions and pages. The items are built from =assignments/ID=, whose =#show= launches the New Quizzes tool for an =external_tool= assignment. The source settles routing and redirects; what a page looks like on the instance, behind its feature flags, is still a browser's to see, and those checks are listed in coverage.org.

* A Published Heading No Module Holds Is a Validate Note (issue #413)

Students reach a course through its modules. A column pushed from =assignments.org= and never given a =modules.org= item is published, dated and graded, and still missing from the Modules page; before #413, validate checked only that each item's link resolved and the drift report only paired items with Canvas's, so nothing went the other way. Finding such a column took a hand script paging every module's items.

=org-canvas--validate-module-coverage= runs once per validate run, after the specs. It resolves every level-2 link in =modules.org= to a heading key (the target's truename and heading position, through =org-canvas--find-heading-in-file=, the lookup the missing-target check already uses) or, for a link straight at a file, to the file's truename. Then it reads the files =org-canvas-validate-module-coverage= names and reports once per published heading no key covers. It stays offline, and it is not push-only: the gap is in the course.

*A note, the third severity.* Every earlier finding was something going wrong: an *error* is a push that fails or sends something wrong, and a *warning* is the file or the course out of step in a way that breaks something (a past date, a stale id, a body fragment, a link that 404s for students). A heading in no module breaks nothing. The file is right and Canvas does what it says; the finding is about how a student gets around the course. Filed as warnings, the demo course's nine findings would have outnumbered its real warnings, and the warning count would stop meaning "look before you push." So =note= sits beside the other two: listed after them (=org-canvas--validate-notes-last=), counted apart in the report's last line and the echo area (the count is shown only when non-zero, so a report without notes reads as before), shown by compilation mode at info level so =next-error= still visits it, and never counted by =org-canvas-validate-batch=. Notes are listed in full rather than folded into a count line the way pending links are, because hiding them would hide exactly what this check exists to show; =NO_MODULE= quiets one. The group-weight sum stays a warning: weights off 100 inflate or deflate every grade, which is something breaking.

- *What counts as linked.* An item Canvas deleted, or any item under a module it deleted, holds nothing (=org-canvas--sync-deleted-stamp=, as #402's cross-heading checks). A link whose directory is wrong falls back to the basename beside =modules.org=, as the sync's resolver does, so validate and the sync agree on what an item points at.
- *What is left out.* Unpublished headings (a dropped column parked unpublished), the front page (Home reaches it), a hidden file, a heading Canvas deleted, and a heading marked =NO_MODULE: t=. =NO_MODULE= is one spec, =org-canvas--no-module-property-spec=, spliced into each content registry as =:local-only=, so it is validated as a boolean, documented in the Property Reference and never pulled, sent or compared.
- *Which files.* Assignments, pages, classic quizzes and discussions by default. Files are opt-in: most are images a page embeds, and a warning per image would bury the ones that matter. With =org-canvas-files-file= added, only file headings (those that are links) are read, and a direct path link and a =files.org= heading link both count. New Quizzes are left out, since a =modules.org= link to =new-quizzes.org= does not resolve as an assignment item today, so the warning could not be fixed. Announcements are left out too.
- *When it is silent.* When =modules.org= is missing or none of its items links to anything, since such a course does not navigate by modules.

The live-side counterpart the issue offered (an assignment Canvas holds that no Canvas module item points to, for a column made in the web UI) is left for the drift report to take up if it bites. A web-UI column appears there as EXTRA already, and once pulled, this check covers it.

* A Column's Grading File Is Found by Its Id (issue #431)

A grading file was found by the column's current name (=org-canvas--submissions-file-path=), so a renamed column orphaned its file. On 2026-09-30 =Attendance 03= became =Attendance 03: Wed Sep 30= after 102 scores had been typed into =Attendance_03.org= and not pushed. The grading queue then called the column =pull= with no Pulled date, and the pull it advised would have started =Attendance_03__Wed_Sep_30.org= empty beside the old file; =Attendance 01= already had both files side by side. Columns are renamed routinely (a date added after class, a title fixed), and nothing said the scores were stranded. The push already found its file by the header's =CANVAS_ASSIGNMENT_ID=; nothing else did.

- *Id first, name second, in one place.* =org-canvas--submissions-locate-file= answers the file whose header names the id, whatever it is called, else the name's path. A file without the id line is still found by name. Every column-to-file mapping goes through it: the pull (=org-canvas--submissions-grading-buffer=), the queue (=org-canvas--submissions-status-pulled-at=), and =org-canvas--submissions-grading-file-path=, which open, refresh-file, the section-window scoring and the push target all use, and which now takes an id as the push target already did. The quiz-attempts and peer-review tables keep their name-based paths: they hold nothing typed, and every pull rewrites them whole.
- *The pull renames; nothing else does.* Only the pull knows the column's current name, from Canvas. =org-canvas--submissions-grading-file-for= renames a file it found under an old name to the new one, moves =files/<old>/= to =files/<new>/= (downloads are laid out by the sanitised assignment name, =org-canvas--submissions-attachment-dir=), rewrites the =[[file:files/<old>/= links and the =#+TITLE= and =CANVAS_ASSIGNMENT_NAME= lines, saves, and logs one info line. Open by id visits the file under its old name, since no new name is known offline. The queue is read-only and renames nothing.
- *A visited buffer follows; a modified one stops the rename.* A buffer visiting the old file takes the new name with =set-visited-file-name= (along with the file, so it is not marked modified). One holding unsaved changes is a =user-error=: renaming under it would leave edits a later save could write back under the old name, or a batch Emacs a question it cannot answer. Saving is the grader's call. A file already holding the new name is likewise refused rather than overwritten, and an attachment directory already under the new name is left where it is, with a warning, rather than merged.
- *Two files claiming one id are named, never chosen.* Which one holds the scores is not knowable from headers: the older may hold typed scores and the newer the latest pull. The pull and open stop with a =user-error= naming both, so no third file is written; the queue names both above its table (=:duplicates= on the row) and shows no Pulled date for the column.
- *The directory is read once per queue.* Each lookup reads the first 4096 bytes of every =.org= file in the submissions directory, lock files (=.#NAME.org=, dangling symlinks) left out. The grading queue looks up every column, so =org-canvas-submissions-status-rows= binds =org-canvas--submissions-id-index= to an index built once; commands that rename read afresh, since an index would go stale under them.

* A Bump at a Scheduled Date Is Not a Conflict (issue #453)

An assignment pushed at 13:04:21Z with =unlock_at= 14:10:00Z had its =updated_at= moved to 14:10:05Z by Canvas, five seconds after it unlocked, with nothing edited. The next push of the heading by name (an edited description, =org-canvas-conflict-strategy= nil) stopped at a conflict, and only ='push= got it through. A full read showed every field the heading sends equal to the heading. The issue names =lock_at= and an override's dates as the same. It matters most on the day a column runs: a column that opens at the start of class and gets a prompt fix during that class always hits it.

*Explained by the date, not by the fields.* The issue offered #410's idea first: compare the payload the push would send with the live object, and restamp when every field agrees. That works for #410 because there the heading's hash matched, so the payload was what had last been sent, and any field that differed could only be Canvas's. Here the heading has been edited, which is why it is being pushed, so the payload differs from the live object in exactly the fields the user changed, and a field that differs is either the user's edit or a web edit, with nothing to tell them apart: =PAYLOAD_HASH= is one hash of the whole payload, not a per-field record of what was last sent. A comparison that agreed would mean the push had nothing to send. So the check asks the other question the issue offered: did a date at which Canvas touches the item on its own pass since the baseline, with the remote timestamp a few seconds after it? =org-canvas--conflict-scheduled-bump= answers that from a list of (LABEL . ISO8601) dates. A date explains the bump when it lies after the baseline and the remote timestamp sits at it or no more than =org-canvas--scheduled-bump-window= (60 seconds, to cover a busy job queue) after it. A date that had passed before the baseline explains nothing: the bump it caused is already behind the stamp.

*The feature names its dates.* The registry takes =:scheduled-dates-fn=, a function of the item as read that answers those dates (=org-canvas--feature-scheduled-dates-fn=). =org-canvas--push-check-and-resolve-conflict= finds it through the run context's feature (=org-canvas--sync-item-scheduled-fn=) and hands it to =org-canvas--conflict-check=, which calls it only once the remote timestamp is newer than the baseline. Assignments declare =org-canvas--assignment-scheduled-dates=: =unlock_at= and =lock_at= from the read, then each override's, from =assignments/ID/overrides=, since the read (=override_assignment_dates=false=, #273) carries none. That GET is spent on the conflict path alone. A failed read of the dates is warned about and leaves the conflict standing: a check that could not explain the bump must not let the push past it. An explained bump logs one info line naming the date, and the push goes ahead; finalize stamps =CANVAS_UPDATED_AT= from the PUT, as for any push. Only assignments declare dates, since only they were seen to bump, and =due_at= is left out, since nothing showed Canvas touching an assignment when it falls due. Another feature seen doing the same declares its own function.

*What it costs.* The timestamp is the only evidence the check has, and Canvas's bump overwrites it, so a web edit made between the baseline and the scheduled date is hidden by the later bump, and one made inside the window is taken for it. Either is then pushed over. The hole is open only when a scheduled date passed since the heading was last pushed, which is the case the issue is about, and the drift report still shows a field that differs before the push. The dry run's "would conflict" prediction (#84) reads the list snapshot, which holds timestamps alone, so it still predicts a conflict here: it errs toward a prompt the real push will not show. A heading not pushed since the bump is still listed by =org-canvas-diff= as CHANGED with no compared property differing, which =org-canvas-diff-adopt-stamp= (#257) already answers.
