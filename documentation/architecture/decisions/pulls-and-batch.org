* Assignment Reads Ask for the Assignment's Own Dates (issue #273)

Canvas applies an assignment's overrides to the =due_at=, =lock_at= and =unlock_at= it returns from the index and the show, and for a teacher, who can see every override, it applies the most lenient one. The first extension written from a heading's overrides table (#224 worked as designed) therefore turned the assignment's own dates into the one student's on every read the package made: =org-canvas-diff= called =R4: Agency= CHANGED with =DUE_AT= four days later than the file, =org-canvas-pull-at-point= or the conflict prompt's pull would have written the extension into the heading as the base due date, and the next push would have sent it to everyone. The full pull was worse still: =org-canvas--override-emit-table= drops a row whose dates match the parent's, so with the substituted dates the extension row read as redundant and was dropped, and the next =org-canvas-sync-overrides= would have deleted the override for not being in the table. Probed 2026-09-14 on course 297530: =GET assignments/2563804= answered =due 2026-09-19T03:59:00Z=, with =override_assignment_dates=false= =2026-09-15T03:59:00Z=, the date in the file.

Every read of an assignment now carries =override_assignment_dates=false=, spelled once as =org-canvas--assignment-read-params= and declared three times: =:list-params= on the feature registration (the drift report, the sync's remote snapshot, adopt and the orphan scan list through =org-canvas--feature-list-params=), =:item-params=, a new registry key resolved by =org-canvas--feature-item-params= that =org-canvas-pull-at-point= and the conflict check read one item with (the check's response is what the pull option writes), and =:params= on =org-canvas-define-pull=. The overrides table was never affected: it reads =assignments/:id/overrides=, which returns the overrides themselves. =all_dates= is not asked for, since Org holds the base dates and the table the overrides. Classic quizzes are deliberately left alone: their serializer substitutes override dates only for a reader who has been a student in the course, and neither quiz operation documents a parameter to turn it off — the read-parameter contract test says so, and would flag the parameter as undocumented if it were added there. That test (=org-canvas-contract-test.el=, "Canvas read-parameter contract") checks every registered feature's =:list-params=, =:item-params= and =:body-list-params= against the query parameters the OpenAPI spec documents on its list and show operations, since a misspelled or unsupported query parameter is silently ignored by Canvas and nothing else in the code path would notice.

* A Pull Takes Its Heading by Name Too (issue #346)

#287 gave pushes a caller without a point; pulls kept only =org-canvas-pull-at-point=. Taking Canvas's version of one heading from a batch Emacs — the approved "Canvas is right" half of a drift report's CHANGED row — meant finding the heading by regexp, redefining the private =org-canvas--confirm= for the rest of the session, pulling and saving.

*The pull twin is generated where the push one is.* =org-canvas-define-sync= also emits =org-canvas-pull-<singular> (TARGET &optional BY)= for a feature with a single-item pull: one that hands the macro =:pull-item-fn=, or says =:pull-heading t= because it registers its pull-item function apart from the sync (classic quizzes, which keep the pull out of the conflict prompt, #295). Outcomes have no single-item pull and get none. New Quizzes, whose sync by heading is hand-written, get a hand-written =org-canvas-pull-new-quiz=. The heading is found by the same =org-canvas--sync-find-heading=, with the module's own =:file=, =:query= and =:id-property=, so a title matches exactly as it does for a push; the errors say to pull, not sync, a repeated title at point.

*The at-point pull's own pieces do the work.* =org-canvas-pull-at-point= was split into a target (=org-canvas--pull-at-point-target=: the feature for the file, the climb to the level-1 entry for a =:pull-whole-entry= feature, the stamp, and the refusal of a heading without one) and the fetch (=org-canvas--pull-at-point-1=, through =org-canvas--conflict-pull-local=, which restamps =CANVAS_UPDATED_AT= and drops =PAYLOAD_HASH=). Both moved from org-canvas.el to org-canvas-core-heading.el, since generated commands live in feature modules, which may require only core. The at-point command keeps its confirmation between the two; the pull by heading has none, because naming the heading is the answer, and saves the file afterwards, which the at-point command leaves to the user. Under =org-canvas--dry-run= it reads and writes nothing and answers =dry-run=; otherwise =pulled=. The issue's other option, a NOCONFIRM argument to =org-canvas-pull-at-point=, would still have left the script finding the heading and saving it.

*=org-canvas-pull-headings= is =org-canvas-sync-headings= with another registry.* Entries are read by the same =org-canvas--sync-headings-entry=, every feature is resolved first (=org-canvas--pull-heading-fns=, filled by the macro), and each runs in the same =condition-case= (=org-canvas--headings-run=, now shared), so a misspelt feature stops the batch with nothing read and one failure does not stop the next.

*The names cannot meet the whole-file pulls.* Those are the plural (=org-canvas-pull-assignments=), these the singular (=org-canvas-pull-assignment=), the same split as =org-canvas-sync-assignments= and =org-canvas-sync-assignment=; none of today's singulars is any other command's name (=org-canvas-pull-quiz= sits beside =org-canvas-pull-quiz-results= without touching it). A feature named by a word with no plural =s=, whose singular would be its plural, would have its whole-file pull silently replaced, so =org-canvas--pull-heading-fn-forms= refuses that at expansion, and a spec checks every registered pull by heading still carries its own docstring.

* The GraphQL Documents Are Checked Against the Schema (issue #269)

The GraphQL documents of the time travelled to Canvas as opaque strings — the post-policy mutations, =postAssignmentGrades=, the checkpoints query and =updateDiscussionTopic=; every document added since (#350's processor query, #351's report query, #352's reads and mutations) is held to the same check — with nothing checking that the fields, arguments and input types they name exist. The REST side has had =test/contract/= since the OpenAPI fixture: every =build-payload= is checked against the documented operation. The GraphQL side had mocks, and a mock cannot tell whether =DiscussionCheckpoints= still has a =dates= field of that shape, which is why coverage.org kept the checkpoint mutation on its watch list.

The same design, with the choices the medium forces:

- *Two sources, introspection preferred.* =instructure/canvas-lms= ships =schema.graphql=, regenerated in the commits that touch the Ruby types, and every document checks against it. But the public mirror is stale by months against the instances, so the SDL is a baseline for reading input types while writing a document, and the instance's own introspection (a POST that is a read, so it runs under =org-canvas-read-only=) is what the code actually talks to. The extractor takes either; the fixture records which, with the ref or the host. When a new document reaches types the fixture lacks and the instance is out of reach, =--supplement= adds only those types from the SDL and lists them under the provenance's =supplements=, keeping everything already there; #350 added =Assignment=, =AssignmentConnection=, =ExternalTool=, =LtiAssetProcessor= and =LtiAssetProcessorConnection= this way, so the next introspection should replace them.
- *The fixture holds the reached types only.* A walk of each document through the schema, plus the transitive closure of any input object it names (a variable builder may fill any field of it), gives about forty types and 60 KB; the whole schema is 13,000 lines. For a reached object type every field is kept, with its arguments and deprecation reason, so a document edited to select a sibling field is still checked without regeneration; a type an unused field names is simply absent, and a document that reaches it fails with "is not in the fixture", the cue to regenerate.
- *The documents are read out of lisp/ by the extractor* (the =query (= / =mutation (= string literals), validated with graphql-core before anything is written, and named by symbol in the test, so the two lists cannot drift apart silently: a document changed in lisp is picked up by the next regeneration, and a new file has to be added to both.
- *No GraphQL parser in Elisp.* The documents are short and of a regular shape (most on one line, the longer reads laid out over several), so the test tokenizes and parses them itself — operation, variable definitions, selections, arguments with variables, literals, object and list values — a hundred lines that would not survive a document with fragments or directives, none of which org-canvas writes.
- *The variables side is the real payload check.* The document check proves the string; the callers are run with the sender mocked and what they hand it is checked against the input types: required keys present, a =Boolean!= from =t= or =:json-false= and never nil (nil encodes as null, which the live probe in #202 caught), an =ID!= a string, a list a vector (=json-encode= writes a Lisp list as an object), enum strings valid.
- *What it cannot say.* A feature flag does not shape the schema: =checkpoints= is in the SDL and in the introspection whether or not the account flag is on, since the flag is enforced when the field resolves. The check catches renames, removals and version lag; the first live run still answers "is the flag on".

* Post Policies Are GraphQL (issue #202)

Canvas keeps the grade post policies and the act of posting grades out of its REST API: REST reports =post_manually= on a course (with =include[]=post_manually=) and on an assignment, and can write neither; setting a policy is the =setCoursePostPolicy= and =setAssignmentPostPolicy= mutations, posting is =postAssignmentGrades=. The GraphQL endpoint takes the same bearer token, so =org-canvas--graphql-send= goes through =org-canvas-api-request= and inherits redaction, rate limiting and the read-only guard. Two rules follow. A query is a read and lifts the read-only guard for its one request (=org-canvas--graphql-query=), and refuses a document that is a mutation; a mutation goes through =org-canvas--graphql-mutate=, which keeps the guard and honours the dry run with the sentinel (Hard Rule 1). GraphQL answers 200 with an =errors= array when a field fails, so the sender turns errors into =org-canvas-api-error= naming them rather than returning a partial =data=.

An assignment's =POST_POLICY= is written by pull only when it differs from the course's (=org-canvas--assignment-remote-post-policy=, with the course policy read once and cached): Canvas reports every assignment's /effective/ policy, and stamping that on every heading would make the next push pin each assignment to an explicit policy the course setting no longer reaches. A silent heading inherits, and the drift report compares the property only where it is declared (=:compare-p=). An unrecognised value falls back to nothing, not to the first allowed value as other enums do, because a typo must not flip a gradebook's posting. The grading file records the assignment's effective policy at pull time so the push can offer to post without another request.

** A Posting Schedule Rides the Post-Policy Mutation (issue #352)

=setAssignmentPostPolicy= also takes =postGradesAt= and =postCommentsAt=, and Canvas keeps them as the assignment's =scheduledPost=, posting the hidden grades and comments by itself when each time comes. That lets a grader push a column hidden and name the release time in one sitting. An assignment heading declares it with =POST_GRADES_AT= and =POST_COMMENTS_AT=, both Org timestamps. What the schema and canvas-lms (=318f2ad0=, =app/graphql/mutations/set_assignment_post_policy.rb=, =app/models/scheduled_post.rb=) say Canvas does decided the rest. None of it has been checked against the live instance.

- *Both times, or neither.* =ScheduledPost= requires both (=DateTime!= on each field, a presence validation on each column). Canvas has no default for a missing one, so one without the other is a validate error, and the push refuses the heading before its PUT (=org-canvas--assignment-check-schedule=). It is not sent and left to fail in finalize, after the assignment has already changed.
- *Grades no earlier than comments.* The model rejects =post_grades_at < post_comments_at=. Equal times are the ordinary case: Canvas then posts both together. Validate and the push compare the parsed times, never the strings, because two offsets must not order by spelling.
- *A schedule means manual posting.* The mutation stores a schedule only when =postManually= is true, and drops the times without an error otherwise. So a heading with a schedule sends manual posting whether or not it declares =POST_POLICY=, which pins the assignment's policy. A heading with =POST_POLICY: automatic= beside a schedule is a contradiction, an error in validate and in the push.
- *Silence keeps Canvas's schedule.* When =postManually= is true and both times are blank, the mutation /deletes/ the schedule it finds. Before this change, on an instance with the feature on, every push of =POST_POLICY: manual= therefore wiped a schedule set in the web UI. A heading that says manual and names no times now sends the schedule Canvas holds (=org-canvas--assignment-schedule-held=, from the course-wide read below). A silent heading keeps its schedule, as it keeps every other field it does not mention. org-canvas never clears a schedule. That is the web UI's job, or it lapses once the times pass. When the read was refused, the push sends no times, as it did before. An instance that refuses the read will likely refuse the mutation as well.
- *The feature flag is invisible, so the reply is checked.* Canvas keeps a schedule only when the site-admin feature =scheduled_feedback_releases= is on, and ignores the times without an error when it is off. The mutation selects =postPolicy { assignment { scheduledPost { ... } } }=, and the push compares the times that come back with the times it sent, as moments. When they differ it logs one =[Verify]= warning naming both. The write still counts as a success, as #349's echo check does. Under a dry run nothing is sent and nothing is compared.

*The read.* The REST assignment has no schedule, so the pull and the drift report read it the way they read document processors (#350). One course-wide =assignmentsConnection= query per command, page by page, is keyed by assignment id and forgotten on =org-canvas--operation-start-hook=. It is a query of its own, not a field added to the processor query: a failure in one must not cost the other, and each degrades on its own warning. The paging and the refusal handling are shared (=org-canvas--assignment-graphql-read=). The properties declare =:remote-fn= with =:remote-known-p=. Canvas's schedule, or its absence, is written by a pull. A refused read leaves both properties as typed and the drift report compares neither. The report compares a property only where the heading declares it: a schedule set by hand beside a silent heading is not drift, since the push would keep it. Both times also go into the payload hash (=:hash-extra=), because they travel outside the PUT, so an edit to the schedule alone is not skipped as unchanged (the #242 lesson).

*Unverified live.* The field names come from the schema, and the contract test checks both documents against the fixture, whose =ScheduledPost= comes from the canvas-lms SDL (=318f2ad0=). Whether the flag is on at Clemson, what a refused schedule looks like in the reply, and whether =postGradesAt= comes back in UTC are all unknown until the first live push. A probe that sets a schedule on a sandbox column and reads it back settles all three.

* A Report Command Describes Itself in Batch (issues #155, #169)

=org-canvas-validate= in =--batch= printed =Validation: 24 error(s), 78 warning(s)= and threw the report away: the detail went into =*canvas-validate*=, and a batch Emacs has no way to show a buffer. The workaround was to know the buffer name and =princ= it yourself, which is fine once you know it and undiscoverable before. Validate is the command with the best claim to running non-interactively — it makes no API calls, so it needs no token and is the natural CI or pre-commit check over a course directory, and the natural first thing to run against a freshly pulled course. Both are batch contexts.

This is the same defect #155 fixed for the pull summary, so the fix is the shared helper #169 asked for rather than a second copy of the =(if noninteractive ...)=: =org-canvas--report-display= (core-org.el) takes a buffer name, a render function and an optional mode function, renders into the buffer either way — so the report is still there to inspect, and the tests that read it still can — then displays it interactively and =princ=s it under =noninteractive=. It returns the text. The next report-producing command reaches for it.

=org-canvas-validate= returns its error count, which is what =org-canvas-validate-batch= exits on, mirroring =org-canvas-diff-batch=. *Errors only* — warnings are the ordinary state of a real course (every past due date is one) and a CI step that fails on them fails always.

* A Body Never Introduces a Headline (issue #175)

Pulled from Clemson CPSC 3720 F26: Canvas had 26 quizzes, =quizzes.org= had 27 level-1 entries; 55 assignments, 57 entries; three entries carried no =CANVAS_ID=. Quiz "Microservices HW Questions" (683589) had six questions on Canvas and one in the file — the other five hung under a phantom level-1 heading whose title was the quiz description's =<h2>= and whose drawer read =:CLASS: article-title=, pandoc's fingerprint. pandoc renders an HTML heading as an Org headline; inserted under an entry, that headline /ends/ the entry, and everything after it — the rest of the description, the questions — belongs to a new id-less one. A push would then CREATE the phantom as a second quiz and leave the real one short, validate would see only a heading with no id, and nothing in the log said a word.

*The invariant: a body can never introduce a heading at or above its parent's level — in practice, at any level.* =org-canvas--org-body-neutralize-headlines= enforces it at the one chokepoint every converted body passes, =org-canvas--html-to-org=, on the pandoc path and the raw-HTML fallback alike, so a test that mocks =call-process-region= exercises it and one that mocks =org-canvas--html-to-org= itself bypasses it (which is how the count guard is tested).

*The representation: an Org special block, =#+begin_hN= … =#+end_hN=, N being the HTML level.* The headline line and the drawer pandoc wrote under it (=CLASS=, =CUSTOM_ID=) become a block holding the heading text as ordinary Org markup — bold, links and all — and =org-canvas--html-heading-block-filter=, an =org-export-filter-special-block-functions= entry that =org-canvas--with-body-export-settings= installs around every Org-to-HTML export the package performs (the subtree exporter, =org-canvas--org-to-html-string= for quiz descriptions and questions), renders a one-paragraph block back as =<hN>…</hN>=. The round trip is exact in tag and text; the drift report, which compares bodies as text (#83), sees no difference. A referenced =CUSTOM_ID= survives as a =<<target>>= at the head of the block and its =[[#id]]= links become fuzzy =[[id]]= links, so a page's table of contents still resolves. Inline conversions (=org-canvas--html-to-org-inline=: table cells, answers, rubric text) drop the marker lines and keep the text. An instructor can write the block by hand to put a heading in a quiz description, which no Org headline could do.

*Rejected: demoting the headline* (pandoc's =--shift-heading-level-by=, or rewriting the stars), the fix the issue first suggested. The extractors say no. A classic quiz's description is the text from its drawer to =outline-next-heading= — any level — and its questions are its level-2 children (=org-canvas--quiz-parse-body-text=, =org-canvas--quiz-sync-children=); new quizzes read the same way (=org-canvas--new-quiz-parse-body-text=); an outcome's children at any depth are outcomes and groups. A demoted =<h2>= would either become a question on the next push or cut the description short, and there is no depth that is safe for all three. A bold paragraph loses the tag; an =#+begin_export html= block keeps it but leaves raw HTML in the file. The block keeps both.

*The guard.* A pull stamps its id property on every entry it touches, so an id-less level-1 entry that was not there before it began is one it did not mean to write. =org-canvas--pull-check-entry-count= counts them before and after (=org-canvas--pull-idless-entry-count=, one pass over the level-1 headings), logs a =[Pull]= warning naming the file, the count and the items written, and records it in the pull summary as a non-fatal error; it never prompts, so a batch pull runs on. It sits in =org-canvas-define-pull= and in the two custom loops whose bodies carry headings, quizzes and new quizzes. Comparing entries to remote items outright was rejected: local drafts, orphans of items deleted on Canvas and a skipped front page all make those differ on a healthy file.

* A Stranded Body Fragment Is Flagged and Never Created Unasked (issue #391)

#175 stopped new fragments; it could not reach the old ones. A re-pull rewrites each item's own subtree by =CANVAS_ID= and leaves the id-less sibling a pre-#175 pull stranded where it was, so on course 295790 =assignments.org= read the item, its fresh body with the heading as a =#+begin_h1= block, and then the same text again as a level-1 heading with =:CLASS: article-title= and the rest of the old body under it. An id-less heading is how a user writes a new item, so every push would have created an assignment titled =*Read the following article: *=, and nothing warned.

*The marks.* =org-canvas--body-fragment-reason= (core-org) calls a heading a fragment when it has neither =CANVAS_ID= nor =CANVAS_URL= and either its drawer holds a property only pandoc writes — =CLASS= or a =DATA-= attribute (=org-canvas--pandoc-attribute-property-re=) — or its title, with anchors, =\ast{}= and whitespace folded, is the text of a =#+begin_hN= block between it and the nearest heading above at its level or higher: the item whose re-pulled body now carries the heading the fragment once was. The second mark catches the drawer-less shape (a column-0 =<strong>= that pandoc made a headline). =CUSTOM_ID= and =STYLE= are left out of the first: a user writes those on a new item too. The answer is a phrase for a message, or nil.

*Validation warns.* =org-canvas--validate-body-fragments= reads every heading of every registered file, once per file as the cross-course scan does (#172), and warns "probably a body fragment from an older pull". A warning, never push-only (#168): the mirror is wrong whether or not a push follows.

*The push refuses to create one without asking, at the runner, not per module.* The id-less create branch of every =org-canvas-define-sync= run passes through one of two places, =org-canvas--sync-execute-pipeline= (a full run) and =org-canvas--push-at-point-runtime= (at point, by name, =org-canvas-sync-headings=), and both consult =org-canvas--sync-refuse-fragment-p= before the push function, so a custom push (calendar, group categories, files) is covered with the generic one. Under =noninteractive= and in a dry run it refuses without asking; interactively it asks with =y-or-n-p= itself rather than =org-canvas--confirm=, since a create students may see is not the non-destructive confirmation =org-canvas-assume-yes= exists to answer. A full run counts the refusal as a skip and names it among the skipped titles, so no new counter joins =org-canvas--sync-stat-keys=; a single-heading push ends with the outcome =fragment=, which the headings report counts as stopped. The custom child loops (quiz questions, New Quiz items, module items) are not guarded: the fragments a pull stranded are level-1 entries, a level those loops never create.

*Rejected: deleting the fragment on pull*, the issue's other option. A pull that removes an id-less sibling whose title matches a block it just wrote would be right on the fragments seen so far and wrong on the first user who typed a heading with that text, and local text is never deleted for looking stale (the orphan cleanup is a separate command for that reason). The warning names the heading; the instructor folds it back into the item above.

* The Syllabus Is the Text Above the First Sub-Heading (issue #275)

The other side of #175. A pulled body never carries a headline, but a heading's /children/ can be its structure: =** Navigation= under the course heading in =settings.org= is the tab list =org-canvas--settings-parse-navigation= reads, the way a quiz's level-2 children are its questions. The settings push, though, took its syllabus from =org-canvas--export-subtree-body-to-html=, which exports the heading to =org-end-of-subtree= — children included — and strips only the drawers and the =overrides= and =accommodations= tables. So the tab list went to the syllabus page, the one page every student is sent to, as a numbered "Navigation" section, and since Org's =toc:t= is the default and the subtree now had a heading, a "Table of Contents" pointing at it sat above the body. Found 2026-09-15 on course 297530: the live syllabus read =Table of Contents 1. Navigation Welcome to CPSC 2920 ... 1. Navigation Home Modules Assignments Announcements Grades Syllabus=, the six tabs of the 2026-08-19 sync; the file had since grown to 25 tabs, fifteen struck through, and the push was withheld.

The exporter takes a =NO-CHILDREN= flag: with it, the temp copy is cut at =outline-next-heading= from the entry's own heading — its first child, or nothing — before the tables and drawers are stripped and the links and images resolved. The settings parse passes it: the syllabus is the text between the drawer and the first sub-heading, which is exactly what a pull writes back (=org-canvas--settings-replace-syllabus-body= then re-inserts Navigation after it), so the round trip is consistent. With no heading left in the export, Org emits no table of contents, which is why the =toc:nil= the issue suggested was not added: it would have been a flag protecting against nothing, and binding it for every body would have taken the table of contents off a page that has sub-headings of its own, which nobody asked for. Cutting =** Navigation= by name was rejected for the same reason quizzes stop at any heading: whatever sub-heading the course heading grows next is structure too.

The consequence is that a sub-heading an instructor writes as syllabus text (=** Office Hours=) is silently left behind by the push, so =org-canvas--validate-settings-structure=, the settings registration's =:structural-fn=, warns on every sub-heading of the course heading that is not =Navigation=, naming it, push-only (#168): the course is not at fault, the push just does not carry it.

* Org Files in Batch Mode: Truenames and Fresh Buffers (issues #97, #121, #188, #249)

- Always =org-back-to-heading t= before property access
- Use markers for safe position tracking
- Save buffer after modifications
- =org-canvas--path= returns truenames — one inode, one buffer. A symlinked =org-canvas-directory= spelling used to give a batch caller a dual buffer: every PUT landed, only the stamps died on the unanswerable changed-on-disk prompt, and the caller's final save clobbered stamps the sync had written (issue #97). =org-canvas--registry-feature-for-file= compares truenames for the same reason
- =org-canvas--find-file-noselect= is how every module opens a course file — never =find-file-noselect= directly. =find-file-noselect= asks "changed on disk. Reread from disk?" for a file it already visits whose mtime moved, which a file-sync client (OneDrive, Dropbox) does moments after each save; in batch the question reads stdin, gets EOF, and the run dies /after/ some entries pushed and before the rest (issue #121). The wrapper passes NOWARN under =noninteractive= and lets =org-canvas--ensure-buffer-fresh= decide instead, keeping Emacs's own prompt interactively
- =org-canvas--ensure-buffer-fresh= guards =org-canvas-org-set-property= and =org-canvas--save-buffer= in batch: an unmodified stale buffer is reverted (a =[Fresh]= warning and a batch =message=, since text the buffer never saw arriving mid-run is never routine), a modified stale one signals a clear error instead of the prompt. A finalize failure after a successful API call logs =[Stamp]= naming the phantom-drift consequence — the [FAILED] line alone reads as a push that never happened
- A restamp is not a rewrite (issue #188). The same sync client that provokes #121 restamps the file a buffer has /just saved/, and a second push at point in that buffer, one second later, had stamped its drawer by the time =org-canvas--save-buffer= ran: modified buffer, moved mtime, and the guard above called it a dual-buffer clobber. The PUT had landed; the drawer kept the old =CANVAS_UPDATED_AT= and =PAYLOAD_HASH=, so the next sync reported drift that was not there. =org-canvas--content-hashes= (buffer-local, newest first) records the text as of every read through =org-canvas--find-file-noselect= and every write through =org-canvas--save-buffer=; when the mtime moves but the file's text still hashes to the newest, =org-canvas--file-restamped-p= is true and the guard refreshes the visited modtime and carries on, edits and all, with a debug =[Fresh]= line. A buffer org-canvas never read or saved has no hashes and is treated as before. The spec's order matters: edit, then restamp, then save — restamped first, a batch Emacs clears the stale time itself on the next edit
- A roll-back is not a rewrite either (issue #249). The same client wrote an /older/ copy of =rubrics.org= back over the buffer's newer saves in the middle of fourteen creates: the disk text was not the last write, so the guard called it an external edit and reread it, the buffer became the stale copy, two stamps whose POSTs had landed vanished, and the three stamps after them were written on top and saved. Nothing surfaced — the reread was an INFO line, the run reported 14/14 — until the next drift report listed two UNCLAIMED rubrics and the assignments linking to them attached nothing. Disk text that hashes to any /earlier/ entry of =org-canvas--content-hashes= is =org-canvas--file-rolled-back-p=: nothing on disk is news to the buffer, so the buffer is the newer side, and =org-canvas--restore-rolled-back-file= refreshes the visited time and writes it back over the file — forced, since an unmodified buffer's last save is exactly what the client undid — under a =[Fresh]= warning and a batch =message=. Only text matching no hash at all is an external write, and that path keeps the reread (or, for a modified buffer, the #97 error)

* A Live Search Greps What Canvas Holds (issue #406)

On 2026-09-29, the day before a midterm's old date, the question was whether Canvas anywhere still said the exam was tomorrow. The Org tree was clean and the drift report was clean, and both were right: =calendar.org= still held the event on Sep 30 and had been pushed that way on 2026-09-24 with everything else. The drift report compares Org against Canvas and cannot see a stale value both sides hold. A hand-written probe that GETs every text-bearing object and greps it found the event in one run; =org-canvas-search-live= (=org-canvas-search.el=, a command file requiring core only) is that probe as a command, and =org-canvas-search-live-dates= the flavour that lists every date a student can see.

*The walk is data on the registry, not a second list of endpoints.* =org-canvas--search-surfaces= names each object type, the feature (or pull-feature) entry whose list URL, parameters, id and title fields list it, the fields whose text is searched and the date fields shown; children (module items, quiz questions, New Quiz items) are read under their parent through a =:fetch= of the parent, and the syllabus through its own read. The URLs come from =org-canvas--feature-list-url= and =-list-params= (Hard Rule 13), so calendar events list from their global endpoint and announcements carry =only_announcements= without the search knowing either. The New Quiz item endpoint is the one call outside the registry, declared from =org-canvas-new-quiz-items.el= rather than required.

*A date field is searched as the Org timestamp a pull would write.* The stale value that started this was not prose but the event's =start_at=, which no regexp over HTML would touch. Each surface names its date fields, rendered through =org-canvas--iso8601-to-org-timestamp= in the course zone, so "09-30" matches the event dated September 30 in the same run that finds the sentence saying so, and the report names the field. The dates flavour is the same walk with a date regexp and the match alone as context: an ISO date (which the rendered field begins with), a month name or abbreviation and a day, or a numeric month/day.

*A hit is reported once.* A quiz's shadow assignment repeats the quiz's description and an announcement is a discussion topic too; the search honours those two features' =:skip-fn=. Pages are not skipped: the front page, which push and delete-all protect, is the one page every student reads (pull-system.org, "A :skip-fn Must Say So").

*A surface that cannot be read is skipped and named, never an abort.* A role refusal or a service the course has off (New Quizzes behind its flag) drops that surface, or that one parent's child list, into the closing line, and the rest of the walk goes on (#155). The report goes through =org-canvas--report-display=, so a batch run prints it (#169), and the command returns the hit count for a script's exit status. HTML is stripped by a small tag-and-entity fold rather than pandoc: the text is matched, never written, and a pandoc round-trip per object would make the audit slow for nothing.

* A Heading Opens Its Canvas Page from Rules Its Module Declares (issue #292)

Attaching a document processor is a browser step by design (#184: the API refuses =asset_processors= from a token), and the validate warning told the instructor to "attach it in the web UI" without taking them there; on course 297530 the address was assembled by hand from =org-canvas-base-url=, =org-canvas-course-id= and a =CANVAS_ID=. =org-canvas-browse-at-point= (=org-canvas-browse.el=, a command file requiring core only) opens the heading at point with =browse-url=, and =org-canvas-browse-edit-at-point= (or a prefix argument) its edit page. It sends nothing.

*Where a heading lives is data on the feature registry, not a =cond= in the command.* Each module declares =:web-pages= beside its =org-canvas-register-feature=: a list of rules, each with a =:level= (nil for any), the =:id-property= the page is named by (nil when it needs none), a =:path= and optional =:edit= format under =/courses/COURSE/=, or a =:path-fn= for a page no single id names (a files.org folder, whose address is its path of folder names). A file the feature registry does not hold — New Quizzes, sections, settings — registers the same rules through =org-canvas-register-web-pages= into a second, web-only list, which =org-canvas--web-pages-for-file= consults after the feature registry. Adding New Quizzes to the feature registry only to reach its web page was rejected: its API is a different service, and every registry consumer (the drift report, the orphan scan, prune) would have listed it at the wrong endpoint.

*A heading whose level no rule names takes its parent's page.* A quiz question, a New Quiz item, a rubric criterion and a heading inside a body have no page of their own, and the nearest useful page is the object that holds them; the echo area names the heading the command started on, so the jump is not silent. A level a rule does name but whose id is absent is an unsynced heading, and the command refuses, naming the property, rather than opening a list page that would look like success.

*The assembled address, not a stored =html_url=.* The issue suggested pulls store Canvas's =html_url= on each heading. That is one more property on every heading of every file for an address the registry already determines, and a copied course would carry the old course's addresses. The drift report does prefer =html_url= where it has one, since its rows carry the remote item and it costs nothing: =b= opens it (now kept on CHANGED rows as well as EXTRA and UNCLAIMED), and =B= opens the edit page assembled from the registry through =org-canvas--feature-web-url=, falling back to =html_url= for a row whose feature declares no page (module items).

There is no =org-canvas-mode-map= to bind the command in, so it is on the transient menu (=b=, =B= in the Sync group), and the canvas-owned validate warning names it.

*A SubHeader opens its module.* =content_tag_redirect= knows no =ContextModuleSubHeader=, so =modules/items/ID= for a text header lands on the Modules page under "Didn't recognize the item type for this tag" (=application_controller.rb= 2583), and the API gives a SubHeader no =html_url= at all (=lib/api/v1/context_module.rb= 94). The level-2 rules now lead with =org-canvas--module-subheader-web-path=, which opens a stamped SubHeader's module: the parse's own test without its link resolution (=ITEM_TYPE: SubHeader=, or neither =EXTERNAL_URL= nor a =[[file:= link). An unstamped one still refuses, and one under an unstamped module falls through to the item address.

*A percent sign is written =&#37;=.* The Files app's router decodes the path and then =generateFolderByPathUrl= runs =decodeURIComponent= on each name again (=ui/features/files_v2/utils/apiUtils.ts= 48), so a folder named =50% Rule= sent as =50%25%20Rule= reaches the second decode as a bare =%= and throws. Canvas's own folder links replace =%= with =&#37;= before encoding (=folderUtils.ts= 30) and the decode side turns it back; =org-canvas--file-folder-web-path= now does the same.

*A New Quiz's edit page is its assignment settings, not the item editor.* =assignments#edit= renders the assignment form for a =quiz_lti= assignment (points, group, dates, assign-to; the React teacher view under =assignment_edit_enhancements_teacher_view=); it redirects only classic quizzes, graded discussions and pages. This is where Canvas itself sends a teacher from a New Quiz module item (=content_tag_redirect=, =use_edit_url=, adding =?quiz_lti= for the breadcrumb and active tab under =newquizzes_on_quiz_page=). The items are built from =assignments/ID=, whose =#show= launches the New Quizzes tool for an =external_tool= assignment. Opened on course 297530 (2026-09-25) against an unpublished probe New Quiz, the rule was confirmed: the assignment settings form, not the item editor (coverage.org, "Watch on First Live Use").

The source settles routing and redirects; what a page looks like on the instance, behind its feature flags, is still a browser's to see, and those checks are listed in coverage.org.
