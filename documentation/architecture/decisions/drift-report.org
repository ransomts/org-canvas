The read-only comparison of Org against Canvas: what it compares, how rows pair, and what each row does when you act on it.

* The Drift Report Compares Bodies (issue #83)

The description is set directly on the payload, outside the property specs, so =org-canvas-diff= could not see it. Modules that push a body declare =:body-api-key= on =org-canvas-register-properties= (assignments/quizzes =description=, pages =body=, announcements/discussions =message=); pages add =:body-list-params '(("include[]" . "body"))= because the pages index omits bodies unless asked, and quizzes a =:body-fn= because their description is only the text before the first question. Local bodies come from =(org-canvas--export-subtree-body-to-html t)= — the OFFLINE flag skips link /and image/ resolution, and image resolution uploads; a report must never write. Both sides go through =org-canvas--diff-html-to-text= (tags dropped, entities decoded, whitespace collapsed) so markup-only differences stay invisible. Its whitespace class is explicit, not =[[:space:]]=: that class goes by the current buffer's syntax table, and in a Lisp buffer newline is comment-end, so the same string normalized differently depending on which buffer was current. A remote item lacking the field, or a failed export, means "not compared", never drift. A CHANGED row with no field differences now carries a line saying the change is in something uncompared.

* By-Design Extras (issue #98)

A synced course never read zero: Canvas scaffolding and deliberate web-UI objects sat as permanent EXTRA rows, so =org-canvas-diff-batch= could not do cron monitoring. Three valves, broad to narrow: structural =:skip-fn=s on the feature registry suppress scaffolding — the root outcome group (no =parent_outcome_group=), the stock "Assignments" group (skip-fns only ever hold back /unclaimed/ items, so a managed group of that name is still compared), and classic-quiz shadow assignments (=quiz_id= present) — counted in the footer the #81 way, and protecting the same objects from orphan cleanup; =org-canvas-diff-excluded-features= skips a feature wholesale with a visible "not checked" line; =org-canvas-diff-known-extras= (=(FEATURE ID &optional NOTE)=) acknowledges individual ids, counted once in the footer, with a =STALE-ACK= divergence — which counts, deliberately — when an acknowledged id stops existing so the list cannot rot. Both defcustoms affect the diff only; prune still lists acknowledged items. A fourth valve is automatic (issue #102): announcement and page attachments land in Uploaded Media as unclaimed files, and the known-extras list grew by hand forever. =org-canvas--diff-feature= records =:referenced-files= — the =/files/<id>= ids the body field of every item embeds — for each feature with a =:body-api-key= (the bodies are already fetched for the #83 comparison), =org-canvas--diff-syllabus-references= adds the syllabus (the one extra GET), and =org-canvas--diff-apply-references= moves matching Files extras into a =:referenced= count rendered as a "Referenced media" footer line. Runs after every feature is diffed, since registry order puts Files before the body features. =org-canvas-diff-scan-references= (default t) turns it off. *Excluding a feature does not exclude it from that scan* (issue #111): announcements are the body feature most often kept out of the report and the one whose attachments land in Uploaded Media, so =org-canvas--diff-excluded-result= still lists an excluded feature that has a =:body-api-key= — one read-only request, no rows, =:references-scanned= recorded so the "not checked" line says the bodies were read.

* The Drift Report Has Verbs (issue #103)

=org-canvas--diff-render= still returns a string, and batch output is unchanged, but each row is inserted by =org-canvas--diff-insert-row=, which stamps the text with an =org-canvas-diff-row= property =(:feature NAME :entry ENTRY)=; text properties survive =buffer-string= and =insert=, and =princ= drops them. The interactive buffer is in =org-canvas-diff-mode= (derived from =special-mode=): =RET= =org-canvas-diff-visit= (heading by id property for MISSING/CHANGED, by title for UNCLAIMED, =browse-url= of the =:html-url= that extras now carry), =a= =org-canvas-diff-acknowledge= (edits =org-canvas-diff-known-extras= in memory, then hands the /whole new list/ to =org-canvas-diff-acknowledge-function=, default =customize-save-variable=; on a STALE-ACK row it drops the entry), =k= =org-canvas-diff-delete= (confirms, then the feature's item URL and =:delete-data=, as orphan cleanup does), =p= =org-canvas-diff-pull= (runs =org-canvas-pull-at-point= in the heading's buffer), =g= re-runs, =TAB=/=S-TAB= walk rows by stepping over property runs (a CHANGED row spans its field lines). An action rewrites its row in place via =org-canvas--diff-rewrite-row=, keeping the property, rather than re-fetching everything. No magit-section dependency: the rows are plain text properties.

* A CHANGED Row With Nothing to Compare Adopts the Stamp (issue #257)

Some writes Canvas makes on its own bump =updated_at= on entries whose content did not move: a metadata-only touch of a file (the case #94 answered for files with =:modified-field=), the association bump a rubric leaves on its assignment (the case #124 restamps inside finalize, and #131 met by hand before that), and a course-wide one — setting =:POST_POLICY:= in settings.org runs =setCoursePostPolicy=, and Canvas rewrites the policy of every assignment in the course, so the next report listed all 77 as =CHANGED (no compared property differs; ...)=. The report was right each time: Canvas is newer than the baseline, nothing compared differs, and there is nothing in Org to change. A push would send the same content again (and walk into the conflict check), a pull would rewrite the same text. What the entry needs is a new baseline, and three times the fix was a one-off script over =org-map-entries=, one list GET and =org-canvas-org-set-property=, reinvented each time.

=org-canvas-diff-adopt-stamp= is that script as a row action, and =org-canvas-diff-adopt-stamps= as a batch command that runs the comparison itself (=org-canvas--diff-collect-results=, the read =org-canvas-diff= was already doing, now shared). Three rules. *Only a row with nothing to compare qualifies* (=org-canvas--diff-adoptable-p=: kind =modified=, =:remote-newer=, empty =:fields=, a string =:updated=); a row where a property differs is refused by the key and counted, not adopted, by the batch — adoption must never paper over real drift. *The hash stays.* =CANVAS_UPDATED_AT= takes the entry's =:updated= (already the feature's =:modified-field=, so files adopt =modified_at=); =PAYLOAD_HASH= is untouched, because the local side did not change and the next sync should still skip the entry — dropping the hash, as a pull does, would push every adopted entry once for nothing. *Nothing is sent*, and the report itself still writes nothing (#83): =a= reads context-sensitively — acknowledge on EXTRA/UNCLAIMED/STALE-ACK, adopt on CHANGED — so the one verb that means "accept what Canvas holds" stays on one key, but it is a verb, never a side effect of rendering. The settings push that causes the course-wide case logs a warning naming the batch command; settings is a feature module and cannot require diff.el, so it names the follow-up rather than running it.

* The Drift Report Deletes Rows in Batch, After Checks and a Snapshot (issue #345)

After a calendar reshuffle (course 297530, pinned to 750dc5e) the report listed nine EXTRA rows: six module items, one assignment and two rubrics left over from dropped sessions. The instructor approved deleting all nine, and =k= was the only way in, one =y-or-n-p= per row. So a script did it: it rebuilt =org-canvas--diff-delete-target='s choice between a module item's URL and the feature's item URL, read each object, checked that the assignment had no submissions or scores and that each rubric had no Assignment association, wrote the object's JSON to a file, and only then sent the DELETE. The report already knew every target; what the script added was the checks and the snapshot, and both belong to any delete, not to one caller.

=org-canvas-diff-delete-rows= takes selectors — =(:feature NAME :id ID)= or =(:feature NAME :all t)= — resolved against =org-canvas--diff-collect-results=, the comparison the report and =org-canvas-diff-adopt-stamps= already share (or a =:results= list a caller computed once), and never prompts. Four rules.

*Only EXTRA rows.* An UNCLAIMED or MOVED row has an unstamped heading the next sync pairs with it — it adopts the twin (#179) or, for a move, leaves the copy — so deleting it in batch would race a sync over an object Org means to keep; =k= still offers them, one at a time, with the row in front of the operator. A selector on any other row answers =not-extra=, one that names nothing =not-found=; neither sends a request.

*Read before delete, and refuse what takes work with it.* =org-canvas--diff-delete-inspect= reads the object at the URL the DELETE will go to (a rubric with =include[]=associations=, an assignment with its =:item-params=) and runs the feature's guard from =org-canvas--diff-delete-guards=. An assignment is held back when its submissions list shows one turned in or one scored or graded, or Canvas's =has_submitted_submissions= says so: deleting it deletes the gradebook column. A rubric is held back when an =Assignment= association names it: its assessments belong to the id (Hard Rule 7). The reason is named in the outcome, and =:force= overrides it. An empty reply is refused too, since there would be nothing to snapshot. =k= runs the same checks and puts the reason into its question — cheap, since the one read is the object the snapshot needs anyway — rather than refusing, because the operator is there to answer.

*An owned assignment is held back too (#366).* The submission check alone let through the assignment another object owns while nobody had submitted yet: a new graded discussion's, or a New Quiz's before it opens, which stays an Assignments EXTRA row whenever the New Quizzes section is excluded or unread (#313). Deleting it deletes or breaks the quiz or discussion. The Assignments guard, =org-canvas--diff-delete-assignments-guard=, now asks first the predicate prune and the orphan scan leave such an assignment by (#319): the assignments feature's =:delete-skip-fn=, reached through =org-canvas--feature-delete-skip=, never a copy of its logic. It reads the fields that predicate reads — =quiz_id=, =submission_types= (=online_quiz=, =discussion_topic=), =is_quiz_lti_assignment= and the external tool's launch URL — all on the assignment the inspect step already GETs at the delete URL with the feature's =:item-params=, so no request is added, and an owned assignment is refused without listing its submissions. The reason names the owner: "the assignment belongs to discussion 'X' (a graded discussion, in discussions.org)" from the embedded =discussion_topic=, "quiz N (a classic quiz, in quizzes.org)" from =quiz_id=, or "a New Quiz, in new-quizzes.org", the category from =org-canvas--assignment-owner=, which diff.el declares rather than requires, as it does the modules.el pairing functions (#299). As with the other checks, =:force= deletes it anyway and =k= names the owner in its question. A New Quizzes row keeps the submission check alone: its object is the quiz, read at the quiz service, and deleting it is deleting the owner, which is what the row asks for.

*Snapshot, then DELETE.* =org-canvas--diff-delete-execute= writes the object's JSON, pretty-printed, to =<time>-<feature>-<id>.json= under =org-canvas-diff-delete-snapshot-directory= (nil means =canvas-snapshots/= under the course directory, resolved when used, as the submissions directory is) and sends the DELETE only after the write succeeded. The push file's "snapshot" is the in-memory remote list a sync reads for its conflict check; it holds list replies, not the single object a rebuild needs, and never touches disk, so it did not fit and the file writer is new. Both =k= and the batch write one.

*Dry run and read-only.* Under =org-canvas--dry-run= the objects are read and checked, and the outcome is =dry-run=: no snapshot, no DELETE (Hard Rule 1; the command takes selectors, so it is not in =org-canvas-dry-run--sync-commands=, which runs each entry with no arguments over the demo course — the diff specs cover it instead). A course marked =org-canvas-read-only= would refuse the DELETE at the transport anyway; =org-canvas--check-writable= runs before the snapshot too, so a refused delete leaves no file claiming it happened. Each row's failure is caught and recorded as =failed=, and the next row goes on.

The report itself is untouched: rendering still writes nothing (Hard Rule 19), and deleting is a verb the operator names.

* The Drift Report Lists Pending Creates and Pairs Moved Items (issue #294)

The report answered only half of "what would a sync do": what Canvas has that Org lacks (EXTRA) and what both hold differently (CHANGED). A heading with no Canvas id — which the next sync POSTs — got no row. After a week-long slide of a course calendar in Org (course 297530, 2026-09-22) the report showed 56 EXTRA module items and nothing of the 57 rebuilt item headings, three assignments, two rubrics and one assignment group the next sync would create, and finding those took a hand script over the Org files.

*A PENDING row per unstamped heading, counted apart.* =org-canvas--diff-feature= returns =:pending=, one =pending= entry per local entry without its id property (an empty value is no id, as =org-canvas--sync-collect-entries= reads it), naming the property the sync would stamp. The Module Items pass does the same for level-2 headings, with the module each sits under. =org-canvas--diff-pending-p-fns= narrows a feature whose file holds headings the sync never creates: a files.org folder heading carries no id and is not uploaded (=org-canvas--diff-file-heading-p=). A heading an UNCLAIMED or MOVED row already names is left out, so one change is one row. *Pending creates are not drift*: they stay out of =org-canvas--diff-count=, so =org-canvas-diff= returns and =org-canvas-diff-batch= exits on divergences alone, the section header reads "N divergence(s), M pending create(s)", and a footer line counts them. The report exists to say whether Canvas has drifted from what Org says; an unpushed heading is Org ahead of Canvas, which is what a sync is for, and a cron job that went red whenever an instructor drafted next week would be switched off. The one pending create that /is/ drift in disguise — a create whose stamp was lost — is already an UNCLAIMED row, and that one counts.

*Why the moved items never paired: two causes.* The Module Items pass (#177) built its extras and returned them; it never called =org-canvas--diff-pair-unclaimed= at all. And had it, the pairing compared the heading text from =org-get-heading= — which, with the flags diff passes, keeps link markup on every Org version in use (checked on Org 9.8: =[[file:assignments.org::*Closer][Closer]]= comes back whole) — against Canvas's plain title. A module item heading is always a link, so no item could pair; a files.org heading is too. The fix is at the local entry: =org-canvas--diff-local-entry= records =:match-title=, the title as a reader sees it (=org-canvas--diff-display-title=: a link's description, a bare heading link's target heading, a bare file link's file name, statistics cookies dropped — the name the sync gives Canvas), and all pairing compares that. =:title= stays the =org-get-heading= text, which is what the existing row lookups search for.

*Pairing module items is one to one, and knows the module.* =org-canvas--diff-module-item-pair= gives each extra at most one unstamped partner, preferring a heading in the item's own module: that pair is UNCLAIMED, worded for items, since the sync adopts a same-content twin itself (#179) and =org-canvas-adopt-at-point= does not reach level 2. A partner under another module makes the pair MOVED, with the old module (=:where=, =:module-id=, so =k= deletes the stale copy) and the new (=:to=). The row says what the sync would do — create it in the new module and leave this copy — and how to make it a move instead: stamp the named id on the heading, and the #105 reconcile creates it in the new module and deletes the old copy (since #352 the sync moves it instead, keeping its id; see below). A SubHeader pairs only within its module, since its title is all it has and "Readings" recurs every week by design. MOVED rows count as divergences, as UNCLAIMED rows do: Canvas holds an item where Org does not put it.

*Still read-only.* Every addition is a read of the Org files the report already opened; nothing is written (Hard Rule 19). A PENDING row carries its file and line, and =RET= goes there, checking the heading still is the one named and otherwise finding it by title; =a= and =k= refuse it, since there is no remote object. Left for later from the issue, and done in #296: the identifying fields on EXTRA assignments and groups (points, due, group, =needs_grading_count=) and an assignment-group weight total line.

* Extra Assignments and Groups Say What They Are (issue #296)

An EXTRA row named a title and an id, and knowing what an instructor had made in the web UI — a 20-point assignment in a new 10% group, due tonight, 89 submissions waiting — took a hand =GET= per row.  And a Canvas-only group hid a weight problem no row stated: Org's groups sum to 100 without it, Canvas's to 110, and nothing in the report added them up.  Split from #294, whose entry above left both undone.

*No request is added.*  Every field is in the list replies the report already holds.  =org-canvas--diff-feature= keeps its reply on the result as =:remote-items=, and =org-canvas--diff-apply-extra-details= runs after every feature is diffed, as the referenced-media pass (#102) does, because each feature needs the other's list: an assignment names its group by =assignment_group_id=, which only the groups reply turns into a name, and a group's assignment count is a tally over the assignments reply.  When the other list was not read (excluded, or its request failed) the detail degrades rather than fetches: the group is named by id, the count left out.  An assignment prints its group, points, due date (in the course zone, as an Org timestamp), publish state and =needs_grading_count= — the last from the index, which returns it to a teacher by default; a group prints its weight and count.  The line goes under the EXTRA row, inside the row's text property, as a CHANGED row's field lines do.  Only EXTRA rows get it: an UNCLAIMED or MOVED row already names the heading that is the item.

*The weight totals line is not drift.*  =org-canvas--diff-weight-totals= sums the =WEIGHT= of every group heading (the registry's =:query=, pending ones included — they are what Org says the course will be) against the =group_weight= of every group Canvas holds, the stock "Assignments" group the =:skip-fn= hides included, since its weight counts toward the grade all the same.  A difference is a =WEIGHTS= line under the section, rendered even when the section has no rows.  It stays out of =org-canvas--diff-count=, so =org-canvas-diff-batch= exits as before: each cause of the difference is already a row — an EXTRA group or a CHANGED weight, both counted — or a pending create, which #294 decided is not drift; counting the line too would count one change twice.  The one cause with no counted row is a weighted stock group, which the footer's "Not checked" line names.  The line cannot say whether the course weights by group at all (=apply_assignment_group_weights= is a course setting, another request), so it says it matters only when it does.  Read-only throughout (Hard Rule 19).

* The Drift Report Pairs Module Items by Content, as the Sync Adopts (issue #299)

#294 paired an EXTRA module item with an unstamped item heading by title; the sync adopts a twin by content (#179: =org-canvas--module-item-same-content-p=, the same type and content id or page url). The two disagreed on exactly the case the report exists for: a same-titled item that links different content read as UNCLAIMED, "the next sync adopts it", while the sync created a new item beside it — and the row hedged ("if the unstamped heading links the same content") because the report could not tell. Now the report asks the sync. =org-canvas--diff-module-item-content= runs the sync's own item parser, =org-canvas--module-item-parse-entry=, on each level-2 heading, and =org-canvas--diff-module-item-match= hands its result and the remote item to the sync's own predicate. A pair by content id or page url, or a SubHeader or external URL (whose title is its content), is =content=; an item whose link target has no Canvas id yet still pairs by title — the sync's predicate does the same — but the row carries =:by-title= and says "paired by title only", since which content the target gets is not known until it is synced. A side effect worth having: an item Canvas has since renamed still pairs when it links the heading's content.

*Why declare, not move and not copy.* Diff is a command file and must not require a feature module it does not drive. Three ways to reach the resolver: copy it into diff.el, move it to core, or =declare-function= the two modules.el functions. A copy is how the report and the sync came to disagree in the first place, and would drift again. Moving it means taking some fifteen functions — the link resolver, the heading search, the files.org path lookup, the file-to-type table, the parse and transform stages, the predicate — out of the module whose pipeline they are, for one caller. Declaring calls the code the sync runs, so the two agree by construction; the cost is a runtime dependence on modules.el being loaded, which =org-canvas= guarantees (it requires every module), and diff.el already declares functions from =org-canvas.el= the same way. If the parser is absent or signals, the heading's =:content= is nil and it pairs by title as before, marked by-title.

*Still read-only (Hard Rule 19).* The parser reads the linked Org file through =org-canvas--find-file-noselect=, which the report already uses for every course file; it sends no request and stamps nothing. It does log, as a sync stage would ("[Stage 1: Parse] Processing Item", "Unresolved link"), which in a report would read as a sync having run, so =org-canvas--logger= is bound to nil around it.

* A MOVED Row Stamps Its Paired Heading, and a Stamped Move Is a RELOCATE Row (issues #342, #343)

A MOVED row (#294) named the item id to stamp and said which module the heading sat in, but nothing stamped it. After a course moved every item from Week 06 on one week later, the report printed 48 MOVED rows, and the stamping was a script that parsed the row text and searched each destination module for a heading of the item's title. Seven of the 48 could not be found that way: the columns had been renumbered ("R6: Arguing Both Sides" on Canvas, "R7: Arguing Both Sides" in Org), and the report had paired those by content (#299) without saying which heading it paired. Once stamped, the 48 then disappeared from the report, which came up with six unrelated EXTRA rows. The next sync, though, would find each id missing from its heading's module (=org-canvas--module-item-disown-foreign-id=), create the item there with a new id and delete the old copy. That is 48 POSTs and 48 DELETEs, and 48 ids changing under anything that stores them.

*The row carries its partner.* =org-canvas--diff-module-item-paired= puts the partner heading on the MOVED entry: =:file=, =:line=, =:partner-heading= (the raw heading text, link markup and all) and =:partner-title= (what it shows). The row prints the shown title and line, so a renumbered pair can be read, and =s= (=org-canvas-diff-stamp-move=) finds the heading again. It tries the recorded line first, accepting it only when the heading there has the same raw text and still has no =CANVAS_ID=. If that fails, it looks for an unstamped level-2 heading with that text under the module the row names (=:to=). It never searches by the item's title, because the title is the thing a renumbering changes and "Readings" occurs in every week. It refuses when any heading in the file already carries the id, since two headings claiming one item is worse than none. A row paired by title only asks first, because nothing proves that pair. =S= and =org-canvas-diff-stamp-moves= stamp every MOVED row paired by content. They run the comparison themselves, as =org-canvas-diff-adopt-stamps= does, confirm unless in batch, list the by-title rows as HELD rather than stamping them, and report STAMPED, CLAIMED and NOT FOUND rows in a buffer of their own. The transient's =J= runs the bulk form.

*Stamping writes =CANVAS_ID= and nothing else, and sends nothing.* It is the second local write in diff.el, alongside stamp adoption (#257), and follows the same rule: a separate key and command, never something rendering does (Hard Rule 19). =PAYLOAD_HASH= is not touched. The module's hash covers its items' properties but deliberately leaves out their ids (=org-canvas--module-items-digest=), and moving the heading had already changed that hash.

*A stamped move is a RELOCATE row, counted apart.* =org-canvas--diff-module-item-relocations= indexes every listed item by the module that holds it. A stamped level-2 heading whose id sits in a module other than its own becomes a =relocate= entry, including a heading under a module not yet on Canvas, whose items the sync will disown the same way. The row says the sync recreates the item in the heading's module with a new id and deletes this copy. The rows sit under =:relocate=, are counted in the section header and a footer line, and stay out of =org-canvas--diff-count=, as PENDING rows do. They are Org's pending work, not Canvas drifting from Org, and a course mid-reshuffle should not turn =org-canvas-diff-batch= red. The row is there because the report is the only warning that the ids will change. =RET= visits the stamped heading and =b= opens the old copy. =a=, =k= and =s= refuse the row: the heading claims the item, and deleting the old copy by hand would leave the sync's own delete nothing to find.

*The MOVED row now describes the recreate.* It used to say "stamp CANVAS_ID … to move it instead", which reads as a move that keeps the id. Canvas cannot move an item between modules (the id's URL names the module, #105), so the row now says that with the stamp, the next sync recreates the item there with a new id and deletes this copy. (Superseded by #352, below: the sync now moves the item and keeps its id.)

* A CHANGED Row Adopts What It Names, and Nothing Else (issue #498)

=org-canvas diff= on a live course listed 21 CHANGED assignments: two publish flips, two =MUTED= flips, a rename, six EXTRA override rows, and fifteen rows with nothing compared differing. =p=, a pull, was the only way to take Canvas's side, and a pull rewrites the whole heading: it deleted =PUBLISHED: true= from nineteen headings (the registry default, #135), wrote =MUTED= wherever Canvas said muted, dropped =PAYLOAD_HASH= and the drawer's alignment, and ran every description through pandoc, which lost an =#+ATTR_LATEX:= line, a table's rules and hard-wrapped paragraphs Canvas had never held. The pull could not be kept; a script copied the stamps and the real changes across instead.

=A= on the row (=org-canvas-diff-adopt-drift=) and =org-canvas-diff-adopt-drifts= (=scripts/org-canvas adopt=) are that script. They live in =org-canvas-drift.el=, a command file that requires diff, and the report never runs them (Hard Rule 19). The rules:

- *Exactly the row's fields.* A CHANGED entry now carries the Canvas item it was compared with (=:item=), so nothing is read again. Each field is written from it: a registered property through =org-canvas--registry-remote-as-org=, the pull's own spelling, written even when it is the default (the heading named the property, and adopting must not turn an explicit =PUBLISHED= into silence), deleted when Canvas holds nothing; =TITLE= by =org-edit-headline=; an =:intent-of= field never (it is the file's declaration, #293), nor a field no spec registers. Every other line of the heading is left as it is.
- *The body only when asked.* Converting HTML back to Org is the lossy part, so the body is held back unless =A= is answered yes or =--body= given. When it is written, only the heading's own text is replaced (=org-canvas--pull-entry-text-bounds=), its =#+NAME: overrides= and =accommodations= tables kept verbatim and written first, where a pull writes them. A module that reads its body its own way (a =:body-fn= or =:body-remote-fn=: quizzes, New Quiz items), or a heading whose sub-headings the push sends as part of the body, is held back with the reason; ~=~ shows the text to copy by hand.
- *The stamp moves only when every field was written.* Then =CANVAS_UPDATED_AT= takes Canvas's stamp. A field held back keeps the old one, so the next push still meets the conflict check rather than overwriting the body Canvas holds. =PAYLOAD_HASH= follows #466's rule: a heading that was what its last push sent is hashed again (it is now what Canvas holds, and its next sync has nothing to send); one with local edits of its own keeps its hash, so the next sync sends them.
- *Nothing compared differing is stamp adoption.* Such a row goes to =org-canvas--diff-adopt-entry= unchanged (#257): stamp written, hash kept. =a= still refuses a row where a property differs; =A= is the verb that writes the property.
- *An EXTRA override row is appended, never rewritten.* =A= on it (=--overrides= in batch) adds one row after the table's last, cells placed by the header's column titles (=org-canvas--override-date-columns=), the existing rows untouched, alignment included. A date the table has no column for is refused, since adding the column rewrites every row; a heading with no table gets one under its drawer (=org-canvas--override-emit-table=). The next push then claims the override instead of deleting it (#411).
- *A CHANGED override row rewrites the dates it names, in place* (#528). A web-UI extension is the commonest override drift, and the first cut of =A= routed only EXTRA rows: =adopt --overrides --all= silently skipped CHANGED ones, and the next push would have sent the old dates back. The CHANGED entry now carries the Canvas override it was compared with (=:override=), and =A= finds the table row that claims it the way the push does (=org-canvas--override-parse-target=, then =org-canvas--override-find-existing=), then writes only the columns the row names. Every other cell and row is left, as for an append. A MISSING row is held, never adopted: Canvas's side of it is "no such override", and writing that means deleting the instructor's row. Batch adoption lists it =HELD= so the count of rows left is true.
- *Nothing is sent*, and a dry run writes nothing either, naming the fields it would write.

The report gained two comparisons so that "the fields the row names" is the whole story:

- *A rename is a field.* A module whose push sends the heading as the item's title declares =:compare-title= on its property registration (assignments, pages, quizzes, discussions, announcements), and =org-canvas--diff-compare-title= puts a =TITLE= field first on the row when Canvas's title differs, whitespace squeezed. A heading that is a link is left out. Before, a rename was a row with nothing compared differing, which =a= would have stamped while the next push renamed it back.
- *A declared boolean default is compared on a silent heading.* The pull deletes =PUBLISHED: true= because the registry's =:default t= matches the parse's fallback (pull-system.org, "How a property is pulled"), and that decision stands: drawers stay terse, and the push sends =published: true= for the silent heading exactly as for the explicit one. What was wrong is the report: it compared only written properties, so an item unpublished on Canvas after such a pull was a row with nothing compared differing, and stamp adoption accepted it while the next push published it again. =org-canvas--diff-compare-default= holds the declared default (only a boolean with an explicit =:default=, never an =:absent-inherits= one) against Canvas when the heading is silent and Canvas sent the field; the row reads =(unset: true)=.

=MUTED= was looked at and left alone. The pull writes it from the item's =muted= through the same registry field the report reads (=org-canvas--registry-remote-field=), so the two cannot read it differently; the report compares it only where the heading writes it, as for any property without a declared default, and its absence means "not sent". The pull wrote =MUTED: true= where Canvas's single-item reply said muted. Whether Canvas's list and item replies disagree on =muted=, or =muted= moved between the two reads (Canvas derives it from unposted grades under a manual post policy), is a live-Canvas question this change does not settle.

* A Heading's Canvas Version Is Shown Without Writing (issue #500)

The report shows a changed body as two excerpts of 40 characters around the first difference (=org-canvas--diff-text-excerpts=). That says the description changed, not what it now says, and the full text took a script over =org-canvas--graphql-query= or a lossy pull. =org-canvas-show-at-point=, =org-canvas-show-headings= (=scripts/org-canvas show FEATURE:TITLE...=) and ~=~ on a CHANGED row (=org-canvas-diff-show-row=) print the Canvas version of one heading: the title and every compared property beside the Org value, starred where they differ (a spec whose =:compare-p= rules it out is left out, as the report leaves it out), and the body three ways: Canvas's HTML, the Org =org-canvas--html-to-org= converts it to (file links not rewritten, since the rewrite downloads), and a unified diff of the heading's own body against that Org. The excerpts in the report stay: the report is a summary, and ~=~ is one key away.

They write nothing. The item is read with =org-canvas--pull-item-read= (=show=), or taken from the row (~=~); a property whose Canvas field is read by GraphQL (a post policy, a posting schedule) costs the read the report makes too; the local body is exported offline, as the report's (#83); the diff program reads two temporary files outside the course. A heading Canvas deleted says so rather than being marked, which is the pull's verb (#399).

* Timestamps Compare at Minute Precision (issue #176)

An Org timestamp has no seconds field. A deadline set in the Canvas web UI does: the end-of-day picker stores =2026-09-10T03:59:59Z=, which pull writes as =<2026-09-09 Wed 23:59>= because that is all the file can say. =org-canvas--diff-values-equal-p= compared the two as exact instants, so the row was a permanent =DUE_AT= divergence with no =(Canvas updated ...)= suffix — pull rewrote the same minute, and the only thing that cleared it was a push, which sends =:00= seconds and moves a live deadline by 59 seconds. The =timestamp= branch now truncates both sides to whole minutes since the epoch (=org-canvas--diff-time-minute=) before comparing. It is a truncation, not a tolerance: =xx:59= and =xx+1:00= render as different minutes in the file and stay drift. Every registered =:type timestamp= property (assignment and calendar dates) goes through this one function, so the rule covers them all. The conflict check and the payload-hash skip are untouched — they compare =CANVAS_UPDATED_AT= against Canvas's own =updated_at= (seconds on both sides), and the hash is of the local payload alone; the one Org-minute baseline, the =#+LAST_SYNCED= header, already rounds up to the next minute for the same reason.

* The Drift Report Compares Overrides Tables (issue #411)

=org-canvas-diff= compared every registered property and the body, and an override is neither: a per-student extension given in SpeedGrader moved the column's =updated_at= and nothing the report compared, so the row read CHANGED with "no compared property differs", and the extension itself was never named. A read-only GET of the assignment's overrides was the only way to learn what Canvas held. Since #380 a push by heading reconciles the heading's table, so an extension the report could not show was deleted by the next push of that heading — =2 deleted= — had the rows not been copied first. The one Canvas-side edit a by-heading push destroys was the one edit the report could not show.

*A child pass under Assignments, costing no request.* The Assignments list is read with =include[]=overrides= — added through the property registration's =:body-list-params=, the key pages use for =include[]=body= (#83), checked against the spec by the read-parameter contract (#273) — so every assignment arrives with its overrides and the pass makes no request of its own. It is a child check like Module Items (#177) and New Quiz Items (#322), reported in a section named *Assignment Overrides* right after Assignments. Every stamped heading's =#+NAME: overrides= table is parsed by the sync's own parser and each row paired with a Canvas override by the sync's own claim (=org-canvas--override-find-existing=: a section row by its section, a group row by its group, a student row by the same set of students), both declared from sections.el, never required, as diff declares modules' functions (#299). A Canvas override no row claims is EXTRA, and its row says the next push of that heading deletes it; a row Canvas lacks is MISSING, which the next push creates; a claimed override whose dates differ is CHANGED with the dates, compared as the reconcile compares them (#380), so a row the push would not send is not a row that differs. An EXTRA whose dates are the assignment's own says so, since a pull writes no row for it. A stamped assignment whose reply carries no =overrides= key makes the section "could not check", never a course without overrides (Hard Rule 16). A heading a pull marked deleted is left out, as the sync leaves it (#402).

*The rows have their own kind and their heading.* Every row is kind =override=, with its state (=extra=, =missing=, =changed=), its assignment (=:where=, =:assignment-id=, the assignment's =html_url=) and its heading's file and line. So =RET= visits the assignment heading, =b= opens the assignment's page, and =p= pulls the heading — the table is part of it, and the assignment pull writes Canvas's table whole — which is how an extension is adopted without a hand copy. The other verbs refuse: an override is deleted by dropping its row and pushing the heading, so =k= has nothing to add, and an acknowledgment would hide what the next push destroys. The section is excluded as ="assignment-overrides"=. A pull over a heading now removes the table it holds before writing Canvas's, since an assignment with no description left the body, and so the old table, alone, and the fresh table landed under the stale one.

*A push by heading asks before deleting.* The reconcile's delete step takes a confirm flag, which only the by-heading push sets: with overrides Canvas holds that the table lacks, it asks with =y-or-n-p=, naming who loses what, whatever =org-canvas-assume-yes= says — a student's extension is not recoverable from Org once gone — and under =noninteractive= keeps them, since a batch push of one heading has no one to answer and must not delete an override no one has seen. The counts gain a fourth number, the overrides kept, which the closing line names as =N kept that the table lacks= when there are any. =org-canvas-sync-overrides= over the whole file still deletes them without asking, as it always did: the whole-file sync is the deliberate reconcile, and its report is the drift report run before it. A dry run asks nothing, since it sends nothing.

* New Quizzes Join the Drift Report Through Their Pull-Only Entry (issue #313)

New Quizzes had no feature-registry entry -- their API is the separate quiz service, and #292 and #297 kept them out so the drift report, the orphan scan and prune would not list them at the course API's endpoint -- so nothing reported a New Quiz built in the web UI (no EXTRA row, and so no =p= to pull it, #295's verb), and nothing compared a New Quiz's settings or the instructions #309 taught the pull to write.

*The pull-only entry opts in; the registry stays as it was.* =org-canvas-register-pull-feature= accepts =:drift-report=, and the New Quizzes entry declares it. =org-canvas--diff-features= is the feature registry followed by every pull-only entry that declares it, and =org-canvas--diff-collect-results= walks that list, so the quizzes go through the same =org-canvas--diff-feature= as everything else: listed through the entry's =:list-url-fn= (=api/quiz/v1/courses/:id/quizzes=), paired on =CANVAS_ASSIGNMENT_ID=, with CHANGED, MISSING, EXTRA, UNCLAIMED and PENDING rows, acknowledgments and exclusion by name. No second drift pass was written: the entry already carried everything the pass needs, and the only thing the shared code lacked was an =:id-field= that is a list, =(assignment_id id)= since #309, which =org-canvas--diff-remote-index= and =org-canvas--diff-unclaimed= now read through =org-canvas--item-id-value=. The orphan scan and prune read only =org-canvas--feature-registry=, so they still never see a New Quiz (Hard Rule 13's resolvers are what the report calls). The row verbs look a row's feature up through =org-canvas--diff-find-feature=, which knows the entry too: =p= on an EXTRA row reaches =org-canvas--pull-new-heading= and the #297 single-item pull, =k= and =org-canvas-diff-delete-rows= (#345) read and delete at the entry's =:item-url-fn= (the quiz service, as =org-canvas-delete-all-new-quizzes= does), refusing a quiz with a submission or score through the assignment's check, since the row's id is the assignment's, and =b=/=B= assemble the assignment pages #292 registered for the file (=org-canvas--diff-web-entry=), since the quiz service sends no =html_url=. =RET= on an EXTRA row now falls back to that assembled page as well, for every feature, rather than refusing a row whose reply carried no address.

*The instructions are the body.* The New Quizzes property registration names =:body-api-key "instructions"= and =:body-fn org-canvas--new-quiz-body-html=, which exports the text above the first item exactly as =org-canvas--new-quiz-parse-entry= does, so the report compares what a push would send, as text (#83). #309 made a pull of that text a fixed point, so a pull clears the row it answers.

*A setting is compared only where the reply carries it.* At #313 the push sent =time_limit=, =shuffle_answers=, =one_at_a_time=, =allowed_attempts= and =scoring_policy= at the top level of the quiz and the pull read them there, a shape no live reply had confirmed, so each spec declared =:compare-p= from =org-canvas--new-quiz-remote-carries=: compared when the reply held the key the push and pull used, silent when it did not (Hard Rule 18). #321's probe showed that key is never there; the settings now read from =quiz_settings=, compared wherever the reply carries that object (below).

*A New Quiz is not also an Assignments EXTRA.* Every New Quiz is an assignment, the assignments list holds them all, and =assignments.org= claims none, so each one -- synced or not -- was already an EXTRA row under Assignments. With a section of their own that is the same object reported twice. =org-canvas--diff-apply-new-quiz-assignments= runs after the other post passes and takes out of the Assignments extras every id the New Quizzes list holds, counting them as =:covered=, which the footer's "Not checked" line names beside the =:skip-fn= counts. It acts only when both lists were read; with New Quizzes excluded or failing, the rows stay as before. It is a report-only move, and it agrees with what prune and the orphan scan do since #319: they leave a New Quiz's assignment alone (=org-canvas--assignment-owned-p=, declared as the assignments feature's =:delete-skip-fn=, not its =:skip-fn=, so the drift report still reads every assignment). The report hides it only where the New Quizzes section reports the quiz instead, so a New Quiz is never an EXTRA offered for deletion twice; with that section excluded or unread, it stays an Assignments EXTRA, as #319 intends, and =k= on it names the New Quiz that owns it, as =org-canvas-diff-delete-rows= refuses it (#366, in the #345 entry).

*Items are not compared yet.* The items under a quiz need a request per quiz and their own pairing (=CANVAS_ITEM_ID=, a title read from the item body), and their rows would need verbs that know the parent quiz, as module items needed =:module-id=. * New Quiz Items in the Drift Report, Paired as the Sync Adopts Them (issue #322)

#313 compared a New Quiz's settings and instructions and stopped there, so an item edited, added or deleted in the web UI left its quiz reading clean. The item pass is the module items' child pass (#177) under a quiz: =org-canvas--diff-children-fns= names =org-canvas--diff-new-quiz-items= for New Quizzes, and its result reports right after them as a section of its own, *New Quiz Items*.

*One request per quiz Canvas still lists.* Only a quiz heading whose =CANVAS_ASSIGNMENT_ID= the quiz list holds is looked into, through =org-canvas--new-quiz-api-endpoint= (=quizzes/:id/items=), as the sync's own item loop does. A reply that is not a list of item objects signals, and the section reads "could not check": a misread list is unknown, never an empty quiz (Hard Rule 16), which would otherwise call every item heading MISSING. The pass fails whole, as the module items' does, rather than quiz by quiz; a partial section would need a way to say which quizzes went unchecked, and one failing read in a course is rare enough to rerun.

*Claims and pairing stay inside the quiz.* An item belongs to one quiz, and the sync PATCHes it at =quizzes/:quiz/items/:id=, so a stamped heading claims only an item of its own quiz; an id it names that its quiz does not hold is MISSING. An unstamped heading is paired with an unclaimed item of its quiz by =org-canvas--new-quiz-item-twin-p=, the predicate the sync adopts a twin with (#179): the item's first paragraph is the heading's title. Headings are taken in file order and each pairs once, as the sync adopts them. Such a pair is UNCLAIMED, with a line saying the next sync adopts it; there is no MOVED row, since the sync never adopts across quizzes. The unstamped headings left over, including those under a quiz not yet pushed, are PENDING. diff.el declares =org-canvas--new-quiz-item-twin-p=, =org-canvas--new-quiz-item-remote-title= and =org-canvas--new-quiz-api-endpoint= and never requires =org-canvas-new-quiz-items=, as #299 declared the modules.el parser.

*What is compared.* The item registration (="new-quiz-items"=) gained what the report needs: =POINTS= reads =points_possible= (=:api-key=), =TYPE= reads =entry.interaction_type_slug= mapped back to the Org spelling (=:remote-fn org-canvas--new-quiz-item-remote-type=), and each is compared only when the reply carries it (=:compare-p=), the #313 reasoning: an item reply of an unconfirmed shape must not flag every item forever (Hard Rule 18). The body is =item_body=, which the Items API nests under =entry=, so the registration names a =:body-remote-fn= (=org-canvas--new-quiz-item-remote-body=), a new optional key =org-canvas--diff-compare-body= reads through =org-canvas--diff-remote-body=; every other feature still reads its body at the top level. The local side is =org-canvas--new-quiz-item-body-html=, the heading and the prompt above the answer list exported exactly as the item parse does (=org-canvas--new-quiz-item-question-text= is now shared by both, and the prompt ends where the item's =TYPE= says, as #335 and #337 made the parse read it; a hot-spot item, which a push refuses since #340, is compared all the same, since its prompt is what a pull writes), offline, compared as text (#83). The answers live in =interaction_data=, whose choice ids every push mints afresh, so they are not compared; that is left for when it bites. =OUTCOME= is a link, never compared. No item carries a conflict baseline, so an item row is never "Canvas updated" and never adoptable (=a= refuses it before looking for a feature).

*Rows that know their quiz.* Every item row carries =:quiz-id= and =:where=, as module item rows carry =:module-id=, and =:container "quiz"=, which the row text uses ("in quiz 'Midterm'"; =org-canvas--diff-container=). A row about a heading also carries =:file=, =:line= and =:heading=, and =RET= finds it the way it finds a PENDING row: an item heading is no feature's own, and titles repeat across quizzes. =k= and =org-canvas-diff-delete-rows= read, snapshot and delete at =quizzes/:quiz/items/:id= (#345's read takes no feature's item parameters, since an item is no feature's own); =b= and =B= open the quiz's assignment page, since an item has none; =p= on a CHANGED or EXTRA item row pulls the whole quiz over its heading (=org-canvas-pull-at-point= on it, which asks first), since a New Quiz pulls whole and its item pull upserts by =CANVAS_ITEM_ID=. Acknowledgments are filed under ="new-quiz-items"=. Nothing in the pass writes (Hard Rule 19).

*An item pulls into a heading and the prompt under it (issue #333).* The item pull used to flatten the whole =item_body= into the =**= heading and write nothing under it, so a question of two paragraphs, a list or an image arrived as one long line. It now writes the layout the parse reads back: the push sends the heading as the body's first paragraph and the text between the drawer and the answer list after it, so the pull splits =item_body= after the =<p>= it opens with (=org-canvas--new-quiz-item-split-body=), writes that paragraph as the heading and the rest, through =org-canvas--html-to-org-with-rewrite=, as the prompt (Hard Rule 22 holds at that chokepoint). A body that opens with no paragraph, or with an empty one, is all heading, as every body was before; a one-paragraph item pulls exactly as it did. The prompt is one region for both sides, =org-canvas--new-quiz-item-prompt-bounds=: the parse reads it, the pull replaces it, and nothing below it is touched, so an existing heading, by =CANVAS_ITEM_ID= or unstamped by its title (#239), is renamed and rewritten in place and keeps its answer list, which the pull used to delete with the rest of the subtree and does not write. A prompt the parse would cut short -- a list, whose first line reads as the start of the answers -- is written as a =#+begin_export html= block of the reply's HTML, which the push sends as it stands. Where the prompt ends is the item's =TYPE='s, one rule for the parse and the pull (=org-canvas--new-quiz-prompt-end-regexp-for=): an ordering item's numbered line ends it as a bullet does (#335), so a numbered list in its prompt goes in the block too, and an essay or file-upload prompt ends at no line (#337), so its list is written as Org and the whole text under the heading is the prompt. Pairing follows the split: =org-canvas--new-quiz-item-remote-title= reads the same first paragraph, so the pull's title match, the sync's twin adoption and the drift report's unstamped pairing agree on what a heading names. Specs pull a two-paragraph item, push its parse, pull that back unchanged, and compare the pushed body with Canvas's as the drift report does, so a pulled item reads clean.
