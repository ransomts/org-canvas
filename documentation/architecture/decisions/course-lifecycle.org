* The Roster Marks Who Left, and Only on Canvas's Word (issue #290)

=org-canvas-pull-people= upserted everyone the roster read returned and, by the pull-only rule, deleted nothing for being absent. A student whose enrollments were deleted therefore kept =ENROLLMENT_STATE: active= for the rest of the term: the roster read asks for active, invited, inactive and completed, and a deleted enrollment is none of those, so the heading was simply never reached again. The only sign was the pull's count (108) disagreeing with the file's (109), and the state was found with a hand script against the enrollments endpoint with =state[]=deleted=. The grading files had got the same rule in #282 (=STATUS: left=); the roster had not.

After the upserts the pull collects, as markers, every heading whose =USER_ID= the roster read did not return (=org-canvas--people-absent-headings=), and reads each one's enrollments on its own: the same course index with =user_id= and every =state[]= Canvas documents (=org-canvas--people-departure-params=). Only that user's rows in a role the roster lists count, whatever else comes back, so an ignored =user_id= cannot mark anyone either. The verdict (=org-canvas--people-departure=) is one of three:

- /departed/: rows exist, and none is in a state the roster read asks for. =ENROLLMENT_STATE= becomes the states Canvas gives (=deleted=, =rejected=), and =DEPARTED= the latest =updated_at=, which is stable, so later pulls rewrite the same value.
- /absent/: no row at all. =ENROLLMENT_STATE: absent=, and =DEPARTED= the pull that first found it so; a heading already =absent= keeps its date.
- /unverified/: a row is in a state the roster asks for (the roster read missed the person), a row is =creation_pending= (enrolled, with no account yet), a row carries no state, or the read failed. Nothing is written, and the closing line names the heading as left unchanged.

Asking the per-person read for every state, the listed ones included, is what makes the third case possible. The issue suggested asking for =deleted=, =completed= and =inactive= only; with that, a roster read that came back short would have sent every missing person's read back empty and marked them =absent=, which is Hard Rule 16's misread-list-as-empty mistake one level down. Asking for everything, a person the roster read dropped comes back =active= from their own read and is left alone. The same rule covers the empty roster: a course always has its teacher, so an empty read with a =people.org= that holds =USER_ID= headings is a misread, and the file is left untouched (the empty-file note, which overwrites, is kept for a file with no person in it). The cost is one request per missing heading on every pull, departed ones included, which is a handful in a term and lets a state change (=rejected= to =deleted=, a re-enrollment) show up without a special path; a person listed again is upserted as before and loses =DEPARTED=.

The departures go in the closing line, one per heading with its state and date, as the issue asked, since a departure nobody reads about is the silence the issue was about. Nothing downstream changed how it resolves a name: a departed heading still carries its =USER_ID=, a grading file or an override written against it still means that person, and hiding it would turn "left the course" into "not found". Instead =org-canvas-validate= warns (=org-canvas--validate-departed-people=, reading =org-canvas--people-departed-state-p= from core) when an override row, an accommodations row or a message's =TO= names someone whose state lists neither =active= nor =invited=; the override and accommodation warnings are push-only, like their not-found siblings.

People is pull-only and deliberately not a registered feature — registering it would put the roster in the drift report, the orphan scan and prune — so its read parameters live in the module's own constants. The contract fixture gained a =pull_only= entry for =list_enrollments_courses= (=PULL_ONLY_READ_OPS= in the generator), and the read-parameter contract checks both reads against it, =user_id= included (Hard Rule 13's check, without the registry).

* A List Pull Marks the Headings Canvas Deleted, on Canvas's Word (issues #392, #399)

A re-pull of a live course reported =Assignments pull complete: 52 items.= while =assignments.org= held 56 headings with a =CANVAS_ID=: four assignments had been deleted on Canvas, and the pull, which upserts what the list returns and nothing else, never reached their headings again. Nothing in the log named them; a count against the API did. #290 had fixed the same shape for the roster only. In a writable course the stale headings were worse than silent: a push PUT to an id Canvas no longer had, and the 404 recovery (=org-canvas--handle-404-retry=) re-created the item under a new id, undoing the deletion without a word.

Every list pull now runs =org-canvas--pull-mark-unlisted= after its upserts: those generated by =org-canvas-define-pull= (announcements, assignment groups, assignments, discussions, grading schemes, group categories, pages, rubrics) since #392, and the pulls with code of their own (classic quizzes, New Quizzes, modules, outcomes, files, calendar events) since #399. It collects, as markers, each stamped heading of the feature's top level whose id the list read did not return — the ids of every item the read returned count as listed, the ones a =:skip-fn= held back included, since those are on Canvas — and reads each one on its own at the registry's item URL with its =:item-params= (Hard Rule 13). The read is =org-canvas--pull-item-read=, which returns the item or =gone= and signals anything else; the verdict (=org-canvas--pull-item-state=) is one of three:

- /gone/: a 404 (=org-canvas--api-not-found-p=, which reads the status off the end of the signalled message; =org-canvas--404-error-p= matches =404= anywhere, an id included, too loose to mark anything on), or a reply whose =workflow_state= is =deleted=. The heading gets =CANVAS_DELETED=, an inactive timestamp of the pull that first found it so, kept on later pulls. The heading and its text stay: the mirror may be the only copy.
- /present/: Canvas serves the item. The list read missed it (or a page's old slug still resolves); nothing is written.
- /unknown/: any other failure, a 403 or a 500 included, logged. Nothing is written.

The closing line names the gone headings with their dates, and the ones left unmarked, as #290's does; each gone heading is also a =gone= record in the pull summary, a section of its own in =org-canvas-pull-all='s report. A heading the list returns again is upserted as before, and the upsert removes =CANVAS_DELETED=: =org-canvas-org-save-sync-state=, through which every pull stamps an id, the hand-written ones included, drops it (#399), as =org-canvas--conflict-pull-local= does for a pull at point or from the conflict prompt, since Canvas answered with the item.

A misread list must never mark anything (Hard Rule 16). Deciding on each heading's own read means a list that came back short costs requests, not headings. The same rule covers the empty list: =org-canvas--pull-emit-empty-file= overwrites, so a list read that came back empty used to replace a file of headings with the "Canvas returned 0 items" note. Now the note is written only to a file holding no heading at all; otherwise the empty list goes through the same per-heading reads, and a course whose items really were all deleted gets every heading marked rather than erased.

"Top level" is =LEVEL=1=, where the pull writes, joined with the property registry's =:query= when that names another level (=org-canvas--pull-gone-query=): assignment groups sync as level-2 headings under a container, and a deleted group there is marked too. Child levels — a rubric's criteria, a quiz's questions — are never matched: they have their own reconcilers, and Hard Rule 16 keeps them unpruned. A feature with no registry entry to read an item from marks nothing, since there is no item URL to ask.

A pull at point (and a pull by name, and the drift report's pull) reads its heading through the same =org-canvas--pull-item-read=: where it used to fail with the 404, it now marks that heading =CANVAS_DELETED=, keeps its text, saves, and says so (#399). It never marks another heading. A pull by name reports the heading's outcome as =deleted=, and =org-canvas-pull-headings= counts those apart from the pulled and the failed. Any other failure still signals.

What a mark means elsewhere:

- The sync skips the heading before parsing it (=org-canvas--sync-skip-deleted=), counted as a skip and named among the skipped titles with "(deleted on Canvas)", so the full sync's summary shows it; a push at point or by name refuses it with a =user-error= saying how to proceed: delete the heading, or remove =CANVAS_DELETED= and its id to create it again. Removing the mark alone brings back the old behaviour, a PUT that 404s and is recovered, which is then the user's explicit choice.
- =org-canvas-validate= warns on a marked heading (=org-canvas--validate-canvas-deleted=). The finding is about the course, not the push, so it is not push-only and a read-only course hears it too. Its checks that pair or count headings across a file leave out a marked heading, and one under a marked heading, by the rule the push skips it with (=org-canvas--sync-deleted-stamp=, the one definition): the duplicate-title check (#164), which paired four deleted assignments with the live twins the instructor had kept and raised three false errors on a live course; the module-item id check; the group weight sum; the assignment count the drop rules are measured against; and the grading-scheme ids a =GRADING_STANDARD_ID= may name (#402). The heading's own warning covers it.
- The drift report's MISSING row adds "a pull marked it CANVAS_DELETED ...". The row still counts as drift: the file and the course disagree until the heading is deleted, and the report must never write (Hard Rule 19).
- =org-canvas-status= shows a "Deleted on Canvas: N" count per file.

=CANVAS_DELETED= is sync state, like =CANVAS_ID= and =CANVAS_UPDATED_AT=, so it is named once in =org-canvas--prop-canvas-deleted= and documented with the common properties rather than registered per feature; #290's =DEPARTED= is a roster word and the roster keeps it.

** The pulls with code of their own (issue #399)

Each custom pull calls the helper once its upserts are done, before it writes the file header and saves, and appends =org-canvas--pull-gone-suffix= to its closing line. The helper accepts either a feature registry name or an entry, and a query naming the headings the list answers for when the default (=org-canvas--pull-gone-query=) would be wrong. Each item URL below was checked against =canvas-openapi3.yaml=:

- /Classic quizzes/: level-1 quiz headings, read at =/courses/:course_id/quizzes/:id=. Questions are never matched.
- /New Quizzes/: level-1 headings by =CANVAS_ASSIGNMENT_ID=, read through the pull-only entry's =:item-url-fn= (=/api/quiz/v1/courses/:course_id/quizzes/:assignment_id=, the New Quizzes API, which the OpenAPI file does not describe). A listed quiz counts under its =assignment_id= or its =id=, which the pull stamps in that order. Items are never matched.
- /Modules/: level-1 module headings at =/courses/:course_id/modules/:id=. Module items are never matched: their reconciler owns them (Hard Rule 16).
- /Outcomes/: level-1 group headings only, at =/courses/:course_id/outcome_groups/:id=, the registry entry's item URL. An outcome is not marked: the pull lists outcomes per group through their links, and one missing from its group's list may have been unlinked or moved rather than deleted, which its own read (=/outcomes/:id=, served after an unlink) cannot tell apart. An outcome under a marked group is skipped by the sync instead, since its create would name a group that is gone: =org-canvas--sync-deleted-note= also answers for a heading one of whose ancestors carries the mark, saying so.
- /Files/: in the =flat= and =hierarchical= modes, every heading with a =CANVAS_ID= at any level (the registry's =LEVEL>0=), read at =/courses/:course_id/files/:id=; the =fresh= mode builds the tree from the list and has nothing stamped to check. Folder headings carry no id and are never read or marked: a folder deleted on Canvas deletes its files, and those are what get marked. The closing line names a file by its link's description.
- /Calendar events/: level-1 headings at the unscoped =/calendar_events/:id= (the registry's =:item-url-fn=), where a deleted event comes back with =workflow_state= =deleted=.

New Quizzes, outcomes and calendar events wrote the empty-file note on an empty list as the macro pulls did, and now write it only to a file with no heading; the other three never did. Every custom sync already runs through =org-canvas--sync-process-entry=, so a marked heading is skipped by a full sync of each; New Quizzes' hand-written push at point refuses one through =org-canvas--sync-refuse-deleted=, the guard the generated at-point runtime uses.

That a deleted item's own read is a 404 (or a deleted state) comes from reading Canvas's controllers, not a live course, for these types as for #392's.

Group categories needed one repair on the way: Canvas serves a category at the unscoped =/group_categories/:id= only, so the course-scoped item URL the registry derived from =:endpoint= 404ed for every category, which would have marked every unlisted one gone. The registry entry now names =org-canvas--group-category-item-url= as its =:item-url-fn=, which also fixes pull at point and the orphan cleanup's delete for them.

* The Institution's Ids Come From the User Records (issue #543)

An instructor filling an office form or a registrar request needed a student's university number, and the only way to get it was a one-off script against the users API: the roster pull asked for `sis_user_id` and `login_id` on the enrollment rows' embedded user objects, where Canvas puts a name only, so the properties the identifiers option promised never appeared. The ids live on the user records `courses/:id/users` returns, gated on the token's role; the pull now reads them there and stamps =SIS_USER_ID= and =LOGIN_ID= into the drawer, and `scripts/org-canvas person NAME-OR-USER-ID` prints one person's entry from the file.

- *The identifiers read runs only when the properties will be written.* `org-canvas--people-with-identifiers` fetches the course's user records only while `org-canvas-people-include-identifiers` is set and the roster read returned someone: a pull not writing the ids reads none, so the opt-out costs no extra request and fetches no sensitive data. The roster's own grouping is untouched — it still comes from the enrollments index, whose `state[]` filtering the departure machinery (#290) is built on; replacing it with `include[]=enrollments` on the users read would have re-asked a settled question to fetch data the pull already had.
- *An omitted field leaves the property out, on a fresh heading and on a re-pull.* Canvas returns each id only for a token whose role may see it, and sends null for a user the institution has not given one; either way the property is left out entirely — never an empty value — and a re-pull removes one Canvas stopped returning, so the drawer reflects the last pull the way =ENROLLMENT_STATE= does. Turning the option off stops writing them but erases nothing: the file is the instructor's to manage, as the Personal Data note says.
- *The lookup reads people.org, not Canvas.* `person` prints the drawer's own facts — name, user id, role, sections, enrollment state, and the ids when the pull wrote them — so it needs no credentials and no network, works where the roster is already pulled, and reports an identifier the pull did not write by naming the option that asks for it. A name resolves against people.org's titles, or a user id (5001 or #5001); a title two people share is an error naming both ids, the same rule the gradebook's student report (#542) settled.

* Write Access Is Scoped by the Credentials File, Not the Course (issue #550)

`org-canvas-read-only` refused every write for a whole course and was the only granularity offered, while the multi-instructor workflow recommends dividing a course by Org file and nothing enforced it: any credentials file that could write at all could write everything. `org-canvas-write-allowlist` — set in `org-canvas-credentials.el`, which is already one file per person — names the files (by basename) and features (the word "submissions") that identity may write. An empty or absent list scopes nothing: `org-canvas-read-only` stays the zero-entry case, and setting it beside a non-empty list refuses everything regardless, since the two do not combine into an exception.

- *The check sits at the command and sync layer, the one exception to #163's transport placement.* The reason is in the routes: scoping by Org file does not map onto them, because a grading push writes through `assignments/:id/submissions/:user_id` and a module item's PUT targets its module — only the command about to push knows which file the write belongs to. `org-canvas--check-write-scope` and `--check-write-feature` (core-api, beside `org-canvas--check-writable` but never called from it) are invoked where that is known: the sync pipeline and the push-at-point runtime every macro-generated command funnels through, the custom-loop commands (settings, overrides, quiz accommodations), the delete runtimes, orphan cleanup, the publish commands, the drift report's `k`, and the grading push paths. The whole-course transport guard is unchanged and still catches anything a future ungated command sends on a read-only course.
- *Grading is separated from content by command, not by route.* The issue's crux: a grader can write submissions without owning `assignments.org`, because the boundary the package already draws is the command — `org-canvas--submissions-push-current` and its kin write a column's submission resource, `org-canvas-sync-assignments` writes the column, and the allowlist inherits that boundary. A route-level check would need a `/submissions/` path convention to tell them apart.
- *A sync skips a refused file; it does not abort.* `org-canvas--safe-sync` catches `org-canvas-write-scope-error` (a child of the read-only error, so handlers written for "this course may not be written" cover it) ahead of its `error` clause, logs `[Skip]` with the refusal, counts a `:skip` rather than a `:fail` in the global summary, and the run carries on; `org-canvas-delete-all` and orphan cleanup skip the same way. The refusal names the file and where to grant it — add it to `org-canvas-write-allowlist` in `org-canvas-credentials.el` — and reads are never refused, so pull, status, diff and validate work for a scoped identity exactly as before.
- *The command-layer choice fails open at the transport, and the corners are closed by hand.* A future write command that forgets the check would write on a writable course, the cost of the route-mapping argument; the reads-only corners that can be closed are. A buffer visiting no file can be named by no entry and is refused while a list is set. Conversations are deliberately out of scope — they are mail, not course content. And `org-canvas-activate-course` clears the allowlist before loading the next course's credentials, so a file that does not mention scoping cannot inherit another course's; `org-canvas-read-only` has the same leak and is left as it is, since it fails closed and is the owner's call to change.

* A Semester Rollover Strips What the Registries Name (issue #547)

Carrying a course into its next semester was a shell pipeline in the workflows guide: copy the directory, hand-edit the credentials file, then a `sed` over every file deleting the stamps the sed's author thought of.  A stamp invented after that list was written survived it — `CANVAS_DELETED` (#392) did exactly that, and a heading still marked deleted is skipped by the next push, so a course copied with one never re-creates that heading.  `org-canvas-new-semester` is the rollover as a command, and its stamp list is not written down anywhere: it is the same registry union a delete clears (`org-canvas--delete-cleared-property-names`, #331) plus the deleted mark, so a stamp registered by a later module joins the strip the moment its module loads.

- *The stamp set is the delete machinery's, plus the deleted mark.* The property registry (`org-canvas-register-properties`) declares content properties, not stamps; the stamps a rollover must clear are the pipeline's own names (`CANVAS_ID`, `CANVAS_URL`, `CANVAS_UPDATED_AT`, `LAST_SYNCED`, `PAYLOAD_HASH`), each feature's `:id-property` and every stamp `org-canvas-register-id-property` names — whose union `org-canvas--delete-cleared-property-names` already computes for a delete — plus `CANVAS_DELETED`, which a delete need not clear (stamping a fresh id clears it) but a rollover must, since it writes no fresh id.  The `#+LAST_SYNCED` file header goes with them.
- *Pull-only reader ids are content, not sync state.* `CANVAS_ENTRY_ID` on a discussion reply, `USER_ID` on a person, `BANK_ID` on a bank: these name what the old course held, but nothing pushes from them, so they cannot point the first sync of the new semester at the old course — the harm the rollover exists to prevent.  They are the file's record of history, the way `AUTHOR` and `POSTED_AT` are, and stripping them would need exactly the hand-kept "which of these count" list the command exists to retire.  They stay; a fresh pull rewrites them.
- *A dry run by default, and Org's own API for the edit.* The report names every heading it would strip, the new course ID and the credentials retarget, and nothing is written until `org-canvas--confirm` answers yes.  The strip runs through `org-entry-delete` (the API the delete machinery uses), so drawers, bodies and spacing survive as their author wrote them — nothing sed-like.  The credentials file is Elisp a user may have edited by hand, so the retarget is a line edit of the two `setq` lines (course id, directory — a copy's file still pins the old semester's path), with the token and any comments kept where they sit; the file is then loaded, so the running session points at the new course.
- *A local transform, never a sync command.* It is deliberately absent from `org-canvas-dry-run--sync-commands`: Hard Rule 1 exists to keep every command that writes to Canvas previewable, and this one sends nothing to Canvas at all — its own dry run is the preview.  Dates and section names stay with the editor, as the issue allows; `org-canvas-validate`'s past-date warnings are the check on that half.

* Student Data Is Kept Out of Git by the Pull That Writes It (issue #549)

People.org, groups.org and gradebook.org hold student names or scores, and until #549 their only protection was a comment in each module and a sentence in the manual: "keep it out of a course repository." A shared course repository was one forgotten `git add .` from a FERPA problem, and the tool knew better — coverage.org's table says which pulls write student data. Now one list, `org-canvas--student-data-files` in core-config beside the registries, names the files, and every pull that writes one runs `org-canvas--student-data-ignore` on it: outside a git work tree (or without git) nothing happens and nothing errors, an already-ignored file is left alone, an already-tracked one gets a warning naming `git rm --cached` (a .gitignore does not untrack), and everything else gets the file's name added to the .gitignore beside it. The wizard offers the same lines beside the credentials file.

- *A defconst of names, not a `:student-data` flag on the features.* The issue offered both shapes. The flag loses: the writers of these files are pull-only readers outside the feature registry — the roster, the groups, the gradebook, the discussion replies have no feature entry, by design, since the drift report and the orphan scan have nothing to say about them — and the files under the submissions directory (quiz attempts, peer reviews, grading files) have no one name at all, one file per assignment. A list of names is what every consumer shares: the wizard writes the lines, the guard takes a file, and a pull that joins the covered table with student data joins the list.
- *The guard adds the line; it does not only warn.* The acceptance criteria name the wizard's suggestion and the tracked-file warning, and a warn-only guard satisfies both — but it leaves a fresh pull's people.org sitting untracked and unignored in a work tree, which is exactly the `git add .` leak the issue opens with, whenever the course was set up without the wizard. The add-and-warn behavior is #452's `org-canvas--gradebook-ignore-scores` generalized (its three private git helpers became `org-canvas--git`, `org-canvas--gitignore-append` and `org-canvas--student-data-ignore` in core), and the submissions directory — the pattern the issue says already works — is the precedent: protection at write time, not at setup time. The wizard still offers the lines, so a course whose pulls have not run yet is covered too.
- *The submissions directory stays its own case.* It gets its own .gitignore, excluding everything in it, when created (`org-canvas-submissions-write-gitignore`, unchanged); the list's `submissions/` line is the wizard's belt-and-braces for when that option is off or the directory has not been created yet. Its tracked-file warning is directory-wide rather than per file — `git ls-files --error-unmatch -- .` from inside it — because per-assignment filenames cannot be named in advance, one warning covers the grading files, quiz attempts and peer reviews alike, and the remedy (`git rm --cached`) is directory-wide anyway.
- *Gradebook-scores.eld keeps the guard it already had.* #452 guarded it through the gradebook's private helpers; it is one of the list's names now and `org-canvas--gradebook-write-scores` calls the shared guard, so a customized `org-canvas-gradebook-scores-file` outside the course directory is still protected — the guard follows the file it is handed, not the default name.

* A Delete-All Snapshots What It Is About to Delete (issue #555)

`org-canvas-delete-all` counted the synced items, asked twice, and deleted every content type in reverse-tier order — and wrote nothing down. The Org files recover the synced half (a re-push recreates it); what nothing recovers is Canvas-only material, an item a web-UI collaborator made that no heading claims. The drift report's batch delete (#345) already had the answer — write the JSON before the DELETE — and the nuke command was the one place the pattern was needed most and absent.

- *One file per feature's run, written by the drift delete's own writer.* `org-canvas--delete-all-snapshot` (core-delete) writes the run's pending items — the listing as Canvas returned it, what `:skip-fn` protects excluded, since those stay — through `org-canvas--diff-snapshot-write`, so the file is `<time>-<feature>-all.json` under `org-canvas-diff-delete-snapshot-directory` (default `canvas-snapshots/` under the course directory) holding one pretty-printed JSON array: the same writer, directory, naming and encoding, not a second format. It holds the list reply rather than the single-object GET #345's delete reads, because a delete-all has no guard to feed and the listing is already in hand; the file records what Canvas held. The custom delete-alls (files, rubrics, outcomes, New Quizzes) call the same helper beside their own listings, so every tier the global command runs is covered — files' folders are paths, not content, and stay out.
- *The snapshot belongs only on the path that deletes.* #550's scope check fires in each feature's runtime before anything is listed, so a refused run never reaches the write: no file claims a delete a scoped identity was refused from making, and a permitted run writes exactly one. A course marked `org-canvas-read-only` writes none either (its DELETEs fail at the transport), and an empty listing writes none — nothing about to go, nothing to record.
- *The completions name it.* Each feature's own message says where its JSON is ("3 removed; its JSON is in …", the path travelling from `org-canvas--delete-all-items` to `org-canvas--delete-all-runtime` through a binding that starts nil every run, never a lingering global), and the global command names the snapshot directory its features wrote under. The double confirmation is unchanged: the snapshot follows both answers rather than replacing one.

* The Shell Reaches the Live Search, and the Orphan Scan Reports First (issue #554)

`diff` let a CI job exit non-zero on drift but nothing let it grep the course for the stale value behind it: `org-canvas-search-live` and `-dates` (#406) were Emacs-only, printing under `--batch` but reachable only through a hand-written `--eval`. `scripts/org-canvas search REGEXP` and `search-dates` wrap them, the report on standard output exactly as the commands print it under `--batch` — no new read, no new parameter, the same walk. `cleanup-orphans` joins them behind the same dispatch.

- *A search exits 0 whatever the hit count.* It is a read, not a check: the report's closing line names the count, and a shell wrapper that wants grep-like semantics counts it. `diff` exits 1 on drift because it compares against something; a search's hits are the answer, not a failure, and exiting 1 on a hit would page whoever ran it to look.
- *The orphan report is the default; the delete is behind `--yes`, like `delete`.* Where `delete` refuses an unconfirmed batch run outright, `cleanup-orphans` runs the scan — it is all GETs — and prints the report, deleting nothing: the scan is the useful half from cron, and `org-canvas--orphan-confirm` (`org-canvas-orphans-confirmed`, modelled on `org-canvas-delete-confirmed` so only that one question is answered) declines in batch with a line naming the flag. A `--dry-run`, before the command or after it, forces the report alone even beside `--yes`.
- *A failed delete exits 1.* `org-canvas--orphan-delete-all` now returns how many deletes failed (each still logged, the next item still tried; a feature outside the write allowlist is a skip, not a failure, as a sync skips its file #550), and the command and the shell wrapper thread it to their status.
- *Messages stay Emacs-only, deliberately.* Sending mail from cron is a footgun the issue names, and no `messages` subcommand exists.
