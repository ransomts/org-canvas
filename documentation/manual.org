* Introduction

org-canvas synchronizes Org Mode files with Canvas LMS. Each course content type has its own Org file, and the package manages bidirectional sync via the Canvas REST API.

The primary workflow treats Org files as the "source of truth" -- you design your course entirely in Org Mode and push changes to Canvas. For instructors with existing Canvas courses, =org-canvas-pull-all= imports the entire course into Org files. The package tracks sync state via properties (=CANVAS_ID=, =LAST_SYNCED=) so it knows whether to create new items or update existing ones, and detects conflicts when items are modified directly in Canvas.

* Getting Started

** Prerequisites

- Emacs 28.1 or later
- Org Mode 9.6 or later
- [[https://github.com/magit/transient][transient]] 0.4+ (built into Emacs 29+)
- A Canvas LMS instance with API access
- A Canvas API token (generate from Account > Settings > Approved Integrations)
- [[https://pandoc.org/][pandoc]] (optional) -- required for HTML-to-Org conversion when pulling content from Canvas

** Configuration

The easiest way to set up a new course is the setup wizard:

#+begin_src elisp
M-x org-canvas-init
#+end_src

The wizard prompts for your Canvas URL, API token, and course ID.  It:

- Tests the connection before saving
- Writes =org-canvas-credentials.el=
- Warns before overwriting an existing credentials file
- Validates the URL starts with =https://=
- Offers to create or update =.gitignore= to protect credentials
- Optionally generates skeleton =.org= files for all content types

Or create =org-canvas-credentials.el= manually in your course directory:

#+begin_src elisp
;;; org-canvas-credentials.el --- Canvas API credentials  -*- lexical-binding: t; -*-

(setq org-canvas-api-token "your-canvas-api-token-here")
(setq org-canvas-course-id "12345")  ; Found in your Canvas course URL
(setq org-canvas-base-url "https://your-institution.instructure.com")
(setq org-canvas-directory "/path/to/your/course/")

(provide 'org-canvas-credentials)
;;; org-canvas-credentials.el ends here
#+end_src

*Important*: Add =org-canvas-credentials.el= to =.gitignore= to avoid committing your API token.

** Testing Connection

#+begin_src elisp
M-x org-canvas-test-connection
#+end_src

On failure, specific error messages indicate the cause:

| Error               | Meaning                                   |
|---------------------+-------------------------------------------|
| HTTP 401            | API token expired -- regenerate it        |
| HTTP 403            | Token lacks required scope                |
| HTTP 404            | Course ID not found                       |
| Network error       | URL wrong or no internet connection       |

This prints your course name if the connection is successful.

* Sync Order and Dependencies

** Dependency Graph

Course files can contain links to other course files. For example, an assignment may reference a rubric, an assignment group, or link to a page for instructions. These links are resolved during sync to obtain Canvas IDs.

#+begin_src mermaid
graph TD
    %% ── Source files (with outgoing links) ──
    modules["modules.org"]
    assignments["assignments.org"]
    discussions["discussions.org"]
    quizzes["quizzes.org"]
    nq["new-quizzes.org"]
    overrides["overrides tables<br/>(in assignments.org)"]

    %% ── Target files (receiving links) ──
    ag["assignment-groups.org"]
    rubrics["rubrics.org"]
    gc["group-categories.org"]
    outcomes["outcomes.org"]
    pages["pages.org"]
    files["files.org"]
    sections["sections.org"]
    announcements["announcements.org"]

    %% ── Property links (resolved to Canvas IDs during sync) ──
    assignments -->|"GROUP"| ag
    assignments -->|"RUBRIC_LINK"| rubrics
    assignments -->|"GROUP_CATEGORY_ID"| gc

    discussions -->|"GROUP"| ag
    discussions -->|"RUBRIC_LINK"| rubrics
    discussions -->|"GROUP_CATEGORY"| gc
    discussions -->|"SPECIFIC_SECTIONS"| sections

    quizzes -->|"ASSIGNMENT_GROUP"| ag

    nq -->|"RUBRIC_LINK"| rubrics
    nq -->|"GROUP"| ag
    nq -.->|"OUTCOME (local only)"| outcomes

    rubrics -->|"criterion OUTCOME"| outcomes

    %% ── Module item links (heading links resolved to content IDs) ──
    modules ==>|"item heading"| pages
    modules ==>|"item heading"| assignments
    modules ==>|"item heading"| quizzes
    modules ==>|"item heading"| discussions
    modules ==>|"item heading"| files
    modules ==>|"item heading"| announcements

    %% ── Override table links (section references in date tables) ──
    overrides -->|"table row"| sections
#+end_src

Three types of cross-file links appear in the diagram:

- *Property links* (thin arrows): An Org property like =:GROUP:= contains a =[[file:...]]= link. During sync, the link target's =CANVAS_ID= is read and included in the API payload.
- *Module item links* (thick arrows): Level-2 headings in =modules.org= that are file links. The linked heading's =CANVAS_ID= (or =CANVAS_URL= for pages) becomes the module item's =content_id=.
- *Override table links* (thin arrows from "overrides tables"): Rows in =#+NAME: overrides= tables within =assignments.org= link to sections. The section's =CANVAS_ID= becomes the override's =course_section_id=.
- *Local-only links* (dashed arrow): The =OUTCOME= property on new-quiz items points to =outcomes.org= for validation but is not sent to Canvas (outcome alignment uses a separate API).

In addition, *body text* in assignments, discussions, announcements, pages, calendar events, and settings can contain inline =[[file:...]]= links. These are resolved to Canvas URLs during HTML export (e.g., a link to =pages.org::*Syllabus= becomes =https://canvas.example.com/courses/123/pages/syllabus=).

** Sync Tiers

Files are synced in tiers based on their dependencies:

*** Tier -1: Course Level

| File           | Canvas Entity   | Notes                         |
|----------------+-----------------+-------------------------------|
| =settings.org=   | Course Settings | Timezone, homepage, license   |

Settings are synced first because they configure the course environment that other content depends on.

*** Tier 0: No Dependencies

These files have no outgoing links to other course files:

| File                  | Canvas Entity     | Notes                         |
|-----------------------+-------------------+-------------------------------|
| =outcomes.org=          | Learning Outcomes  | Groups (L1) and Outcomes (L2) |
| =rubrics.org=           | Rubrics            | Grading rubrics (criteria may link to outcomes) |
| =assignment-groups.org= | Assignment Groups  | Weight categories             |
| =group-categories.org=  | Group Categories   | Group sets for group work     |
| =pages.org=             | Wiki Pages         | Course content pages          |
| =files.org=             | Files              | Binary file uploads           |
| =discussions.org=       | Discussions        | Discussion topics             |
| =announcements.org=     | Announcements      | Course announcements          |
| =calendar.org=          | Calendar Events    | Office hours, holidays, etc.  |
| =sections.org=          | Sections           | Course sections               |

*** Tier 1: Depends on Tier 0

| File            | Depends On                                       |
|-----------------+--------------------------------------------------|
| =quizzes.org=     | assignment-groups.org, outcomes.org               |
| =new-quizzes.org= | rubrics.org, assignment-groups.org                |
| =assignments.org= | rubrics.org, assignment-groups.org, outcomes.org |
|                 | pages.org, files.org                             |

*** Tier 1.75: Depends on Tier 0 + 1

| File           | Depends On                     |
|----------------+--------------------------------|
| =sections.org=   | sections (Tier 0), assignments |
| (overrides)    | quizzes (from Tier 1)          |

Per-section date overrides are defined as tables in =assignments.org= and require both sections and assignments to exist first.

*** Tier 2: Depends on Tier 1

| File        | Depends On                                    |
|-------------+-----------------------------------------------|
| =modules.org= | assignments.org, quizzes.org, discussions.org |
|             | pages.org, files.org                          |

** Automatic Sync Order

The =org-canvas-sync= function syncs files in proper dependency order:

1. =settings.org= (Tier -1) - course settings and navigation tabs
2. =outcomes.org= (Tier 0)
3. =rubrics.org= (Tier 0)
4. =assignment-groups.org= (Tier 0) - first pass, without drop rules
5. =group-categories.org= (Tier 0)
6. =sections.org= (Tier 0) - course sections
7. =files.org= (Tier 0)
8. =pages.org= (Tier 0)
9. =discussions.org= (Tier 0)
10. =announcements.org= (Tier 0)
11. =calendar.org= (Tier 0)
12. =quizzes.org= (Tier 1)
13. =new-quizzes.org= (Tier 1)
14. =assignments.org= (Tier 1)
15. =assignment-groups.org= (Tier 1.5) - second pass, with drop rules
16. Per-section overrides (Tier 1.75)
17. =modules.org= (Tier 2)

*Note*: Assignment groups are synced twice because Canvas rejects drop rules for groups with no assignments. Per-section overrides require both sections and assignments/quizzes to exist.

*** Navigation Tabs

Control the order and visibility of sidebar navigation tabs using a =** Navigation= sub-heading under the course heading.  Items in strikethrough (=+Tab+=) are hidden from students.

#+begin_src org
,** Navigation
1. Home
2. Modules
3. Assignments
4. Announcements
5. Grades
6. +Discussions+
7. +People+
#+end_src

Tabs are matched case-insensitively against the Canvas tab labels.  The "Home" and "Settings" tabs cannot be hidden (Canvas does not allow it); a warning is logged if you try.  Only tabs that differ from the current Canvas state are updated.

*** Course Card Image

Set the Dashboard thumbnail for the course using the =COURSE_IMAGE= property:

#+begin_src org
:COURSE_IMAGE: [[file:images/banner.png]]
#+end_src

This uploads the local image to Canvas and sets it as the course card image.  You can also use a direct URL:

#+begin_src org
:COURSE_IMAGE: https://example.com/images/banner.png
#+end_src

*** Inline Images

Image links in page, announcement, discussion, and assignment body text (=[[file:diagram.png]]=) are automatically uploaded to Canvas and replaced with preview URLs during sync.  Supported formats: PNG, JPEG, GIF, SVG, WebP, BMP.

Images are uploaded to a Canvas folder named =org-canvas-images/= and cached per sync session to avoid re-uploading unchanged files.

*** Publishing and Point Totals

Canvas computes a classic quiz's =points_possible=, its =question_count= and the
points on its backing gradebook column when the quiz is *published*, not when a
question is added.  org-canvas therefore creates a quiz unpublished, syncs its
questions and question groups, and publishes it last, so publishing is a real
transition and the totals are computed with the questions in place.

This matters because the failure it prevents is invisible: a quiz published
while still empty keeps =points_possible: 0= and a gradebook column out of 0,
while every question still shows its own point value in the Canvas editor.

The same applies when an already published quiz gains a question.  After
syncing questions, org-canvas checks whether Canvas's counts still match what
it wrote, and if they are behind it republishes to regenerate them.  A quiz
that already has submissions cannot be unpublished, so in that case it reports
the discrepancy and leaves the quiz alone -- open it in Canvas and save to
regenerate the totals by hand.

*** Question Groups (Question Banks)

Question groups randomly select questions from an external question bank at quiz delivery time.  They appear as level 2 headings with ~TYPE: group~.

**** Workflow

1. Create a question bank externally (e.g., using [[https://github.com/gpoore/text2qti][text2qti]] to convert Markdown to QTI)
2. Import the QTI file into Canvas via Settings > Import Course Content
3. After import, find the bank ID in the Canvas UI URL (e.g., =courses/123/question_banks/42= means bank ID is 42)
4. Add a level 2 heading under your quiz with the properties below

**** Question Group Properties

| Property             | Type   | Description                                    |
|----------------------+--------+------------------------------------------------|
| =TYPE=               | string | Must be =group=                                |
| =PICK_COUNT=         | number | Number of questions to randomly select (default 1) |
| =QUESTION_POINTS=    | number | Points per selected question (default 1)       |
| =QUESTION_BANK_ID=   | number | Canvas assessment question bank ID (optional)  |

**** Limitations and Caveats

- *Bank ID is create-only*: ~assessment_question_bank_id~ is accepted on POST but ignored on PUT.  To change the bank, delete the group from Canvas and remove ~CANVAS_ID~ from the heading, then re-sync.
- *Bank ID must be obtained manually*: Canvas has no public API for listing question banks.  Get the ID from the Canvas UI URL after QTI import.
- *Invalid bank IDs are silently accepted*: Canvas creates the group without linking to a bank.  Verify the bank exists in Canvas before syncing.
- *Pull does not import groups*: There is no "list all groups" endpoint, so ~org-canvas-pull-quizzes~ cannot discover existing groups.
- *Bank questions are invisible via API*: Questions from banks are resolved at quiz delivery time and do not appear in the Quiz Questions API response.
- *Classic Quizzes only*: This feature is for Classic Quizzes.  New Quizzes uses a separate "item banks" system with a different API.

*** What a Change Costs

Canvas has no endpoint that replaces a file's bytes in place, so a content
change means deleting the Canvas file and uploading a new one -- which mints a
new file id.  Anything that referenced the old id breaks: a link typed into a
Page or Announcement body, a syllabus link, a student's bookmark.  Module items
are repaired within the same run; nothing outside the managed Org files is.

Everything else is one =PUT= and keeps the id.  Renaming a heading, moving a
file to a different folder, flipping =PUBLISHED= or =HIDDEN=, changing the
dates or the usage rights -- none of those re-upload anything.

org-canvas tracks the two halves separately in =PAYLOAD_HASH=, which is stored
as =BYTES:METADATA=.  An entry whose whole hash matches is skipped; one whose
bytes match is updated in place; only a genuine content change re-uploads.
Entries synced before this split carry a single hash and re-upload once more,
after which they too carry both halves.

Before either kind of write, a file that already exists on Canvas is checked
for remote modification, and a file changed in the Canvas web UI opens the same
diff prompt as any other conflict.  Choosing *pull* there overwrites your local
copy with the one Canvas is serving.

*** Visibility

Canvas gives a file three visibility states, not two, and they are carried
by two independent flags:

| State in the Canvas UI                    | =PUBLISHED= | =HIDDEN= | Canvas fields          |
|-------------------------------------------+-----------+--------+------------------------|
| Published                                 | =true=      | =false=  | neither set            |
| Unpublished                               | =false=     | —      | =locked: true=           |
| Only available to students with the link  | =true=      | =true=   | =hidden: true=           |

The unlisted state is weaker than it looks: the file is not listed in the
Files tab, but Canvas still serves it to anyone holding the URL.  Use
=PUBLISHED: false= when you mean "students must not have this yet".

Both flags are sent on every sync, in both directions, so flipping either
property back and forth is a true toggle.  =UNLOCK_AT= and =LOCK_AT= are sent
only when present: deleting one of those properties leaves the date already
stored on Canvas alone, so clear it there if you need it gone.

The upload endpoint itself accepts none of this — Canvas discards
visibility fields sent with the upload — so org-canvas applies them in a
follow-up request once the upload lands.  A failure there leaves the entry
dirty on purpose, so the next sync retries the settings rather than
reporting a file as synced with the wrong visibility.

* Link Resolution

Properties like =GROUP= and =RUBRIC_LINK= can contain Org links to headings in other files. During sync, these links are resolved to Canvas IDs.

** Resolution Process

1. Parse the file path and heading name from the link
2. Open the referenced file
3. Find the heading matching the name
4. Read its =CANVAS_ID= property

* Conflict Detection

When pushing content to Canvas, org-canvas can detect if an item was modified directly in Canvas since your last sync.  This prevents silent overwrites of changes made by TAs, co-instructors, or the Canvas UI.

** How It Works

Every successful push records the remote =updated_at= Canvas returned, as a
=CANVAS_UPDATED_AT= property on the heading.  That is the baseline: it is
Canvas's own clock, so it needs no allowance for a workstation whose time
differs from the server's, and it exists on courses that are only ever pushed.
Entries synced before it existed fall back to the file-level =#+LAST_SYNCED=
header, which is written after every pull and after every push that changed
something.

There are two checks.

*Before each update*, org-canvas GETs the item, reads its =updated_at=, and
flags a conflict if that is newer than the baseline.  This applies to updates,
not creates, and an entry with no baseline at all (a first sync) is never
flagged.

*Before skipping an unchanged entry*, org-canvas consults a snapshot of the
feature's remote items -- one list request per feature per sync -- and takes
any entry Canvas has touched since the baseline off the skip path, so it goes
through the full comparison instead.  This matters because a matching
=PAYLOAD_HASH= only proves the *local* file has not changed.  Without the
snapshot, an item edited solely in the Canvas web UI was skipped on every
subsequent sync and the two never reconciled; a sync could report =0 failed=
while dozens of items disagreed.

When the snapshot cannot be fetched, the run reports how many entries it
skipped without checking, rather than letting the summary imply a comparison
that did not happen.

** Interactive Resolution

When a conflict is detected, org-canvas opens a =*canvas-conflict*= buffer showing a side-by-side comparison of the local and remote versions:

- Timestamps (local =LAST_SYNCED= vs remote =updated_at=)
- Title differences (if the title changed remotely)
- Body/description preview (truncated to 500 characters)

You then choose an action with a single keypress:

| Key | Action    | Effect                                                   |
|-----+-----------+----------------------------------------------------------|
| =p=   | Push      | Overwrite the remote item with your local version        |
| =l=   | Pull      | Overwrite the local heading with the remote version      |
| =s=   | Skip      | Leave both versions unchanged, move to the next item     |
| =P=   | Push All  | Push this and all remaining conflicts without prompting  |
| =L=   | Pull All  | Pull this and all remaining conflicts without prompting  |
| =S=   | Skip All  | Skip this and all remaining conflicts without prompting  |

The capital-letter variants apply the chosen action to *all subsequent conflicts* in the current sync, so you only need to decide once if you want a consistent policy.

*** Pull Behavior

When you choose *Pull* (=l= or =L=):

1. The heading title is updated to match the remote version
2. The module-specific pull function updates properties and body content (the same function used by =org-canvas-pull-*= commands)
3. =LAST_SYNCED= is refreshed to the current time
4. =CANVAS_UPDATED_AT= is set from the remote response
5. =PAYLOAD_HASH= is deleted (so the next sync will detect the item as changed)
6. The buffer is saved

Pull is available for modules that have a pull-item function: assignments, pages, discussions, announcements, assignment groups, rubrics, group categories, and calendar events.

** Configuration

| Variable                    | Default | Description                              |
|-----------------------------+---------+------------------------------------------|
| =org-canvas-detect-conflicts= | =t=       | Enable conflict detection before pushes  |

** Commands

| Command                | Description                                  |
|------------------------+----------------------------------------------|
| =org-canvas-sync=        | Sync with conflict detection (default)       |
| =org-canvas-force-push=  | Sync without conflict detection (overwrites) |

** Scope

Conflict detection applies automatically to all modules using the shared =org-canvas--push-to-api= helper: assignments, pages, discussions, announcements, assignment groups, and rubrics.  The pre-skip drift check covers every module that runs through =org-canvas-define-sync=, which additionally includes modules and calendar events.  Modules with fully custom sync loops (files, quizzes, new quizzes, outcomes, overrides) are not covered by either.

* Publishing a Week

Releasing content is the most repeated action in running a course, and doing it
by hand means editing =PUBLISHED= in every file that owns a piece of the week:
the module in =modules.org=, its lecture PDFs in =files.org=, the assignments due
that week, sometimes a page.  Six to ten edits across three or four files, every
week for a semester.

** Publishing on Demand

#+begin_src elisp
M-x org-canvas-publish-module RET Week 03 RET
#+end_src

Sets =PUBLISHED: true= on the module and on the heading that owns each object its
items point at, in whichever file that is, then offers to sync.
=org-canvas-unpublish-module= is the reverse.

The publish state is written to the object's own heading, never inferred from
the module at push time.  A module item that has no object behind it -- a
SubHeader or an external URL -- owns its state, so those are set in place.  See
[[*Conflict Detection][Conflict Detection]] for why that distinction matters.

Items whose links do not resolve are named in the report rather than silently
passed over, so a typo in a link surfaces instead of quietly leaving one piece
of the week unpublished.

** Publishing on a Schedule

Give a module a =PUBLISH_AT= and the release plan lives in the file:

#+begin_src org
,* Week 03 (Aug 31 to Sep 4): Ethics II; Networks
:PROPERTIES:
:PUBLISH_AT: <2026-08-31 Mon 06:00>
:END:
#+end_src

Every =org-canvas-sync= applies any release whose date has passed, before the
first feature syncs -- so the objects it publishes are pushed by that same run.
The publish is written into the Org files as ordinary =PUBLISHED: true=
properties, so the files stay the source of truth and re-running changes
nothing.  A whole semester can be authored in August and release itself.

=M-x org-canvas-apply-scheduled-releases= runs the same pass on its own.

Note that =PUBLISH_AT= is org-canvas's own scheduling, not Canvas's: it is never
sent to the API.  A module's =UNLOCK_AT= is Canvas's, and the two are
independent.

* Drift Report

Three commands sound alike and answer different questions.

| Command                   | Question it answers                          | API calls |
|---------------------------+----------------------------------------------+-----------|
| =org-canvas-status=         | What do my Org files say about themselves?   | none      |
| =org-canvas-sync-dry-run=   | What would a sync push?                      | none      |
| =org-canvas-diff=           | Does Canvas match my Org files?              | read-only |

Only the third can see a change made in the Canvas web UI.  A dry run reports
entries whose =PAYLOAD_HASH= changed locally, which is a different set
entirely: an assignment someone published in Canvas has an unchanged hash and
so appears in neither of the first two.

** What It Reports

Per feature:

- *CHANGED* -- the item exists on both sides but they disagree.  The report
  names each differing property with both values, and says so when Canvas's
  =updated_at= is newer than the last sync.
- *MISSING* -- a heading carries a Canvas id the course no longer has.
- *EXTRA* -- an item in the course that no Org heading claims.

Every property a module registers is compared, so this covers =PUBLISHED=,
points, due dates, group weights, drop rules and the rest without a separate
list to maintain.  Two deliberate exclusions:

- Properties *absent* from the Org file are not compared.  An absent property
  means the file expresses no opinion, and each module applies its own default
  at parse time, so treating absence as a value would report differences that
  no sync would act on.
- Link-typed properties (=GROUP=, =RUBRIC_LINK=) are skipped: the Org side is a
  heading link and the Canvas side an id.

** Cost and Safety

One list request per feature.  Nothing is written, locally or on Canvas, so it
is safe to run at any time.

** Scheduled Checking

=org-canvas-diff-batch= exits non-zero when it finds drift, so a course can be
checked routinely rather than only when something feels wrong:

#+begin_src sh
emacs --batch -l /path/to/org-canvas.el -f org-canvas-diff-batch
#+end_src

Wire that into cron and have it mail you the output on a non-zero exit.

* Canvas-to-Org Migration

Instructors with existing Canvas courses can import their entire course into Org files using =org-canvas-pull-all=.

** Quick Start

#+begin_src elisp
;; Import an entire Canvas course
M-x org-canvas-pull-all
#+end_src

This creates (or updates) all =.org= files in your course directory with content pulled from Canvas.  HTML content (page bodies, assignment descriptions, discussion messages, syllabus) is converted to Org format via [[https://pandoc.org/][pandoc]].

** pandoc Dependency

pandoc is required for converting HTML content to Org format.  If pandoc is not installed:

- =org-canvas-pull-all= will prompt whether to continue
- HTML content is stored as raw HTML with a warning comment
- All other properties and metadata are still imported normally

Install pandoc from https://pandoc.org/installing.html or via your system package manager.

** Pull Order

Content is pulled in dependency order so that cross-references can be reconstructed:

1. Settings (course-level configuration and navigation tabs)
2. Sections (course sections)
3. Assignment Groups (grade categories)
4. Group Categories (group sets)
5. Outcomes, Rubrics, Pages, Files, Discussions, Announcements, Calendar Events
6. Assignments (reconstructs GROUP and GROUP_CATEGORY_ID links)
7. Quizzes (fetches questions as sub-headings)
8. New Quizzes (fetches items as sub-headings)
9. Modules (reconstructs cross-file links to assignments, pages, etc.)

** Heading Matching

When pulling, each Canvas item is matched to an existing Org heading by its =CANVAS_ID= (or =CANVAS_URL= for pages).  If no match is found, a new heading is created at the end of the file.  This makes pulling idempotent -- running it multiple times updates existing headings rather than creating duplicates.

** Link Reconstruction

After pulling, cross-file links are reconstructed where possible:

- *Assignments*: The =GROUP= property is set to a link like =[[file:assignment-groups.org::*Labs][Labs]]= by matching the =assignment_group_id= from Canvas to the heading in =assignment-groups.org= with that =CANVAS_ID=.
- *Modules*: Item links are reconstructed by matching the Canvas =content_id= and =type= to headings in the appropriate =.org= file (e.g., =[[file:assignments.org::*Lab 1][Lab 1]]=).

* Orphan Cleanup

When you remove a heading from an Org file, the corresponding Canvas item is not automatically deleted.  The orphan cleanup command finds these stranded items.

** Usage

#+begin_src elisp
M-x org-canvas-cleanup-orphans
#+end_src

This command:

1. Scans all pushable content types (assignments, pages, quizzes, new quizzes, discussions, announcements, files, rubrics, assignment groups, outcomes, modules, group categories)
2. For each type, fetches all items from Canvas and compares against local =CANVAS_ID= values
3. Items on Canvas with no corresponding Org heading are reported as orphans
4. Displays an orphan report in a =*canvas-orphans*= buffer
5. Prompts whether to delete the orphaned items from Canvas

** Orphan Report

The report buffer shows each orphan grouped by content type:

#+begin_example
org-canvas Orphan Report
Course: 12345 | https://canvas.example.com
============================================================

Assignments: 2 orphan(s)
  - [98765] Old Lab Assignment
  - [98766] Deleted Homework

Pages: 1 orphan(s)
  - [draft-page] Unused Draft

============================================================
Total orphans: 3
#+end_example

** Skipped Items

The following items are never treated as orphans:

- The course front page (pages with =front_page: true=)
- Sections (pull-only, not pushed)
- Per-section overrides (managed per-assignment)

   :END:
   #+end_src

3. *Build course content.*  Fill in the Org files for each content type you need.  A typical order that respects dependencies:

   - =assignment-groups.org= -- grade categories (Homework, Labs, Exams)
   - =group-categories.org= -- group sets for group assignments (optional)
   - =outcomes.org= -- learning outcomes (optional)
   - =rubrics.org= -- grading rubrics (optional)
   - =pages.org= -- syllabus, reference pages, instructions
   - =files.org= -- lecture slides, handouts, datasets
   - =assignments.org= -- homework, projects (link to rubrics and groups)
   - =quizzes.org= -- classic quizzes with embedded questions
   - =new-quizzes.org= -- New Quizzes with items
   - =discussions.org= -- discussion boards
   - =announcements.org= -- welcome announcement
   - =calendar.org= -- office hours, holidays, review sessions (optional)
   - =modules.org= -- organize everything into weekly modules

4. *Validate offline.*  Run =M-x org-canvas-validate= to catch property errors, missing links, and invalid dates before making any API calls.

5. *Preview changes.*  Run =M-x org-canvas-sync-dry-run= to see what would be created or updated without touching Canvas.

6. *Push to Canvas.*  Run =M-x org-canvas-sync=.  This syncs all files in dependency order and sets =CANVAS_ID= properties on each heading.

7. *Verify.*  Open Canvas in a browser and spot-check the published course.

** Importing an Existing Canvas Course

Adopting org-canvas for a course that already has content on Canvas.

1. *Initialize.*  Run =M-x org-canvas-init= with the existing course's ID.  Choose *not* to generate skeleton files (the pull will create them).

2. *Install pandoc.*  HTML content (page bodies, assignment descriptions) requires [[https://pandoc.org/][pandoc]] for conversion to Org format.  Without it, HTML is stored as raw markup.

3. *Pull everything.*  Run =M-x org-canvas-pull-all=.  This imports all content types in dependency order, creating one =.org= file per type.  Each heading receives a =CANVAS_ID= and =LAST_SYNCED= property so org-canvas treats them as existing items on future syncs.

4. *Review the import.*  Open each =.org= file and verify the converted content.  Fix any pandoc conversion artifacts (e.g., stray HTML tags in complex formatting).

5. *Make your first edit and sync.*  Change a heading in any file, then run =M-x org-canvas-sync=.  Only the modified item will be pushed -- unchanged items are skipped thanks to payload hashing.

6. *Version control.*  Run =git init= and commit the =.org= files (keep =org-canvas-credentials.el= in =.gitignore=).  You now have a full history of your course content.

** Semester-to-Semester Course Copy

Reusing last semester's Org files for a new section.

1. *Copy the directory.*  Duplicate your course folder and update =org-canvas-credentials.el= with the new course ID.

2. *Strip sync state.*  Delete all =CANVAS_ID=, =CANVAS_URL=, =LAST_SYNCED=, =CANVAS_UPDATED_AT=, and =PAYLOAD_HASH= properties from every heading.  This tells org-canvas to create fresh items instead of trying to update the old course:

   #+begin_src bash
   # Remove sync properties from all .org files
   sed -i '/:CANVAS_ID:/d; /:CANVAS_URL:/d; /:LAST_SYNCED:/d; /:CANVAS_UPDATED_AT:/d; /:PAYLOAD_HASH:/d' *.org
   #+end_src

3. *Update dates.*  Search for Org timestamps (=<2025-...>=) and update them to the new semester.  Per-section overrides in =assignments.org= need updated dates too.

4. *Update sections.*  Edit =sections.org= with the new semester's section names if they changed.

5. *Validate and push.*  Run =M-x org-canvas-validate=, then =M-x org-canvas-sync=.  Everything is created as new items in the new course.

** Incremental Edits During the Semester

Day-to-day workflow for an instructor maintaining a live course.

1. *Edit a single item.*  Open the relevant =.org= file (e.g., =assignments.org=), navigate to the heading, and make your changes.

2. *Sync just that item.*  With point on the heading, run =M-x org-canvas-sync-assignment-at-point=.  This pushes only the current heading without re-syncing the entire file.

3. *Sync a single module.*  If you changed several items in one content type, run the per-module sync command (e.g., =M-x org-canvas-sync-pages=) to push just that type.

4. *Full sync after large edits.*  After updating many files, run =M-x org-canvas-sync= to push everything.  Unchanged items are skipped automatically via payload hashing, so this is safe to run frequently.

** Collaborative Course with TAs

When multiple people edit content -- some via Org files, others via the Canvas web UI.

1. *Enable conflict detection.*  This is on by default (=org-canvas-detect-conflicts= is =t=).  Before each push, org-canvas compares =LAST_SYNCED= against the remote =updated_at= timestamp.

2. *Resolve conflicts interactively.*  If a TA edited an assignment in Canvas and you modified the same heading locally, =org-canvas-sync= opens a diff buffer showing both versions and prompts you to *push* (overwrite Canvas), *pull* (accept the TA's changes into your Org file), or *skip* (leave both untouched for now).  Use capital letters (=P=, =L=, =S=) to apply the same choice to all remaining conflicts.

3. *Force push when needed.*  If you're confident your local version should always win, use =M-x org-canvas-force-push= to bypass conflict detection entirely.

4. *Divide responsibilities.*  Consider splitting ownership -- the instructor manages content via Org files, TAs handle grading and student-facing interactions in Canvas.  Conflict detection prevents accidental overwrites in the overlap.

** Removing Content and Cleaning Up

Deleting items that are no longer needed.

*** Deleting a Single Item

1. Navigate to the heading in the =.org= file.
2. Run the delete-at-point command (e.g., =M-x org-canvas-delete-assignment-at-point=).
3. This deletes the item from Canvas and clears sync properties from the heading.
4. Optionally remove the heading from the Org file.

*** Deleting All Items of a Type

1. Run =M-x org-canvas-delete-all-assignments= (or the equivalent for another type).
2. Confirm the deletion.  All items of that type are removed from Canvas and sync properties are cleared.

*** Finding and Removing Orphans

When you delete a heading from an Org file but forget to delete it from Canvas:

1. Run =M-x org-canvas-cleanup-orphans=.
2. Review the orphan report in the =*canvas-orphans*= buffer.
3. Confirm deletion to remove stale Canvas items.

** Per-Section Date Overrides

Setting different due dates for different course sections.

1. *Pull sections.*  Run =M-x org-canvas-pull-sections= to populate =sections.org= with section headings and =CANVAS_ID= properties.

2. *Add override tables.*  In =assignments.org=, add a =#+NAME: overrides= table under the relevant assignment heading:

   #+begin_src org
   ,* Homework 1
   :PROPERTIES:

   :END:

   Default description...

   | Section                                      | Due At                 | Unlock At              | Lock At |
   |----------------------------------------------+------------------------+------------------------+---------|
   | [[file:sections.org::*Section A][Section A]] | <2026-09-16 Tue 23:59> | <2026-09-01 Mon 00:00> |         |
   | [[file:sections.org::*Section B][Section B]] | <2026-09-18 Thu 23:59> | <2026-09-01 Mon 00:00> |         |
   #+end_src

3. *Sync.*  Run =M-x org-canvas-sync=.  Sections are synced first (Tier 0), then assignments (Tier 1), then overrides (Tier 1.75).

4. *Modify overrides.*  Edit dates in the table, add new rows, or remove rows.  The override sync reconciles against Canvas: new rows are created, changed rows are updated, and removed rows are deleted.

** Pre-Semester Validation Checklist

A final review workflow before making the course visible to students.

1. *Validate all files.*  Run =M-x org-canvas-validate=.  Fix any errors (invalid properties, broken links, past-date warnings).

2. *Dry run.*  Run =M-x org-canvas-sync-dry-run= to confirm the sync plan looks correct.

3. *Sync everything.*  Run =M-x org-canvas-sync=.

4. *Check status.*  Run =M-x org-canvas-status= to see a summary of synced items per module and any issues.

5. *Clean up orphans.*  Run =M-x org-canvas-cleanup-orphans= to remove any leftover items from earlier drafts.

6. *Review in Canvas.*  Open the course in a browser, walk through the modules, and verify everything renders correctly.

7. *Commit to git.*  Commit the final state of all =.org= files so you have a clean snapshot of the published course.

* Troubleshooting

** Common Issues

*** "Request failed: Timeout"

The API request timed out. org-canvas has built-in timeout recovery that searches Canvas for recently created items and retries if needed.

*** "CANVAS_ID not found for linked item"

The item being referenced hasn't been synced yet. Run =org-canvas-sync= to sync in proper dependency order, or sync the referenced file first.

*** "API returned 404"

The item exists in your Org file but was deleted from Canvas. org-canvas will automatically retry the operation as a POST (create) instead of PUT (update).

*** "Authentication failed (HTTP 401)"

Your API token has expired or been revoked. Generate a new one at Canvas > Account > Settings > Approved Integrations, and update =org-canvas-credentials.el=.

*** "Permission denied (HTTP 403)"

Your token lacks the required scope. Ensure the token has full access to the course, or generate a new token with broader permissions.

*** "N heading(s) have LAST_SYNCED but no CANVAS_ID"

A heading was previously synced (has =LAST_SYNCED=) but its =CANVAS_ID= was removed.  Syncing it again would create a duplicate on Canvas instead of updating the existing item.  Either restore the =CANVAS_ID= property or delete the =LAST_SYNCED= property to treat it as a new item.

*** "Rate limited after N retries"

Canvas throttles API requests. org-canvas automatically retries on 429 responses with a per-second countdown in the echo area so Emacs doesn't appear frozen.  If the rate limit persists after all retries, try waiting a few minutes. Configure retry behavior:

| Variable                        | Default | Description                    |
|---------------------------------+---------+--------------------------------|
| =org-canvas-rate-limit-retries=   |       3 | Number of retries on 429/403   |
| =org-canvas-rate-limit-wait=      |      10 | Seconds between retries        |

** Dry Run

=M-x org-canvas-sync-dry-run= previews a sync: it reads from Canvas to work out what would change, but issues no request that writes.  Every module honors this, including the ones with hand-written sync loops (files, overrides, settings) that do not go through the shared push helper.  A dry run also leaves your Org files untouched -- no =CANVAS_ID=, =LAST_SYNCED= or =PAYLOAD_HASH= is recorded -- so a preview never makes an item look synced.

Note for files specifically: Canvas cannot update file content in place, so a real sync of a changed file deletes the old file object and uploads a new one under a new ID.  A dry run reports this as "Would REPLACE" and performs neither step.

** Unmanaged Assignment Groups

A Canvas assignment group that is not in =assignment-groups.org= is invisible to org-canvas.  That matters because of how weighted grading works: if the groups you manage already sum to 100, an assignment sitting in an unmanaged group counts toward *nothing*.  Canvas raises no error, the assignment looks normally graded to you and to students, and the weighting simply omits it.  Nothing is visibly wrong until final grades come out.

The usual instance is the stock =Assignments= group that every new Canvas course ships with.  Assignments you sync from Org are never at risk, because sync always places them in a group from =assignment-groups.org=; the exposure is an assignment created through the Canvas web UI, which can default into the stock group.

=org-canvas-sync-assignment-groups= therefore checks the remote group list after each sync and reports anything it does not manage:

| Situation                             | Reported as | Why                                                    |
|---------------------------------------+-------------+--------------------------------------------------------|
| Unmanaged group holding assignments   | error       | Those assignments are live silent zeros                |
| Unmanaged group that is empty         | warning     | Nothing is mis-weighted yet, but the trap is armed     |

This check cannot live in =org-canvas-validate=, which makes no API calls by design -- knowing that a group exists remotely means asking Canvas.  It costs one extra GET per group sync.

*Nothing is ever deleted.*  Canvas requires at least one assignment group, deleting one that holds assignments forces a move, and silently removing something you made in the web UI would be worse than the problem being reported.  To resolve the report, either add the group to =assignment-groups.org= (pull it with =org-canvas-pull-assignment-groups=) or move its assignments into a group you manage.

The mirror-image mistake -- managed groups whose =WEIGHT= properties do not total 100 -- is caught offline by =org-canvas-validate=, which needs no network.

** Unattended and Batch Runs

Under =emacs --batch= there is nobody to answer a prompt, and =y-or-n-p= reads from standard input -- so a prompt can silently consume input meant for something else and derail the rest of the run.  org-canvas therefore assumes yes for confirmation prompts when =noninteractive= is non-nil.

Set =org-canvas-assume-yes= to =t= to get the same behavior in an interactive Emacs:

| Variable                 | Default | Description                                      |
|--------------------------+---------+--------------------------------------------------|
| =org-canvas-assume-yes=    | =nil=     | Answer yes to non-destructive confirmations      |

This covers prompts that merely confirm the operation you already asked for, such as "sections.org already exists, pull will overwrite headings" or "buffer has unsaved changes, save first".  Prompts guarding mass deletion (=org-canvas-delete-all-*=, =org-canvas-prune-*=) still ask.

** Preflight Check

When running =org-canvas-sync=, a preflight check runs automatically before any content is synced. It validates:

1. =org-canvas-api-token= is set and non-empty
2. =org-canvas-course-id= is set and non-empty
3. The API connection works (fetches course name)

If any check fails, the sync aborts with an actionable error message before any API calls are made. Individual sync commands (e.g., =org-canvas-sync-pages=) do not run the preflight check.

1. *Parse* - Extract data from Org heading properties

- Present: UPDATE (PUT) operation
